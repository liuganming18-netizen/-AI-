## 冲突 1｜到底有几个「同一个策略」：6 个代码代际

**A 方（说明它们是同一个策略）**
- 2125 个 run 的 `fingerprints.rules.sha256` **全部相同**：`1f1167de…9a8ab`。
- 2125 个 run 的 `fingerprints.config.sha256` **全部相同**：`0faa5fc0…55d7b0`。
- 策略名、版本号、参数在 `inputs.json` 里完全一致。

**B 方（说明它们不是同一个对象）**
- `code_combined_sha256` 有 **6 个不同值**，覆盖的代码文件不同：

| 代际 | run 数 | `runner.py` | `engine.py` | `fill.py` | `engine_adapter.py` |
|---|---:|---|---|---|---|
| `1e419902415c` | 178 | `d7fa0ef2` | `6e22d7ce` | `15e29dd0` | `b08b61af` |
| `4c5a5c58b9b6` | 197 | `a3b5814a` | `6e22d7ce` | `15e29dd0` | `b08b61af` |
| `0d300eced7e5` | 201 | `07e98001`（=HEAD） | `c86d454b`（=HEAD） | `f050652c` | `fc956b55` |
| `f0b18131f457` | 374 | `07e98001`（=HEAD） | `8cf36bc5`（=工作树） | `f050652c` | `fc956b55` |
| `f24313aaeb72` | 631 | `45bcfb5d` | `8cf36bc5` | `f050652c` | `fc956b55` |
| `734c505d771a` | 544 | `d9e88158`（=工作树） | `8cf36bc5` | `f050652c` | `fc956b55` |

- 当前工作树只与 `734c505d` 逐位一致（18/18 文件），其余 5 代**无法用现有代码复现**。
- `f0b18131` 是「已提交的 runner + 未提交的 engine」的混合态，这个组合从未作为任何一次提交存在过。

**影响面**：跨代际合并统计会把撮合实现不同的结果加在一起。
最直接的外部证据：`BACKTEST-LOSS-03` 在旧代际（`fill.py = 15e29dd0`）上查出 **41.7% 成交价越界**
（价格被压到 0.01 网格），而 `run_batch_2026_aug_100.py` 文件头自述「旧批次缺合约规格时回退 0.01 默认步长」。

## 冲突 2｜初始资金：2000 还是 10000

**A 方（2000）**
- `config.py` 第 69 行：`initial_equity: float = 2000.0`。
- 2125 个 run 的 `summary.trading_summary.initial_equity` 全部为 2000.0。
- 所有批量脚本文件头写「本金严格 2000 USDT」。

**B 方（10000）**
- `config.py` 第 67–68 行注释：「10000 USDT 是本轮研究口径，已写入每次 Run 的 inputs.json / summary」。
- 冻结规则本身**不固定绝对本金**，只固定「每笔风险 = 提交时权益的 0.5%」这个比例。

**影响面**：绝对金额不可比。若对外说「净 +101 USDT」，必须先说清是 2000 本金下的 5.1%，不是 10000 本金下的 1%。

## 冲突 3｜账户模式：单标的独立账户 vs 组合级限制

**A 方（单标的独立）**
- 每个 run 目录 = 1 个标的 + 1 套 2000 本金 + 1 套独立账本。
- `runner.run_variant_abc` 每次只处理一个 `symbol`。
- `AUDIT-375-V3` 明确：「单币盈亏算术累计严禁解释为共享投资组合收益」。

**B 方（规则要求组合级）**
- 冻结规则 §4：「同币种最多一仓，全组合最多三仓；全部初始风险预算合计最多 1.5%；每仓名义最多 30%，总名义最多 90%」。
- `config.py` 里这些参数确实存在（3 / 0.015 / 0.30 / 0.90）。

**影响面**：在单标的账户里，组合级上限永远碰不到 ⇒ 规则里「最多三仓」「总风险 1.5%」这两条**从未被真实检验过**。
任何「组合回撤」「组合夏普」都无法从现有产物直接得到。

## 冲突 4｜币池：静态名单 vs 每日重算前 50

**A 方（实际用静态名单）**
- 8 个 `selected_*.json` 文件（20 / 50 / 100 / 100 / 100 / 100 / 528 个）。
- 每个批次的标的集合与某个 JSON **完全一致**（已逐项核对，见 `02_逐项清点.md` §2.4）。

**B 方（规则要求动态池）**
- 冻结规则 §6：「每天 UTC 00:00 按此前完整 30 天平均日成交额选前 50 个，要求上市满 90 天，排除 INDEX」。
- `AUDIT-375-V3` 把「每日前 50 币池凭据」列为四条红线之一，判定 164 个 run「缺流动性筛选凭据」。

**影响面**：静态名单用的是「今天还活着的币」，会引入幸存者偏差；且「出池不强制平仓」这条规则无从检验。

## 冲突 5｜时间窗口：统一日历边界 vs 逐币自适应 / 394 种窗口

**A 方（有统一窗口的批次）**
- `runs_sep_all_latest`：522 个 run 统一 `2026-09-01 00:00 ~ 2026-10-17 18:00`。
- `runs_aug100`：102 个统一 `2026-08-01 ~ 2026-09-14`。
- `runs_2025aug100`：102 个统一 `2025-08-01 ~ 2025-12-31`。

**B 方（没有统一窗口的部分）**
- `runs` 池有 **394 种**不同窗口；其中大量是 365 天滚动窗口，起点各不相同。
- `runs_sep50` / `runs_sep50_check` 是**逐币自适应**：49 种窗口，最早起点 `2020-01-24 16:00`。
- 脚本自述依据：`run_batch_round5_100.py` / `round6_100.py` 文件头「具备自适应时间窗口对齐能力」。
- `AUDIT-375-V3`：205 个 run 的实际窗口与请求窗口不一致，最短只跑了 36.29 天（请求 181 天）。

**影响面**：窗口不同 ⇒ 行情阶段不同 ⇒ 收益不可直接相加；也会让「同一标的多窗口」被当成多个独立样本。

## 冲突 6｜「四组对照」有三套，且结论方向相反

**A 方：`FLOW-OI-01`（阶梯叠加）**
- 组 4（基线 + 流量 + OI + 大户）= 144 笔，+14.72，PF 1.024。
- 相对基线 +101.53，**净收益下降 86.81**。

**B 方：`FACTOR-ENTRY-01`（平行过滤）**
- 组 3（拥挤度）= 169 笔，+272.55，PF 1.389；组 4（合并）= 102 笔，+143.83，PF 1.339。
- 相对基线 +101.53，**净收益上升 171.02**。

**C 方：冻结规则（只有三组 A/B/C）**
- A = 含 OI 门槛；B = 关 OI；C = 成本压力。没有「大户」「拥挤度」这两组。

**交叉证据**
- `FACTOR-ENTRY-02` 对 B 方做了方法复核，判定「在严格科学意义上不成立」：
  拥挤度组排除的 36 笔里 **24 笔是 2022 年指标缺失被判剔除**，这 24 笔亏损 −166.73，占总改善 **97.5%**；
  在 181 笔共同可用样本上真实改善只有 **+4.28 USDT（+1.6%）**。
- `FLOW-DATA-01` 对 A 方做了 PIT 抽查：**227/227 用了未收盘的 1h K 线**（信号时刻正好是开盘时刻，
  当根还有 60 分钟没走完），metrics 也 227/227 用了未结束的 5 分钟桶。

**影响面**：三套都不能直接作为验收依据，但**原因不同**（B 方是样本选择偏差，A 方是前视偏差，C 方是没有独立 run 目录）。

## 冲突 9｜合约规格：0 条 verified vs 全部 formal_pass=False

**A 方（规格缺失是原因）**
- `summary.instrument_spec.applicability` 分布：`unverified_historical` 1682、`contradicted` 60、`not_listed` 8、**`verified` 0**。
- 典型说明：「没有任何快照的 serverTime 早于窗口开始 ⇒ 窗口起点之前无证据」。

**B 方（可能是判定过严）**
- 同一批 run 的 `spec_status` 多为 `spec_applied`（规格已实际用于取整）。
- 也就是说：**取整用了规格，但「这份规格在该窗口一直适用」证不出来**。

**影响面**：这两件事必须分开说——「成交价按规格取整了」≠「规格在历史上正确」。
`FULL_SWEEP_200x100` 报告也把 `formal = 0` 解释为预期内。

## 冲突 11｜两套回测入口

**A 方：批量脚本**
- `run_batch_*.py` 直接调 `EventTrendRunner`，写 `回测日志/event_trend_v0_1/runs*`，产物 17 个文件齐全。

**B 方：后端接口**
- `框架/backend/backtest_runner.py` 第 918 行按 `strategy_id == "WX_EVENT_TREND_V0_1"` 走 `_run_event_trend`，写 `bt_*` 目录。
- 现有 5 个 `bt_*` 目录：4 个 `interrupted`（服务重启导致），1 个标 `succeeded` 但目录里**只有 `run.json` 一个文件**，无 inputs、无 summary、无账本。

**影响面**：通过界面/接口发起的回测，目前**没有任何一个完整成功的产物**；
所有可用产物都来自批量脚本。两条路径是否等价，没有对账证据。

## 未知项（连证据都没有）

1. `selected_*.json` 是怎么生成的：工程里**没有**生成这些名单的脚本，也没有生成时点记录。
2. `runs` 池里 21:00Z 与 22:00Z 两簇（共 543 个 run）由哪个脚本产生：脚本文件里没有对应输出目录常量，
   `run_full_sweep_200x100.py` 明确「不写 run 目录」，排除。
3. `runs_sep50_full` / `_strict` 的 0 成交：是「没有候选」还是「候选被拒」，报告层没写。
4. 375 个旧结构 run 的 `chart.json` 是否可用：旧结构没有 `precision` 块，无法与成交逐笔对齐验证。
5. `reconstructed/` 三个目录是谁在什么条件下生成的：目录内只有 `RECONSTRUCTION_NOTICE.json` 与事件文件，
   没有 inputs、没有账本，无法归入任何批次。
