# 05 · 聪明钱：历史不足时怎么做（前向分析，不补造、不替代）

> 整改要求 5：**明确聪明钱历史不足时的处理：使用现存真实快照开展前向分析，
> 不补造历史，不用大户多空比替代。**

---

## 一、先说事实（全量清点，不是抽样）

`scripts/70_聪明钱基线.py` 逐个读了 `框架/backend/快照/smart_money/` 下全部快照文件：

| 事实 | 值 | 说明 |
|---|---|---|
| 快照文件数 | **523** | 池内 526 币里缺 3 个：`1000000BOBUSDT`、`PROMPTUSDT`、`PUMPBTCUSDT` |
| 一小时内刷新 | **52** | `_progress.json` 声明 `total=51 / done=51`，实测 52 个文件的 `fetched_at` 在一小时内 |
| 停更 >24 小时 | **471** | 停更时长中位 **373.7 小时（15.6 天）**，最长 374.0 小时 |
| 历史序列 | **没有** | 按 `symbol` 覆盖写同一文件，只有当前值，没有任何时间序列表 |
| 队列定义 | **未公开** | `cohort_definition = "undisclosed（币安未公开「聪明钱」队列的成员判定规则）"` |
| 明细字段 | 11 个 | `avgEntryPrice / currentPositions / currentQty / side / lastTradeTime / traders / userType / topTraderId / netPositions / timeRange / traderName` |
| 时间戳 | 三种 | `fetched_at`（采集）、`last_trade_time`（成交）、`upstream_snapshot_time`（上游快照） |

**一句话**：这不是「历史数据少」，是**只有当前值、没有历史**；
而且**当前值也只覆盖 52 个币**，另外 471 个币的快照是 15.6 天前的存量。

## 二、为什么不能补造历史

| 理由 | 具体说明 |
|---|---|
| 接口只给当前队列 | 币安这个端点的语义是「此刻该队列的持仓明细」，**没有按时间回看的参数** |
| 没有历史端点 | 工程内不存在任何可回补该数据的历史接口；`raw/` 下也没有这类原件 |
| 补造必然是未来函数 | 「把 2026-10-26 的队列成员回填到 2026-09-01」= 用未来信息构造过去特征，任何回测结论都会失真 |
| 覆盖不全使补造更荒谬 | 471 个币的「当前值」本身已经是 15.6 天前的，回填连"当前"都不成立 |

⇒ **不补造。** 该数据只能从「现在」开始积累。

---

## 三、为什么不能用大户多空比替代

| 维度 | 聪明钱快照 | 大户/多空比（`metrics`） |
|---|---|---|
| 观测对象 | 一批**具体队列成员**的逐笔持仓（含 `topTraderId`、`side`、`avgEntryPrice`） | 全体大户/全市场的**加总比值**（4 个比值列） |
| 时间性质 | 当前值，覆盖写 | 5m 序列，**但停在 2026-10-14T23:55Z，全池停更 11.12 天** |
| 口径透明度 | 队列定义**未公开** | 币安公开字段，但两组字段互为别名（全量 0 差异） |
| 能否互相替代 | **不能**：一个是「谁在持什么」，一个是「多空人数/持仓的比」 | 同左 |

两条硬理由：
1. **对象不同**：比值是加总统计量，无法还原「某个大户的进出」，而聪明钱的价值恰在个体行为；
2. **时间不对**：用一份停更 11 天的比值序列去替代「当前队列」，等于拿旧口径冒充新数据。

⇒ **不替代。** 两者只能并列展示，不能互换。

## 四、前向分析怎么做

### 4.1 已经做的：t0 基线（只读复制，无下载）

`scripts/70_聪明钱基线.py` 把 523 个快照**原样复制**到 `forward/t0/`，
并在 `out/70_smart_money_t0.json` 的 `t0_anchors` 里逐文件记下
`symbol / bytes / sha256 / fetched_at_utc / age_hours`。

用途：以后任何一次前向分析，都能用 sha256 判断「这个币的这份快照，相对 t0 有没有变过」，
而不是靠猜。

### 4.2 还没做的：追加式快照归档（**未启动，需批准**）

设计要点（**不是**现在就跑）：

```
每 N 分钟（建议 5 分钟，与现有 300 秒刷新节拍对齐）
  读本地 523 个快照文件（只读磁盘，**不新增任何 API 调用**）
  对每个币算 digest = sha256(成员集合 + 各成员 currentQty/side + fetched_at)
  若 digest 与上一轮相同 ⇒ 不写（这是上一单的教训：每 2 秒全量重写会写爆磁盘）
  若变了 ⇒ 追加一行到 smart_money_forward.jsonl：
      {symbol, fetched_at, n_details, net_qty, wavg_entry,
       members_digest, added:[...], removed:[...]}
```

体积估算（**估算，未实测**）：每行约 200 字节；若每币每天变化 5 次，
523 × 5 × 200 B ≈ **0.5 MB/天 ≈ 180 MB/年**；用 digest 去重后不会随轮询频率线性膨胀。

**为什么还没启动**：它是新增的持续写盘任务，属「新增运行组件」，
按工单纪律「涉及新增下载的范围与资源需求单列，不自行启动」类比处理——**先报后做**。

### 4.3 分析口径（先把规矩定死，避免以后又吵）

| 要求 | 具体做法 |
|---|---|
| 禁止前视 | 特征只用 `fetched_at ≤ t` 的快照；标签用 `t` 之后的 1h/4h 收益 |
| 只在有效样本上出结论 | **只有当前在刷的 52 个币**能做时序；其余 471 个只能做一次性截面，且必须标「存量 15.6 天」 |
| 队列定义未知要写进结论 | 每条结论都要带「队列判定规则币安未公开」这句限定 |
| 最小样本 | 至少 **30 个交易日 × 20 个币 × 50 次成员变化**；不足就写「样本不足，不出结论」 |
| 不许与大户比值混算 | 两套数据分别建模，不许把一个当另一个的代理变量 |

### 4.4 资源需求（单列）

| 项 | 值 |
|---|---|
| 新增 API 调用 | **0**（只读本地快照文件） |
| 新增磁盘 | 约 0.5 MB/天（估算） |
| CPU | 每轮 523 次 sha256（约 6 MB 读盘），可忽略 |
| 需要批准的事项 | 是否启动这个持续归档任务；启动后它的产物放哪里（建议 `数据/forward/smart_money/`，不塞进 `evidence/`） |
