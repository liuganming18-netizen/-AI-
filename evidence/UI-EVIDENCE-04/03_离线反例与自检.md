# 03｜离线反例与修复后样例自检

> 工单第 7 条：「增加离线反例：错误 run、缺源文件、哈希不符均能被检查识别。」

复现：
```
python evidence/UI-EVIDENCE-04/queries/negative_tests.py
python evidence/UI-EVIDENCE-04/queries/dryrun_fixed_outputs.py
```
原始读数：`out/negative_tests.json`、`out/fixed_sample_check.json`、样例目录 `out/fixed_sample/deliv/`

---

## 1. 校验器设计

`queries/lib_verifier.py` 提供唯一入口：

```python
verify_delivery(deliv_dir, project_root) -> dict
```

同一个函数既跑真实交付（UI-03），也跑临时构造的反例 —— 不存在「测试专用宽松路径」。

判定三态：**PASS / FAIL / UNVERIFIED**。未验证不计入通过。

六个检查项：

| 编号 | 检什么 |
|---|---|
| C1 | CSV 声称的字段路径能否在源文件里真实走到，值是否一致 |
| C2 | 是否把哈希来源谎称成 manifest（manifest 缺失 / `run.json.hashes` 为空 ⇒ FAIL） |
| C3 | 清单是否排除自身、大小与哈希是否逐行一致 |
| C4 | 截图数量与报告是否矛盾、是否存在字节重复 |
| C5 | 是否绑定前后端源码 / 构建产物 / 测试脚本 |
| C6 | 页面 run_id 与磁盘 `run.json.run_id`、CSV run_id 是否三方一致 |

---

## 2. 离线反例：9/9 全部识别

在临时目录构造假交付（`tempfile` + 自动清理，零网络零后端），逐个注入缺陷：

| # | 场景 | 期望失败 | 实际失败 | 识别 |
|---|---|---|---|---|
| N0 | 基线（全部正确） | — | — | ✓ |
| N1 | **错误 run**（页面 run_id 改成 `run_WRONG_999`） | C6 | C6 | ✓ |
| N2 | **缺源文件**（删掉 `summary.json`） | C1 | C1 | ✓ |
| N3 | **哈希不符**（清单里改一个字符） | C3 | C3 | ✓ |
| N4 | **manifest 谎称**（CSV 写 manifest 来源但文件不存在） | C2 | C1 + C2 | ✓ |
| N5 | **清单自指**（自身写成 size=0 空哈希） | C3 | C3 | ✓ |
| N6 | **重复截图改名**（state 复制自 view） | C4 | C4 | ✓ |
| N7 | **字段路径错**（`trading_summary.*` 实际不存在） | C1 | C1 | ✓ |
| N8 | **数量矛盾**（报告 24 张，实际 3 张） | C4 | C4 | ✓ |

**9/9 识别成功**（`negative_tests.json` → `"全部识别": true`）。

三点说明：

1. **N4 同时报 C1 + C2**：CSV 加了一行 `manifest.json / …`，C1 也会查这一行（manifest 不存在 ⇒ FAIL）。这是正确行为，不是误报。
2. **哨兵值处理**：当 CSV 的字段路径写 `missing` / `—` / `字段不存在` 这类**明确表示缺失**的哨兵时，C1 判「双方均缺失 ⇒ 一致」，不 FAIL。但哨兵必须与实际情况相符 —— 声称缺失而实际有值，仍会 FAIL（走值比对）。
3. **反例只覆盖「检查能力」**，不覆盖「修复版能跑通」。后者见 §3。

## 3. 修复后样例自检

`dryrun_fixed_outputs.py` 用**修复版逻辑**离线生成一份完整交付样例（`out/fixed_sample/deliv/`），复用 UI-03 的真实 PNG，源产物指向真实 run，然后交给 `verify_delivery()` 自检。

样例内容：

| 文件 | 生成方式 |
|---|---|
| 25 个 `*.png` | 从 UI-03 原样复制 |
| `04_…对账表.csv` | 按 P4 重写，字段路径全部取真实命中值 |
| `audit_ui_verification.json` | 补 `run_id_aligned` / `official_sha_source` / `manifest_status` / `summary_field_layer` |
| `00_报告.md` | 按 P6 动态统计数量 |
| `08_文件清单与哈希.csv` | 按 P5 最后生成、排除自身（**28 行**） |
| `08_清单自身哈希.json` | 按 P5 单独保存自身哈希 |
| `09_源码与构建产物版本绑定.json` | 按 P7 绑定，4 类齐全、缺失项为空 |

自检结果：

| 编号 | 判定 |
|---|---|
| C1 字段路径 | **PASS** |
| C2 manifest 声称 | **PASS** |
| C3 清单自身 | **PASS**（28 行，自身已排除） |
| C4 截图唯一性 | **FAIL** —— 3 组字节重复 |
| C5 版本绑定 | **PASS**（`frontend_src`/`frontend_dist`/`backend`/`test_script` 全在） |
| C6 run_id 对齐 | **PASS** |

### 为什么 C4 仍然 FAIL —— 这是好事

样例复用了 UI-03 的真实截图，其中 3 组字节完全相同：

```
d7ccc274a0f9  state_position_normal.png = view_05_position_panel_and_daemon.png
8d0951525d49  state_signal_normal.png  = view_02_signal_list_panel.png
0936f38dfb06  state_stop_trail_normal.png = view_06_stop_trail.png = view_07_gate_and_pending.png
```

**这不是脚本没修好，而是截图本身需要重拍。** 修复版脚本只能保证「如实统计并标出重复」，不能凭空造出三张不同的画面。

按工单第 6 条，这 3 个「状态·正常态」必须记 **未验证**，不能写成「已覆盖」。重拍需要起浏览器，属集成采证范围，待 A 通过后另开。
