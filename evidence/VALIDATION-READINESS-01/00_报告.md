## 〇、三句话结论

1. **入口是齐的，而且是同一条链**：从冻结规则文件 → `EventTrendConfig` → 数据加载 → 状态机出候选 → `run_event_trend_backtest` → `trading_core` 撮合与结算 → 17 个逐笔产物 + 四类指纹，全部走同一套生产代码，**不需要另建框架**。
2. **四项能力里三项现成可用**（指定时间范围、保留原始逐笔、版本指纹），**固定仓位配对可用但实现不在策略包内**（在 `evidence/BREAKEVEN-02/code/`，不参与代码指纹），这是下一阶段唯一需要「带路径复用」的地方。
3. **真正挡住结果可信的不是入口，是数据与口径**：PIT 资格全 False、历史合约规格 0 条 verified、暂无可证明的样本外数据——这三项在 `OOS-READY-01` 已记录，本单不重复测试；入口侧只有两项会影响「结果可信」（固定仓位代码无指纹、无组合回撤指标），其余都是方便性问题。

## 二、四项能力核对

完整表见 `out/02_能力核对表.csv`。

| 能力 | 结论 | 关键证据 |
|---|---|---|
| **固定仓位配对** | **支持，但实现不在生产包内** | `evidence/BREAKEVEN-02/code/be_core.py` 的 `install(breakeven_r, fixed_quantities)`；`decide_entry` 内用 `replace(intent, quantity=fq)` 把数量钉死。`02_run_fixed.py:run_window` 每个信号单独隔离成一次回放，并断言 `len(trades)==1`（隔离被破坏直接抛错）。已有产物 `evidence/BREAKEVEN-02/out/raw_fixed.jsonl`（201 事件口径）。**风险**：`CODE_FILES` 20 个文件不含它，产物里没有能证明「用的哪一版配对代码」的指纹 |
| **指定事件范围** | **支持（适配器级）** | `engine_adapter.py:341` 的 `candidates: List[CandidateSnapshot]` 传单元素即单事件隔离回放。`runner` 层没有事件过滤参数，需要调用方自建循环——现成样例就是 `02_run_fixed.py` |
| **指定时间范围** | **支持** | `load_symbol_data(start_date, end_date, allow_auto_window=False)`。必须传 `False`：`True` 会在窗口数据不足时静默换成「上线后 180 天」，跑出来的日期跟标称窗口对不上（`runner.py:210-212` 已写警告）。批次脚本把窗口写死在模块常量里，改窗口要改脚本 |
| **保留原始逐笔输出** | **支持** | 17 个文件：`candidates / decisions / events / transitions / validation_results / orders / fills / positions / trades / rejects / funding / ledger / equity_curve / instrument_spec / inputs / summary / manifest`（`.jsonl` 逐笔 + `.json` 汇总）。`manifest.json` 记每文件 `bytes` 与 `sha256`，原子提交保证不存在半套 run |
| **版本指纹** | **支持** | 四类齐全：`rules`（冻结规则文件哈希）/ `code`（20 文件逐个 + combined，带 `missing` 列表）/ `config`（参数哈希）/ `inputs`（各 DataFrame/数组内容哈希）。另有 `pit_guard_version` 与 `spec_status` |

**结论**：下一阶段不需要另建框架。唯一要额外做的事是把 `evidence/BREAKEVEN-02/code/` 两个文件（`be_core.py`、`02_run_fixed.py`）连同其 sha256 一起带进新工单，作为「配对实现」的显式版本声明。
