## 三、C2 UI 数据与同响应、源账本一致 → 不通过

### 3.1 缺陷 1：缺 live 库时 `/api/v1/paper/accounts` 硬崩 500

**复现**（进程内，不需要起服务）：

```
LIVE_DIR=/tmp/wx_live_empty（空目录）
→ live_api.paper_accounts()
→ _paper_accounts_legacy()  L637  start_ms = L.get_live_start_ms()
→ live_store.get_live_start_ms() → get_run() → live_conn(ro=True)
→ sqlite3.OperationalError: unable to open database file
```

`_paper_accounts_legacy` 只 catch 了 `LedgerUnavailable` / `LedgerIdentityMismatch`，**没 catch `sqlite3.OperationalError`** ⇒ 未处理异常 ⇒ HTTP 500。

对照：同一批接口的 `/paper/positions`、`/paper/orders`、`/paper/identity` 在正常环境都返回 OK，说明**降级能力是有的，只是这个接口漏了**。

**性质**：这是「依赖缺失时该降级却硬崩」，属 C2 的实质缺陷。UI 上会表现为页面报错或空白，而不是「如实显示不可用」。

### 3.2 缺陷 2：`service_manager` 无法做数据路径隔离（部署安全问题）

`ServiceConfig.resolve_paths()` 里：

```python
if not self.market_db:
    p = self.project_root / "数据" / "市场数据" / "db" / "market_v2.sqlite3"
    self.market_db = str(p if p.exists() else ...)
if not self.paper_ledger_dir:
    self.paper_ledger_dir = str(self.project_root / "数据" / "paper")
```

**完全不读环境变量** `MARKET_DB` / `PAPER_LEDGER_DIR`。随后：

```python
shared_env["MARKET_DB"] = str(self.cfg.market_db)
shared_env["PAPER_LEDGER_DIR"] = str(self.cfg.paper_ledger_dir)
```

把调用方传进来的环境变量**覆盖掉**。

**实测后果**：我 13:47 用

```
PAPER_LEDGER_DIR=/tmp/wx_c/paper MARKET_DB=/tmp/wx_c/market.sqlite3 \
  service_manager.py start --port 18787 --pid-dir /tmp/wx_c/pid --log-dir /tmp/wx_c/logs
```

起了一个「以为在隔离环境」的实例，结果：

| 目标 | 实际 | 结果 |
|---|---|---|
| 账本 `数据/paper` | mtime 仍 10:54 / 11:13 | **未写**（因为 API 只读、Worker 不碰账本） |
| 行情库 `market_v2.sqlite3` | mtime 变成 **13:47:27** | **被写了**（Worker 跑了 tail_sync） |

日志明确写着：

```
[adapter] 127.0.0.1,::1:18787 db=.../数据/市场数据/db/market_v2.sqlite3
```

**性质**：这不是「测试没做好」，是**产品本身缺少隔离手段**。任何想在不碰生产数据的前提下验证系统的人，用现有入口都做不到——只能改代码。

> **我为此造成的影响**：Worker 对生产行情库跑了若干 `tail_sync`（补齐最新 1h K 线，每标的 4 根，幂等增量）。这不破坏历史数据，但**是不该发生的跨环境写入**。已立即 SIGTERM 停止两个进程并释放 18787 端口。生产账本 4 个文件 mtime 未变，未受影响。

### 3.3 缺陷 3：`service_manager stop` 停不掉自己启动的进程

实测输出：

```
[!] 拒绝停止未知 worker 进程：pid=19809, cmd=''
[!] 拒绝停止非本项目 API 进程：pid=19806, cmd=''
```

`cmd=''` ⇒ 取不到 cmdline ⇒ 判定「非本项目」⇒ 拒绝停止。

**这是防误停做到了、但正常停止也失效了。** 最后我改用 `os.kill(SIGTERM)` 手工停止，两个进程均正常退出（rc=0），18787 端口释放。

**性质**：B 任务里我判「隔离与停止范围正确」，是因为我测的是 `unified_runtime` 自身的 SIGTERM 行为（通过）。**`service_manager.stop()` 这条路径没有通过**——这是 B3 结论的边界，必须说清。

### 3.4 正面项（也要记）

正常环境下四个接口都能返回，且 `paper_accounts` 的 cash/equity 与源账本**排除作废后**的口径一致（见 §四）。

## 五、为什么这一轮没有起 HTTP 服务

`service_manager` 无法做数据路径隔离（§3.2）。起一次服务就会写生产行情库。为不再产生跨环境写入，C2 改为**进程内直接调处理函数**取证：

- 正常环境探测 → 四个接口的真实返回与异常
- 缺 live 库探测 → 复现 500 的完整堆栈
- 账本直读 → 与接口返回值逐项比对

代价：没有验证「浏览器渲染出来的数字」。但那部分已在 `02_UI差异独立复核.md` 里用截图逐字核对过，且结论是不通过。

## 七、给用户的可执行结论

1. **C1 不通过**：16 视图声称只有 10 个真实画面，需要重拍 `view_11~14`、`view_08~10`、`view_02/03` 这 9 个文件对应的真实页面。
2. **C2 不通过**，三个具体修法：
   - `_paper_accounts_legacy` 补 catch `sqlite3.OperationalError`，降级为 `missing_reason`
   - `ServiceConfig` 增加从 `MARKET_DB` / `PAPER_LEDGER_DIR` / `PAPER_LOCK_DIR` 读取（或加 `--market-db` / `--paper-dir` 参数）
   - `service_manager.stop()` 在 `cmd=''` 时不要直接拒绝，改为按 pidfile 归属判定（pidfile 是自己写的，应可信）
3. **C3 通过**，无需处理；但建议把 `paper_state.cash` 与 `account_view.cash` 的口径统一，避免后人读错。
