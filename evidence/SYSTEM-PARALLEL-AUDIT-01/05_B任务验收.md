### 4.2 已知瑕疵（如实记录，不因此判不通过）

**停止后 `overall_health` 仍报 `healthy`，而 `execution_daemon` 已 `stopped`。**

根因在 `get_full_status`：

```python
overall = "healthy"
if self.stats.get("last_error"):
    overall = "degraded"
if not self._is_process_alive(self.pid) and self.stats.get("health") == "running":
    overall = "unhealthy"
```

停止时进程自己还活着，所以 `_is_process_alive(self.pid)` 为真 ⇒ 不会判 unhealthy。这个逻辑在「进程存活」的前提下是自洽的，但**最后一帧状态文件会留下 `healthy` + `stopped` 的组合**。

**影响**：任何只看 `overall_health` 不校验 PID 存活的读者，会以为进程健康。这属 C 任务「UI 数据与同响应一致」的观察点，已转记。

`service_manager.stop()` 的隔离判据（代码级）：

```python
if "unified_runtime.py" in cmd and (str(self.cfg.backend_dir) in cwd
                                    or str(self.cfg.project_root) in cwd):
    os.kill(r_pid, signal.SIGTERM)
```

**cmdline + cwd 双校验**，只杀自己启动的 runtime。这与「按端口杀」「按名字杀」有本质区别——后者会误伤同名进程或占用同端口的其他程序。

## 七、我这一轮犯的错

### 7.1 状态文件取值路径错，误判「PID 不一致」

**现象**：首跑 B2 报 `PID一致=False`、`status文件PID一致=False`，看起来像产品缺陷。

**根因**：状态文件是**嵌套**结构：

```json
{"runtime_identity": {"pid": 19624, ...}, "execution_daemon": {"status": "running"}}
```

我在顶层取 `sj.get("pid")`，取到 `None`。`--status` 输出同样是嵌套的，我也在顶层取。

**修复**：改为 `sj["runtime_identity"]["pid"]`。修复后 PID 一致。

**教训**：看到「不一致」先怀疑自己的取值路径，别急着判产品不通过。这次如果我直接写「PID 不一致 ⇒ 状态不准确」，就是一个假阳性结论。

### 7.2 第一次跑时忘了建行情库

首跑 `--once` 返回 `no such table: candles`。这次**不是 bug**——是我没建市场库。但它反而成了一个有价值的对照：证明错误不会被吞掉。
