## 1. 策略身份 / 运行身份（三个不同的东西，别混用）

| 名称 | 取值（当前实测） | 存在哪 | 谁写的 |
|---|---|---|---|
| `strategy_key` | `wyckoff_v0_1` | `live_signal.strategy_key` | 持久化函数写死 |
| `strategy_version` | `v0.1.0` | `live_signal.strategy_version`＋`payload.strategy_version` | 取自 `EventTrendConfig.strategy_version` |
| `rule` / `model_version` | `FT-LOW4H` / `FT-LOW4H-EXP-V2.2` | **只在运行身份里，信号行上没有** | `EventTrendConfig.rule` / `.model_version` |
| `param_hash` | `82dec362c182`（= 生效视图 sha256 前 12 位） | 接口顶层 `param_hash` | `paper_engine.approved_params().view_sha256` |
| `params_source` | `frozen_view_10_研究参数生效视图_v2_2_user5000_shared` | 接口顶层 | 同上 |

**硬事实（必须写进双方实现）：**

1. **信号行上的 `strategy_version` 是 `v0.1.0`，不是 `FT-LOW4H-EXP-V2.2`。**
   接口顶层的 `strategy_version=FT-LOW4H-EXP-V2.2` 来自执行侧（`paper_engine`），
   与信号行的 `strategy_version` **不是同一个口径**。
   ⇒ 任何「按 strategy_version 对账」的做法都会错。对账要用 `signal_uid` + `param_hash`。
2. **`payload_json` 里没有 `rule` / `model_version`**（实测 `payload_has_rule_or_model_version=false`，
   payload 31 个键全是 `CandidateSnapshot` 字段）。
   ⇒ 信号行**无法自证**自己属于 FT-LOW4H 规则，只能靠运行身份反推。
3. `live_signal` 表有 `config_hash` / `data_version` 列，但**持久化函数没有写它们**（实测为 `null`）。

出处：`策略/WyckoffMaster/event_trend_v0_1/config.py:14-17,79-80`；
`框架/backend/unified_runtime.py:68-72,2114-2160`；`框架/backend/live_api.py:81-120`。

## 3. 来源 / 研究标签（`origin`）

`live_signal.origin` 是**唯一**决定「进不进当前交易信号区」的字段。库上**没有 CHECK 约束**，
所以取值靠契约约定，不能靠数据库兜底。

| 取值 | 语义 | 进当前区？ | 现状 |
|---|---|---|---|
| `live` | 本次运行实时产出 | **是** | 运行中在用 |
| `recovered` | 重启后仍在成交时效内的真实候选 | **是** | 运行中在用 |
| `replay` | 回放产出 | 否 | 运行中在用（`run_replay`） |
| `historical_research` | 显式导入的旧研究信号 | 否 | 旧导入器在用 |
| `test` | 测试 | 否 | 测试在用 |
| `research` | **本单新提议**：研究/未批信号 | 否 | **仅在本单隔离库验证过，尚未进任何生产代码** |

当前区白名单原文：`origin IN ('live','recovered')`。
⇒ 接入研究信号时，**必须显式传 `origin`，禁止用默认值**（默认是 `live`）。

出处：`框架/backend/live_api.py:336`；`unified_runtime.py:2529,2802,2876`。

## 4. `signal_uid` 幂等键

- 值 = `CandidateSnapshot.candidate_id` = `f"cand_{event_id}_{close_time_ms}"`（确定性）。
- 写入语句：`INSERT … ON CONFLICT(signal_uid) DO UPDATE SET payload_json, executable_state, display_state, updated_at`。
- 语义：**同键只一行**；`first_seen_at` 与事件时间/价格事实**永不改写**，只补 payload 与状态。
- 已实测（本单隔离库）：同键写两次 ⇒ `new=1, updated=1`，行数仍为 1，`first_seen_at` 不变、`updated_at` 推进。

出处：`state_machine.py:605`；`unified_runtime.py:2146-2151`。

## 5. 时间口径（四个时刻不许互相替代）

| 字段 | 含义 | 现状取值 |
|---|---|---|
| `event_time` | 事件（突破 1h 收盘）时刻 | `= snapshot_time_ms` |
| `confirmed_at` | 确认时刻 | `= snapshot_time_ms` |
| `available_at` | 决策可得时刻 | `= snapshot_time_ms`（与 confirmed 相同） |
| `bar_open_time` / `bar_close_time` | 真实 bar 边界 | `snapshot−1h` / `snapshot` |

**已知缺口**：`available_at` 与 `confirmed_at` 恒相等，**没有表达 OI 发布延迟**。
payload 里的 `pit_proven=false` / `pit_assumption_note` 是唯一提示。
⇒ 研究信号接入时，若来源是回放，`available_at` 必须由回测侧给出**真实可得时刻**，
不得用「回放跑完的时刻」代替。

## 7. 反重力侧交付必须满足的输入（本单提出，待主代理核）

回测包交给 Work 接入前，每条信号至少要能回答：

1. **运行身份**：`run_id`、`strategy_key`、`rule`、`model_version`、`param_hash`（或生效视图 sha256）、
   数据窗口起止、数据版本（若未冻结必须写 `null` 而不是猜）。
2. **来源标签**：这条信号属于「回放」还是「研究」，用 §3 的取值，**不得留空**。
3. **幂等键**：能给出确定性的 `candidate_id`（或等价键），使重复接入不新增行。
4. **四个时刻**：`event_time` / `confirmed_at` / `available_at` / `bar_close_time`，
   其中 `available_at` 必须是「当时可得」的证据或明确标 `unproven`。
5. **批准状态**：`approved=false`（当前只能为 false）＋ 原因（G01–G05 pending / 参数未批）。
6. **可执行状态与拒绝原因**：`executable_state` + `executable_reason`（若不可执行）。

缺任一项 ⇒ Work 按工单「识别不清即阻塞」处理，不接入。

## 8. 需要主代理裁决的两件事（本单不擅自选择）

1. **研究信号的可视落点**：现有信号页面只请求 `scope=current`，结构上不显示研究信号。
   要么只落审计通道（页面不可见），要么接到已有的观察区（页面已渲染，只读）。
   两条路都要么不改前端、要么改前端架构（工单禁止）⇒ 需裁决。
2. **`origin` 是否新增 `research` 取值**：新增需改运行时代码（本单未改）。
   未批准前，研究/回放信号应复用既有的 `replay` / `historical_research`。
