## 一、 缺陷原因定位与最小修复

### 1. FT-BASELINE-05 错误填 0 根因定位
经源码溯源查明，在 FT-BASELINE-05 的表格生成脚本 [`evidence/FT-BASELINE-05/code/metrics_entrypoint.py`](file:///Users/boos/Desktop/威科夫因子共振趋势/evidence/FT-BASELINE-05/code/metrics_entrypoint.py) 第 253 行中：
```python
old_r = df_old_map.get(sym, {})
old_funding = float(old_r.get("funding_fee", 0.0))
old_amount = float(old_r.get("trade_size", 0.0))  # ❌ 错误根因：字段名误写为 'trade_size'
```
在输入源文件 [`evidence/FT-DATA-01/out/05_旧引擎基准成交.csv`](file:///Users/boos/Desktop/威科夫因子共振趋势/evidence/FT-DATA-01/out/05_旧引擎基准成交.csv) 中，记录持仓数量的列名实际为 **`qty`**，不存在 `trade_size` 列。由于字典使用 `.get("trade_size", 0.0)` 读取，找不到键时静默回退为默认值 `0.0`，导致下游计算出的 `old_amount = 0.0`，进而导致 `数量比例(旧/FT) = 0.0`。

同时，原脚本在计算 `资金费比例` 时未对收付符号做彻底规范化（旧引擎正数代表支出扣除，FT 负数代表支出减少），导致算出的比例出现负号混乱。

### 2. 最小修复方案
1. 将数量读取字段名修正为 `old_r["qty"]`，并增加判空强校验（若为 None 或 <=0 直接中断并报错，严禁填 0 兜底）；
2. 规范化收付符号：
   - 旧引擎现金流贡献：$f_{\text{old}} = - \text{funding\_fee}$（收取为正，支付为负）；
   - Freqtrade 官方现金流：$f_{\text{new}} = \text{funding\_fees}$（收取为正，支付为负）；
   - 资金费比严格定义为：$\text{资金费比} = \frac{f_{\text{old}}}{f_{\text{new}}}$，因两引擎收付方向 100% 相同，相除结果严格为正数；
3. 计算 `数量比 = 旧数量 ÷ 本次数量` 与 `偏差 = |数量比 - 资金费比|`，在浮点极限下验证吻合度。

## 三、 差额来源实际计算与核对结论

1. **真实数量追溯**：
   - 5 笔交易的旧数量全部取自基准文件 [`evidence/FT-DATA-01/out/05_旧引擎基准成交.csv`](file:///Users/boos/Desktop/威科夫因子共振趋势/evidence/FT-DATA-01/out/05_旧引擎基准成交.csv) 的 `qty` 列；
   - 本次数量全部取自 Freqtrade 官方回测记录 [`evidence/FT-BASELINE-05/out/04_freqtrade_trades.csv`](file:///Users/boos/Desktop/威科夫因子共振趋势/evidence/FT-BASELINE-05/out/04_freqtrade_trades.csv) 的 `amount` 列；
   - 真实数据 0 缺失，0 填零替代。
2. **符号与比例完全吻合**：
   - 统一为净现金流贡献（收取为正、支付为负）后，5 笔收付方向完全相同；
   - 统一后的资金费比例与数量比例完全吻合，5 笔最大比例残差仅为 **$5.55 \times 10^{-16}$**（浮点机器精度极限）。
3. **资金费差额本质定性**：
   - 两引擎的资金费绝对差额（BAT: +0.000249 U, PUMPBTC: +0.014180 U, BANANA: -0.004751 U, CTSI: +0.004044 U, AR: +0.000816 U，合计仅 0.014539 U）**100% 来源于开仓数量计算时的微小整数量化与精度处理差异**；
   - 在持仓期间的全部 168 次结算事件中，每一笔结算的基准费率、Mark 结算价格完全一致；由于名义价值严格等于 $\text{Mark} \times \text{Quantity}$，持仓数量的恒定比例直接决定了资金费发生额的恒定比例。
