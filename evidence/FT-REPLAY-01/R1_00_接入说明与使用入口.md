## 二、四个时刻是怎么分开的（这是本工单最要紧的一件事）

一段交易在时间轴上不是两个点，是四个：

| 顺序 | 时刻 | 含义 | 图上长什么样 |
|---|---|---|---|
| ① | 信号时间 | 候选 K 线**收盘**那一刻（箱体突破被发现） | 方块（inBar） |
| ② | 确认时间 | 确认 K 线**收盘**那一刻（C1/C2 才有） | 圆点（inBar） |
| ③ | 下单/成交时间 | 真实入场成交那一刻 | 向上箭头（belowBar） |
| ④ | 出场时间 | 真实出场成交那一刻 | 向下箭头（aboveBar） |

### 为什么要较真：一个差点犯的错

上游 `enter_tag` 末尾带一串毫秒数字（如 `cand_C1_ev_..._1717146000000`），
看上去像是「信号时间」，直接拿来用最省事。

**逐笔核对后发现它不是信号时间**：

| 模式 | 比对对象 | 结果 |
|---|---|---|
| C1 / C2 | 确认表 `confirm_time_ms` | **1330 / 1330 完全相等** |
| C1 / C2 | 确认表 `orig_signal_time_ms` | 只有 72 / 1330 相等 |
| C0 | 是否整 1 小时对齐 | 2995 / 2995 全部对齐 |
| C0 | 入场时间 − 尾段 | 2902 / 2995 = 15 分钟（其余 30/45/60 分钟） |

结论：
- **C1/C2 的尾段 = 确认 K 线收盘时间**（不是信号时间）；
- **C0 没有独立确认环节**，尾段既是信号 K 线收盘、也是决策时刻，所以 C0 的信号时间取它、
  确认时间留空（界面显示「无此环节」）。

如果当时直接拿尾段当信号时间，图上就会把「确认时刻」画成「信号时刻」——
正是本工单明令禁止的那类错。所以代码里尾段单独存成 `tag_time_ms`，
由调用侧按模式分派，并给每笔写明来源（`signal_time_basis` / `confirm_time_basis`）。

### 一个真实的例子（可直接在系统里核对）

`run_FT_ENTRY_09_C1_Vs04_Z02_1000XECUSDT`，唯一一笔：

```
信号时间  1717142400000  ← 候选 1h K 线收盘（来自确认表 orig_signal_time_ms）
确认时间  1717146000000  ← 确认 K 线收盘（+1 小时）
下单/成交 1717146900000  ← 真实入场（+15 分钟）
出场时间  1717171200000
```

三个时刻依次相隔 1 小时、15 分钟，正是 C1 的「信号 K 线 → 下一根确认 → 再下一根 15m 入场」。

## 五、已知限制（这些地方如实标了「未知」，没有编数）

1. **计划风险（入场时打算亏多少）全部未知。**
   上游只落盘了 `initial_stop_loss_abs`，而它是 freqtrade 的兜底 −99%，不是真实计划风险。
   硬拿它乘仓位算「计划风险」等于编数，所以 4325 笔全为 `null`，界面显示「未知」。

2. **C0 的原始 P0 未知（2995 笔）。**
   P0 来自候选确认表，而 C0 模式没有确认环节、也就没有这张表。
   界面显示「未知」，不拿 `orig_low` 之类推算。

3. **C0 没有确认时刻**，界面显示「无此环节」，不是「未知」——
   两者含义不同，故意用了不同文案。

4. **一个 run 的成交可能分散在几年里**（标记跨度中位 3.2 万根 15m、最长 10.7 万根）。
   不聚焦时 K 线只返回末 2 万根，载荷里带 `candles_truncated=true` + `candles_note` 写明
   从哪根开始；**点选某一笔后**用 `focus_ms` 重新取数，那一笔的四个点必然都在图内。

5. **时区**：页面表格与 K 线一律显示 UTC，鼠标悬停显示原始毫秒时间戳（`title` 属性），
   供逐值核对。

## 八、浏览器实机验收（2026-10-21，截图见 `screens/`）

不是「接口通了就算过」——用真实浏览器在 `http://127.0.0.1:3000/` 上走了一遍，
过程中发现并修掉了 4 个只有真点才会暴露的问题：

| # | 问题 | 现象 | 修法 |
|---|---|---|---|
| 1 | 「候选 ID」列空着 | 研究期回测的候选 ID 存在 `event_id`（`ev_…`），而这一列只认正式回测的 `signal_id`（`cand_…`）⇒ 每行都显示 — | 两个字段都认，都没有才写 — |
| 2 | 「初始止损 / 毛盈亏」用 — 表示缺失 | 与「未知 / 无此环节 / 未记录」三档文案的约定不一致 | 改成「未记录」并在悬停里写明为什么不推算 |
| 3 | 净值/回撤面板报红「取数错误」 | 研究期 run 没有引擎落盘的净值序列，被当成取数故障 | 空态改成「未记录：研究期 run 按上游落盘成交重建，没有引擎落盘的净值序列（不绘制合成曲线）」，不再显示红色错误 |
| 4 | **按批次视图里这批 run 列不出来** | 批次目录只放清单、run 实体在主运行根 ⇒ 后端判定为「清单型批次」⇒ 页面显示「该批次没有 run 目录 / 共 0 条」，数字对但清单空 | 批次目录里给每个 run 建**相对软链**（指向主运行根的实体目录，不复制、不占双份磁盘）；`batch_meta.json` 的 `manifest_batch` 改为 false |

第 4 条修完后，批次视图的数字与清单**互相自洽**（后端自己会核对）：

```
runs_total 1065｜trades_total 4325｜net_pnl_sum −3678.73493358
checks: trades_total_matches_rows = true
        net_pnl_matches_rows     = true
        trades_rows = 4325｜net_pnl_from_rows = −3678.73493358
```

同时补了两处「一眼看出不是本策略成绩」的标识：

- 批次 run 清单的**归属**列：原来一律写「当前策略」⇒ 研究期 run 现在写「研究期重建」；
- 批次 run 清单的**状态**列：研究期 run 与按单 run 列表一样带「研究期」徽标。

以及新增一块只读对照（不改前端结构，只是在「单条记录回放」下面多一个可折叠块）：

**「同一候选在 C0 / C1 / C2 的结果对照」**——标题行先给三个计数
（成交 / 拒单 / 未成交），展开后逐行列出模式、参数组、结果、净盈亏、入场时间、
出场原因或拒单原因。三种结果用不同徽标分开，**不会把「没做」和「做了亏」混成一个数**。

例：`ev_FT_ENTRY_02_binance_ALICEUSDT_1651435200000` 在 9 个参数组 × 3 个模式下
= 成交 7 笔 / 拒单 2 笔（`outside_retest_zone`）/ 未成交 0 笔。
