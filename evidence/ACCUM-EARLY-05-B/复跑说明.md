## 三、注意事项（都是踩过的坑）

1. **脚本不删任何目录**。`03` 每次跑落在 `runs/03_chain/<运行号>/<作业名>`，`05` 落在 `runs/05_isolation/<运行号>/`，运行号取启动时刻；同时写 `LATEST.json` 指针。历史结果一律留着对照。
   - 原因：环境的安全删除守卫按**单轮累计文件数**拦截（`shutil.rmtree` 一次删 60 多个文件会被直接拒），于是「按序跑完六个脚本」会在第 5 个脚本莫名失败。改成不删之后，复跑稳定，且能回看历史。
   - 后果：跑多了 `runs/` 会变大（每个作业几百 KB）。想清理请手工挑着删，别用整目录递归删除。
2. **`06` 的路径全部从证据里取**，不硬编码目录名：作业目录读 `03_全链验证.json` 的 `run_dir`，连接探针日志读 `05_隔离边界.json` 的 `worker_json`。所以 `06` 必须在 `03`、`05` 之后跑，且永远读的是**最新一轮**。
3. **`06` 需要 `README.md` 里的数字表**。若表被改动或删掉，`06` 会以退出码 1 报出「缺哪几项 / 多哪几项」，不会静默通过。
4. **`06` 不读 `out/*.json` 里的汇总值当答案**。它重算的来源是：模块常量、账本表（`paper_position` / `paper_order` / `paper_fill`）、观察库表（`accum05_candidate` / `accum05_exit` / `observe_data_gap`）、子进程连接探针日志。改 `out/` 里的数字不会让它变绿。
5. **`04` 里有一处临时替换**：把 `paper_engine.approved_params` 换成返回 `stoploss_s=0.04` 的版本，用来证明「引擎已确定语义被改时闸门会拦」。替换在 `finally` 里恢复，**不落盘**。`04` 每次会重开自己的观察库（只删 3 个文件，不删目录），避免「本次尝试记录」混进历史行。
6. **`04` 与 `05` 都改父进程的环境变量**（`PAPER_LEDGER_DIR` 等）。它们是独立进程，互不影响；但不要在同一个解释器里 import 它们再跑别的。
7. **哈希只分块算**。`market_v2.sqlite3` 有 12 GiB，用 `read_bytes()` 会被系统直接杀掉（实测 SIGKILL、无报错）。`_common.sha256_file` 已改成 8 MiB 分块。
8. **行情库的 sha 必然变化**（采集器实时在写），所以它只记录、不作为泄漏判据。泄漏判据只用生产四本账本 + 实时信号库的 sha。

## 四、产物落在哪

| 路径 | 内容 |
|---|---|
| `out/0N_*.json` | 每个脚本的判定与明细（`06_数字事实.json` 是复算结果，`06_报告对撞.json` 是比对结果） |
| `out/07_经济口径一致性校验.json` | 五个经济口径用例的逐项结果（临时目录在系统 tmp 下，用完即弃，不落本单目录） |
| `runs/03_chain/<运行号>/<作业名>/paper/paper_4{a,b,c}.sqlite3` | 三本研究账本（可逐笔复核） |
| `runs/03_chain/<运行号>/<作业名>/observe.sqlite3` | 观察库（事件、候选、迁移、缺口、委托尝试、退出明细） |
| `runs/03_chain/<运行号>/<作业名>/worker_open.json`、`worker_resume.json` | 子进程原始输出 |
| `runs/03_chain/LATEST.json`、`runs/05_isolation/LATEST.json` | 指向最新一轮运行目录 |
| `runs/04_gate/cfg/*.json` | 11 条闸门用例的配置变体（含故意写错的） |
| `runs/05_isolation/<运行号>/worker_iso.json` | 连接探针全量日志 |
