### 2.2 A 类：有数据却打不开（375 个，全量复测）

375/375 全部返回 HTTP 400，响应体只有一句：

```
{"错误": "list indices must be integers or slices, not str"}
```

原因：这些 `chart.json` 的 `candles` 是数组元组 `[t,o,h,l,c,v]`，读侧按对象 `c["t"]` 取值。
前端 `utils/candles.ts` 两种形态都能吃（有注释说明踩过这个坑），**后端没有**。
所以这 375 个 run 是「应能重开却报错」，属于必须修的一类。

### 2.3 B 类：盘上没留存，靠临时读行情库（1,268 个）

实测 `run_FT_LOW4H_DYN01_Wyckoff_C1_S05_DYN999_Vs08_Z06`：

- `chart.json` 有 **390,847 字节**，但 `candles` 是 `[]` —— 体积全在 `trades`/`equity_curve`/`signals` 上
- 接口照样返回 **15,698 根 1h**，并在 `candles_source` 里如实写：
  「读时从市场库读取 binance/um/AVAXUSDT/1h 连续行情…**未写回 run 目录**」
- `candles_window_matches_run_window = false`（显示窗口 2021-12-11 → 2023-09-27，run 窗口 2021-12-01 → 2024-12-31）
- `chart_blocked_reason` 原文：「本 run 为 74 标的组合回测…以单标的 symbol+window 取 K 线，无法承载组合」
  ⇒ 但接口最终把这条原因置成 `null`、`chart_partial=false`，因为「有 K 线了」——**有 K 线不等于有对的 K 线**

这意味着两件事：

1. 「留住」对 1,268 个 run **不成立**：现在能看，是因为行情库还在；行情库一旦清理或补数，
   这批图就变了，而且**没有任何盘上快照可以对照**，无法证明「重开看到的就是当时那批」。
2. 组合 run 会被静默降级成单标的（AVAXUSDT）图，且 `symbols` 里 44 个币只有下拉可切，
   `candles_source` 这句话**前端根本不渲染**（`LabChartPanel` 只认 `derived_from`，
   而 `derived_from` 在 B 类是 `None`）⇒ 用户看到一张 AVAX 图，不知道它是「代表图」。

**另需更正一处我自己写过的数**：`candles_source` 里有没有「读时」二字，**不能用来统计重建率**。
抽样 40 个 E 类 run（盘上 K 线非空），**35 个数据明明来自盘上却被贴「读时取」**——
因为该字段是默认填充文案，不是事实判断。详见 `05_历史产物分层.md` §6。

## 第 3 项：默认 1h、多图联动、订单与图表双向定位

**状态：完成（图表端本身），但有两条边界不成立。**

### 3.1 默认 1h：确认成立，且不是缺陷

按用户给的口径重新判：只有「请求周期、返回实际周期、界面标签」三者不一致才算缺陷。
实测三者是自洽的：

| 环节 | 实测 |
|---|---|
| 前端默认 | `BacktestWorkbench.tsx` → `useState<string>('1h')` |
| 后端返回 | 项目引擎 run 忽略 `?timeframe=1h`，返回 15m（`step_s=900`），`display_timeframe=15m` |
| 前端处理 | `actualTf` 取 `candles_timeframe → display_timeframe → detectCandleTimeframe → exec_timeframe`，得 15m；再按 UTC 边界聚合到 1h |
| 界面标签 | 卡片副标题显示「… 根（**1h 聚合**）」，非聚合时显示「（15m 原始）」 |

⇒ 用户看到的是 1h 图，标签写的是「1h 聚合」，**没有欺骗**。上一单把它算成缺陷是错的（更正 C-2）。

留一句给运维：后端 `?timeframe=` 对这类 run **不生效**，谁直接调接口要 1h 会拿到 15m。
这是实现选择，不是用户可见缺陷，但接口语义应当写清或干脆不支持该参数。

### 3.2 多图联动与双向定位：有自测证据，未经独立验收

`evidence/BT-CHART-CLOSURE-10/` 自报 16/16 PASS，关键几条：

- 主图缩放/拖拽 → 资金图跟随、资金图反向拖拽/缩放 → 主图跟随，误差 0s
- 负向检验：人为把界面偏移 15 天，断言判 FAIL（防放水有效）
- 标记点击反查订单：编号/币种/时间/价格四要素对应
- 深链重开：`?run=&vf=&vt=` 恢复手动视窗；`?run=&order=` 订单居中聚焦，两种徽标不混用
- 周期切换：15m/30m/1h/4h 分别返回 900/1800/3600/14400 秒

**但这仍是交付方自测，不是独立验收。** 且下面两条边界要单独记：

### 4.2 模拟盘逐笔的三处硬伤（都有原始行）

`paper_fill` 6 行里，3 笔平仓的 `order_id` **全是 NULL**：

```
fill_id=2  order_id=None  action=close  fill_ts=1792668586661
fill_id=4  order_id=None  action=close  fill_ts=1792668606013
fill_id=6  order_id=None  action=close  fill_ts=1792668687677
```

同时开仓的 `fill_ts` 是 K 线整点（`1792666860000`），平仓的是**挂钟毫秒**
（`1792668586661`）⇒ 同一张表里两种时间口径。后果：

- 「订单 → 成交」这条链在平仓侧断了（没有 `order_id` 可关联）
- 「成交时间」不可比：开仓是 bar 时间，平仓是执行时刻
- 导出 CSV 时这一列要么空、要么混两种语义

这条归入 F-02。

### 4.3 导出

`BT-CHART-CLOSURE-10` 的 `8.2` 用例真实点击了「导出委托订单为 CSV」「导出本 run 逐笔交易记录为 CSV」，
拦截浏览器下载、读回文件内容、核对文件名里的 `run_id` 与 CSV 表头及数据行 ⇒ 自报 PASS。
**未做**的是：把导出内容与原始账本逐字段对账（行数、ID 关联、费用、资金费、期末持仓）。
所以本项只能算「导出按钮真的能下载」，不能算「导出与账本一致」。

### 4.4 这一项的缺口

1. Freqtrade 链 `/fills` 返回 `total=0` 且 `missing_reason=null` ⇒ 会被误读成「这个 run 没成交」（F-04）
2. Freqtrade 链 `orders.jsonl` 只有开/平两行，无 `filled_qty`/`remaining_qty`，`trades.jsonl` 无 `stop_trace`
   ⇒ 结构上不支持「逐次成交」与「止损轨迹」
3. 模拟盘平仓缺 `order_id`、时间口径混用（F-02）
4. 部分成交 / 撤销**没有真实样本**（合约最小变动单位下几乎不可能），只能用明确标注的隔离样例，
   不能写「已支持」
