## 2. 逐条：原文 → 更正 → 依据

### C-1｜分母 3,989 → 4,026（不是 5,091）

**原文**（`PROJECT-REVIEW-07_总览报告.md` §6 表四）：
> 3,989 个 run 目录，九件套齐 1,717；375 个打开直接 400（D-04）；2,677 个 `inputs.json` 无参数身份 ⇒ 不可复算（D-05）

**更正**：
- **物理 run 目录 = 4,026 个**（`08_软链接核对.py`）；
- 按目录名枚举会得到 5,091，其中 **1,065 个是软链接**：全部在 `event_trend_v0_1/runs_ft_replay_01/`，
  全部指向 `runs/` 下同名目录，断链 0、指向 `runs/` 之外 0、唯一目标 1,065；
- 上一单的 3,989 与物理数**接近**（差 37 个），差的原因是它只数「同时有 `chart.json` 或 `inputs.json`，
  且有 `candidates.jsonl` 或 `run.json`」的子集。

**依据**：`out/08_软链接核对.json`、`out/01_产物分层.json`、`out/01b_未覆盖run目录.json`。

**连带更正**：
- 「九件套齐 1,717」不变，比例从 43%（1,717/3,989）改写成 **42.6%（1,717/4,026）**；
- 「2,677 个无参数」不变，但要说清：**4,982 个有 inputs 的 run 里 2,677 个无参数**；另有 109 个连 inputs 都没有。

> **自查留档**：本单第一版写的是「5,091 个、上一单漏了 1,102 个」，**这是错的**。
> 错因是 `01_产物分层.py` 用 `os.path.isdir()` 枚举，它会跟随软链接 ⇒ 1,065 个链接被当成独立 run，
> 同一批 run 被数了两次（一次在 `runs/` 判为 B 类，一次在 `runs_ft_replay_01/` 判为缺来源）。
> 由此还连带错了两个数：「D 缺来源 1,102」应为 **37**；「727 条读时重建」不可统计（见 C-7）。

### C-6｜空图不是"全都没原因"，400/404 才是

**原文**（`缺陷表.md` D-09）：
> 10 个返回 200 但 K 线 0 根，且 `chart_partial` / `blocked` / `candles_source` / `derived_from` 全为 `null` 或空串

**更正**：

**依据**：`out/02_重开与提示.json`（提示样本）、`out/02c_重开实测.json`。

### C-7｜`candles_source` 是默认填充文案，不能当判据

**本单第一版原文**（`05_历史产物分层.md` 第一版 §5.3）：

**更正**：这个统计作废。`backtest_api._finalize_chart_meta` 里：

```python
if not chart.get("candles_source"):
    chart["candles_source"] = f"读时按本 run 自己的标的与窗口取真实 K 线（…），未写回 run 目录"
```

这是**默认填充**，不是事实判断：只要原 chart 没写这个字段，哪怕 K 线就是盘上那份，也会被贴「读时取」。

抽样 40 个 E 类 run（盘上 `candles` 是对象且非空），比对盘上根数与首末时间戳 vs 接口返回：
**35 个数据来自盘上但标签说「读时取」**、5 个确为重建（盘上窗口与本 run 窗口不符被拒收那一类）。
**87.5% 误标。**

**依据**：`out/09_candles_source核对.json`、`probes/09_candles_source核对.py`。

**正确的判据**：看盘上 `chart.json` 的 `candles` 是否为空。按这个口径：
有 K 线 **1,692**（E 1,317 + A 375，占 42.0%）、没有 **2,188**（B 1,268 + 缺 chart 920，占 54.3%）、其余 146。
