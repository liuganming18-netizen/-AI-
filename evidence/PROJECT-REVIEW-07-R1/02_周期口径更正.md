# 02｜周期口径更正（PROJECT-REVIEW-07-R1）

> 本单只更正判据与结论，不改图表代码。

## 0. 一句话

上一单把「默认展示 1h、执行 15m」当成缺陷（`缺陷表.md` D-07「叠加事实」、`四项重点验收表.md` 表三「组合 run 的默认展示周期＝不通过（显示 1h，执行 15m）」）。**这条不成立**：1h 默认展示是用户明确要求，15m 执行是策略实际粒度；返回体里 `exec_timeframe=15m`、`display_timeframe=1h`、实测间隔 3600 秒，三者自洽，不是"同一条响应里两个字段互相矛盾"。

## 1. 判据（按工单口径）

只有下面三件事不一致，才算这一类缺陷：

1. **请求周期**（`?timeframe=`）；
2. **返回的实际 K 线间隔**（相邻 `t` 的中位差）；
3. **界面标签**（前端按哪个周期标注）。

「默认展示 1h + 执行 15m」允许；「显示 4h、执行 15m」也允许。**不允许**的是：请求 4h、返回 15m 数据、界面却标成 4h。

## 2. 实测结果

### 2.1 行情接口：8/8 一致

| 交易所 | 5m | 15m | 30m | 1h | 4h | 8h | 12h | 1d |
|---|---|---|---|---|---|---|---|---|
| binance BTCUSDT | 300s ✔ | 900s ✔ | 1800s ✔ | 3600s ✔ | 14400s ✔ | 28800s ✔ | 43200s ✔ | 86400s ✔ |
| okx BTC-USDT-SWAP | 空 | 空 | 空 | 空 | 空 | 空 | 空 | 空 |

okx 返回 0 根并带 `missing_reason`（不在补充集合）——这是**正确行为**，不是缺陷。响应里同时有 `timeframe` 与 `is_native` 字段，前端本可以校验。

### 2.2 回测图表接口：分引擎

| run | 引擎 | 默认 | 15m | 30m | 1h | 4h |
|---|---|---|---|---|---|---|
| `run_FT_LOW4H_DYN01_…Vs08_Z02` | freqtrade | 3600s / display 1h | 900s ✔ | 1800s ✔ | 3600s ✔ | 14400s ✔ |
| `run_FT_LOW4H_DYN01_…DYN_Vs04_Z04` | freqtrade | 3600s / display 1h | 900s ✔ | 1800s ✔ | 3600s ✔ | 14400s ✔ |
| `run_WX_EVENT_TREND_V0_1_TAOUSDT_…` | 项目引擎 | 900s / display 15m | 900s ✔ | 900s（请求被忽略） | 900s（请求被忽略） | 900s（请求被忽略） |
| `run_FT_STOP20_…Vs04_Z02` | 项目引擎 | 900s / display 15m | 900s ✔ | 同上 | 同上 | 同上 |
| `run_WX_EVENT_TREND_V0_1_COOKIEUSDT_…` | 项目引擎 | 900s / display 15m | 900s ✔ | 同上 | 同上 | 同上 |
| `run_FT_ENTRY_09_…CELOUSDT` | 项目引擎（归档副本） | 900s / display 15m | 900s ✔ | 同上 | 同上 | 同上 |

两种行为都**不会让标签撒谎**：

- freqtrade：服务端按请求周期重采样，`display_timeframe` 等于请求；
- 项目引擎：服务端忽略 `?timeframe`，返回 15m，但 `display_timeframe` **如实写 15m**；前端 `LabChartPanel` 用 `actualTf`（`candles_timeframe` → `display_timeframe` → 实测间隔）判断真实周期，再在客户端聚合到用户选的 1h/4h。

### 2.3 前端两处，行为不同

| 位置 | 取周期的方式 | 判定 |
|---|---|---|
| 回测工作台 `LabChartPanel.actualTf` | 先看后端声明，再用实测间隔兜底；`actualTf ≠ tf` 时客户端聚合 | **通过**（不会把 15m 标成 4h） |
| 行情页 `adapters.ts::adaptCandles` | 直接用**请求的** `tf` 调 `formatCandleTime`，从不读响应的 `timeframe` | **不通过**（后端一旦回退，标签会跟着错，且无提示） |

## 3. 上一单错在哪

- `out/05_回测重开抽样.json` 里那两条 `display_tf=1h` 的记录，`exec_tf` 明明写的是 **`15m`**；报告却写成「`exec_timeframe` 仍写 `15m`、`display_timeframe` 写 `1h` ⇒ 同一条响应里两个周期字段互相矛盾」。**把两个不同语义的字段当成互相矛盾**。
- 表三据此判「组合 run 的默认展示周期＝不通过」，把用户要求的默认 1h 当成缺陷。
- D-07 的「叠加事实」引用 `out/05`，但 `out/05` 的数据不支持这条结论。

## 4. 真正残留的两个小问题（P2，不影响当前判断）

1. **项目引擎静默忽略 `?timeframe`**：请求 1h 却返回 15m，虽然 `display_timeframe` 诚实、前端会聚合，但接口层"请求参数无效且不说明"。建议：要么服务端重采样，要么在响应里写一句「本 run 仅提供 15m 原生 K 线，已按 1h 聚合由前端完成」。
2. **行情页不校验响应周期**：响应里有 `timeframe`，前端没用。建议：`adaptCandles` 比对 `env.timeframe` 与请求 `tf`，不一致时挂告警条（不要静默改写）。
