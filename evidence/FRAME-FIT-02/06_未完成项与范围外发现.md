## 三、已知薄弱点（如实列出）

### 1. `record_execution` 不校验 `run_id` 是否真存在于运行库

它和 `attach_run()` 同级：能直接调登记 API 的代码，本来就能直接写事件。
防伪造靠两点：① 两道闸门**全程只读**（用例 `test_launch_pass_keeps_zero_runs` 锁住）；
② 记录只由执行器在真实执行后产生。

**没有做**：拿 `backtest_store.read_run(run_id)` 反向核对。原因：会让登记模块反向依赖
运行库，且在同一进程里仍可被绕过 —— 收益低、耦合高。若后续要做进程级隔离，这条应一并处理。

### 2. 进程被强杀时不会留下试验结论

`_run` 执行中途进程被 `kill -9`，run 状态会停在 `running`，登记里既没有 run 也没有 trial
（绑定发生在执行之后）。此时该实验的交付资格仍是 False（原因「尚无已登记运行」），
需要人工重新跑或人工补记 —— **不会**被误判成「已完成」。

### 3. 并发未做压力测试

登记写入有进程内 `RLock` + append-only 哈希链，两个 run 同时写会串行化；
但本单没有做多进程/多线程并发压测。

### 4. `data_sha256` 目前记 `None`

`record_execution` 从 run 文档取 `data_sha256`，而当前 run 文档里没有这个字段
（数据指纹在 `_run` 的返回值里，落盘的是 `inputs.json`）。
按项目纪律「未知即 `None`，不填占位符」，记 `None`。要填真值需要执行器把指纹写进 run 文档，
属另一处改动，本单未做。

### 5. `backtest_api` 响应里 `formal_eligible` 仍是硬编码 `False`

启动那一刻它本来就该是 False（还没跑），所以没有错；但**跑完之后**控制器不会回头更新这个字段。
要查交付资格，应读 `list_experiments()` 的 `formal_eligible`。
本单未改控制器（保持零改动）。
