## 六条必须记住的硬结论

1. **`scope=current` 的 `origin` 白名单漏 `recovered` 是一整条断链。** 进程短暂停机后重启，`bootstrap` 会把仍在成交时效内的真实候选以 `origin='recovered'` 落库并交给路由（实测 `persisted=1 / registered=1`），旧白名单只认 `live` ⇒ 库里有行、账本里有挂单、**信号区永远看不到**。修的时候后端、`adapters.ts`、`types/crypto.ts`、`isCurrentSignal` 四处必须一起改，少一处就还是看不见。
2. **`bootstrap` 只按 4h 收盘驱动 `process_market`，最后一根 4h 之后已收盘的 1h 永远喂不进去。** 后果不是「少一次迁移」而是**永久漏候选**：那根 1h 确认的突破既不被 bootstrap 产生（进不了 recovered），又被 `step_once` 的 `available_at >= started_at` 过滤。实测同一份数据 `upto=15:30` 得 `recovered=0`、`upto=16:00` 得 `recovered=1`；补齐后 `upto=15:30` 即得 1。**任何「重建 vs 连续」的比较都必须补 `step(upto)`，这是第二次踩到同一个坑**（06 收口已记过一次）。
3. **`bootstrap` 的热库分支曾经必崩。** `hist` 为空时走 `else` 分支，但「42 根上下文」用的是只在 `if hist` 里赋值的 `b4_all` ⇒ `UnboundLocalError`，整个 `bootstrap` 中断、一个候选也产生不了。生产走 `hist` 分支所以没暴露，回归测试（`test_paper_live_01`）当场打出来。修复后生产状态分布逐项未变（`IDLE 191 / BOX 300 / SWEEP 21 / RETEST 14`），证明没有改变生产结果。
4. **「没有数据」不能显示成一个具体时刻。** `as_of` 空表曾是 `1970-01-01T00:00:00Z`；改成 `null` 后又被 `adapter.py` 合并层回落成「现在」（`envelope()` 里那句 `iso(STORE.clock())`）⇒「没有数据」与「数据刚好到现在」不可区分。现在当前区**无条件采信**实时层的 `as_of`（含 `None`），审计通道保持旧行为。
5. **「加载中」不是「故障」。** 逐币诊断首次要排队十余秒（排在账本与实盘只读之后），旧文案在这段时间写「守护状态接口未返回」——接口明明返回了。加 `diagnosticsPending` 之后：加载中显示「正在读取」、`pending=false` 仍为 null 才显示「未取到」、接口异常走独立红框。**三者混在一起等于把信息删掉。**
6. **生产零信号是规则结果，不是故障，也不是数据缺口。** 最近候选 `2026-10-11T20:00Z`（METISUSDT），此后 **13.62 天零候选**；同期行情库 `binance` 4h 已收盘 bar **42,768 根 / 528 个标的 / 每个 81 根**、1h 172,128 根，**没有缺口**。51 个历史候选全部早于启用时点 `2026-10-14T01:00Z`。**不改阈值、不平移启用时点**——那等于伪造。
