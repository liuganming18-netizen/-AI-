## 五条必须记住的硬结论

1. **「接口异常显示成空列表」的根因在后端契约，不在前端渲染。** 前端只要按 `quality.status` 判就必然踩坑 —— 因为后端在两条失败路径上把 `status` 留成了 `"ok"`。**只改前端是治不好的**：前端看不到任何可判据。以后凡是「某类异常被当成正常空」，第一件事是查后端有没有把 `status` 写对，而不是加 `if (error)`。

2. **`quality.note` 恒有值，绝不能当故障判据。** 生产正常态实测 `status=ok` + `missing_reason=null` + `note` 172 字符。若把「有说明字段」一律当故障，正常空列表会被误报成接口坏了 —— 这是本单要求里明确点名要避免的。判据只能是 `missing_reason` 非空，或 `status` 落在故障枚举。

3. **`bootstrap` 现在有「尾部补齐」，会改变「谁产生候选」的归属。** 上一单 `03_iso_e2e`（修复前）用 `upto=候选收盘-1ms` 时 step 能产生 1 个新信号；本单同一截止时刻下 bootstrap 会先把那根 1h 吃掉、候选进 `recovered`，step 得 `new_signals=0`。**这不是回归，是修复的正确后果。** 要演示「新产生」路径，bootstrap 必须停在候选前一根 1h 之前（本单用 `候选-1h-1ms`），否则演示不到那个分支。**任何「重建 vs 连续」的对比都要先确认 bootstrap 的截止时刻与尾部补齐是否已生效。**

4. **三层的 `confirmed_at` 表示不同，比的是时刻不是字面。** 数据库存毫秒 `1790953200000`，接口/页面给 ISO `2026-10-02T15:00:00Z`。验收脚本直接 `Number()` 比会得到 `NaN`，报出三处**假失败**。**同一时刻的两种表示不是数据不一致** —— 必须先归一化再比，否则会把自己骗进「数据错位」的结论里。

5. **行情库 sha 变化不能当「探针泄漏」的判据。** `market_v2.sqlite3` 由常驻采集器每秒写入当前时段 K 线，sha 一定会变（本单实测前后都变，但 `MAX(open_time)` 同为 `2026-10-25T10:00Z`）。正确判据是 `live_signals.sqlite3` 与四本账本的 sha —— 这两个实测**零变化**。拿行情库当判据会得出「隔离失败」的错误结论，进而去改本来没问题的隔离代码。
