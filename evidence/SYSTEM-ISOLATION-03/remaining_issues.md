# 工单 A｜SYSTEM-ISOLATION-03 边界约束与剩余问题说明

## 1. 边界与设计约束

### 1.1 隔离模式强校验与日常目录硬隔离
- 隔离模式（通过 `--isolated`、`is_isolated=True` 或环境变量 `ISOLATED_MODE=1` 显式声明）：
  - 必须完整提供全部 6 项路径：`market_db`、`live_db`、`paper_ledger_dir`、`paper_lock_dir`、`pid_dir`、`log_dir`；
  - 缺失任一项立即拒绝启动（抛出 `RuntimeError`），严禁静默 fallback 到日常生产目录；
  - 若传入的 `paper_ledger_dir` 或 `market_db` 解析后指向日常生产数据路径（`数据/paper`、`数据/市场数据/db/market_v2.sqlite3`），系统立即抛出硬拦截异常，杜绝污染生产库。
- 非隔离模式（默认日常启动）：
  - 仍允许读取默认日常目录，但若显式指定了路径或环境变量，优先采纳并贯穿子进程，不再被内部默认逻辑覆盖。

### 1.2 进程精准停止与外部进程防护
- 停止操作仅针对当前实例启动并登记在 `service_meta_{port}.json` 或实例专属 PID 文件中的目标进程；
- 停止前严格比对命令行（API 匹配 `adapter.py`，Worker 匹配 `backtest_worker.py`，Runtime 匹配 `unified_runtime.py` 及 `--arm` 参数）与工作目录；
- 若端口存在外部未知进程或伪造 PID，系统明确报错拒绝操作（`RuntimeError: 拒绝停止非本实例 API 进程...`），绝对禁止按端口批量杀（无 `pkill -f`），绝对禁止仅凭 PID 文件盲杀；
- 重复调用 `stop()` 保证完全幂等，不会重复报错或误杀其他服务。

### 1.3 状态与总体健康度精确定义
- `overall_health` 现严格区分四种状态：
  - `healthy`：管理的必需服务均存活、运行正常且 HTTP/心跳探针健康；
  - `stopped`：所有服务均已安全停止或禁用（停止后绝不再误报 healthy）；
  - `degraded`：服务处于启动中、未完全就绪或未经验证状态；
  - `unhealthy`：服务出现端口冲突、异常崩溃退出或写入失败。

### 1.4 纸面账户缺库返回契约
- 当缺少实时信号库（`LIVE_DB` 文件不存在或不可读）时，`/api/v1/paper/accounts`：
  - 严格复用既有契约：`quality.status = "unavailable"`，`missing_reason = "实时信号库缺失：..."`；
  - 返回条目 `items = []`，`total = 0`，绝对不伪造零余额账户（不构造虚假 0 余额 items）；
  - 绝对不隐式调用 schema 初始化或自动在日常生产目录新建空数据库文件。
