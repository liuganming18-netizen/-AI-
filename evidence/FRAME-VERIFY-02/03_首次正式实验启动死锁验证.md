## 三、深层原因剖析：混淆“允许启动”与“结果合格”

1. **逻辑死锁循环（Chicken-and-Egg Deadlock）**：
   - 用户要执行一个正式实验，必须先通过 `backtest_api.create_run` 创建 Run；
   - `create_run` 调用 `guard_create` 检查是否允许创建；
   - `guard_create` 在处理 `formal` 模式时，直接调用了 `reg.formal_eligible(eid)`（行 1119）；
   - `formal_eligible`（行 907-908）硬编码了规则：
     ```python
     if not exp["runs"]:
         reasons.append("尚无已登记运行（试验次数为 0，不能宣称有结果）")
     ```
   - 结果：**因为这是一个新实验，尚未有任何运行（`runs == []`），`formal_eligible` 判定不合格（`ok=False`），导致 `guard_create` 直接拒绝创建**！
2. **死锁后果**：
   在正式模式下，必须已有运行记录才能创建运行；但要产生运行记录，又必须先创建运行。用户被逼入死胡同：**除非手工向数据库注入伪造的虚假 run 记录，否则第一个合法的正式实验物理上绝对无法启动！**
3. **实现方测试盲区**：
   查验 `框架/backend/tests/test_frame_fit_01.py::T07_RealEntrypoint`，实现方只写了未绑定实验、未登记、未冻结、已放弃等 5 个**拒绝路径**测试，**完全遗漏了“合法首次正式实验受理”的正常路径测试**。

## 四、责任归属与最小整改要求

- **责任归属**：**`FRAME-FIT-01`**
- **失败判定**：**`FAIL`（死锁阻断合法业务流）**
- **最小整改要求**：
  严格解耦**“允许开始实验（Run Launch Permission）”**与**“实验结果具备正式交付资格（Formal Result Eligibility）”**：
  1. 在 `guard_create` 中，正式模式只校验：
     - `exp` 存在且为 `formal` 模式；
     - 配置已冻结（`exp["frozen_at"] is not None`）；
     - 当前代码/参数指纹与冻结指纹一致；
     - 分组策略已配置自洽（`policy.configured is True`）；
     - 留出未被污染；
     **绝不得在创建运行时刻要求 `runs` 或 `trials` 非空！**
  2. 将“尚无已登记运行（试验次数为 0）”的检查限制在最终评估、解封留出（`unseal_holdout`）或交付审计环节。
