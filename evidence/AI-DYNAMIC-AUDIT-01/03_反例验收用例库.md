# 03 反例验收用例库 (Adversarial Acceptance Test Suite)

> **工单**：工单三｜反重力独立核查与三组对照验收设计  
> **设计目标**：针对 AI 动态系统最容易发生的信息泄露、过拟合、数据污染、时序倒置、外部依赖崩溃等极端场景，制定 10 大反例验收用例。  
> **门禁原则**：任何策略或调度器在正式获批接入前，必须在隔离测试环境中 **10/10 100% 通过** 本反例用例库，出现任何一次静默吞错、越权放行或数据穿透即判定**验收不合格**。

---

## 反例用例总览表 (10 项)

| 编号 | 用例名称 | 核心防范目标 | 注入阶段与位置 | 判定级别 |
|---|---|---|---|---|
| **TC-01** | **未来数据注入 (Lookahead Data)** | 防范模型或策略偷看未闭合 K 线或未来价格 | 行情供给层 / 状态机输入 | **P0 致命** |
| **TC-02** | **晚到数据处理 (Late-Arriving Data)** | 防范由于行情入库延迟导致的时钟穿越决策 | 市场数据监听器 (Watcher) | **P0 致命** |
| **TC-03** | **修订数据处理 (Data Restatement)** | 防范已结算 K 线或资金费被上游改写破坏账本 | 行情库版本控制与资金费表 | **P1 严重** |
| **TC-04** | **重复决定拦截 (Duplicate Decisions)** | 防范模型或并发进程在同一周期发起重复调仓 | 策略路由与挂单注册中心 | **P1 严重** |
| **TC-05** | **过期决定丢弃 (Stale Decision Expiry)** | 防范网络延迟或模型长耗时导致的失效指令入场 | 订单撮合前置时效闸门 | **P1 严重** |
| **TC-06** | **缺失指标容错 (Missing Indicators)** | 防范合约规格、ATR 或资金费率缺失时的违规静默兜底 | 特征工程与风控预检层 | **P0 致命** |
| **TC-07** | **模型超时与崩溃 (Model Timeout/Crash)** | 防范 AI 接口 500、断网或格式异常导致交易瘫痪 | AI 决策代理客户端 (Client) | **P1 严重** |
| **TC-08** | **账户状态异动 (Unsynced Account State)** | 防范持仓强平或扣款导致真实净值与模型预期分叉 | 动态仓位计算与名义敞口校验 | **P0 致命** |
| **TC-09** | **越权调整拦截 (Unauthorized Actions)** | 防范模型尝试修改未授权参数或越界调仓 | 动态决策执行沙箱 (Sandbox) | **P0 致命** |
| **TC-10** | **重启与断点恢复 (Crash Continuity)** | 防范系统挂起或重启时动态上下文丢失与重复下单 | 统一运行时 Bootstrap 预热 | **P0 致命** |

## 逐项用例规约与断言设计

### TC-01 未来数据注入 (Lookahead Data Injection)

- **测试意图**：确保无论是特征提取器、规则引擎还是 AI Prompt 构建器，其输入数据中绝不包含任何 `timestamp > decision_time` 的未来行情。
- **前置与注入条件**：
  - 构造包含未来时刻的合成 K 线序列，例如当前决策时钟为 `2026-10-25 12:00:00`，但在输入队列中注入 `12:15:00` 甚至 `13:00:00` 的 K 线数据，或在 1h K 线尚未闭合（当前仅 12:35）时强行将该 1h 标记为 `is_closed=1`。
- **系统预期反应**：
  - 因果守卫（Causality Guard）主动触发拦截；
  - 拒绝将包含未来时间戳的数据传递给策略上下文；
  - 记录致命因果违规日志 `FATAL: lookahead_data_detected`。
- **通过断言**：
  ```python
  assert all(candle["close_time"] <= decision_time_ms for candle in context["candles"])
  assert candidate.available_at_ms <= decision_time_ms
  assert "lookahead_detected" not in audit_logs
  ```
- **放水特征**：模型生成了“预知行情下跌而精准下调仓位”的神奇动作，而特征向量中实际包含了未来最高/最低价。

### TC-02 晚到数据处理 (Late-Arriving Data)

- **测试意图**：在真实网络环境中，交易所行情往往因拥堵延迟数秒或数分钟到达。验证系统不会将实际物理到达时刻晚于决策时刻的数据当作历史事实。
- **前置与注入条件**：
  - 模拟网络严重卡顿，一根本应在 `12:00:00` 闭合的 1h K 线，由于延迟在 `12:08:30` 才被拉取入库落盘（`available_at = 12:08:30`）。
  - 触发一个在 `12:01:00` 发起的历史时钟决策回放任务。
- **系统预期反应**：
  - 系统严守两套时间戳原则（事件发生时间 `event_time` vs 系统可知时间 `available_at`）；
  - 在 `12:01:00` 时刻，该 K 线因 `available_at > 12:01:00` 被认定为“当时尚不可知”，严格拒绝被该决策消费；
  - 返回状态 `data_not_available_at_decision_anchor`。
- **通过断言**：
  ```python
  assert bar["available_at"] <= decision_anchor_ms
  assert execution_result["status"] == "skipped_due_to_unavailability"
  ```

### TC-03 修订数据处理 (Data Revision / Restatement)

- **测试意图**：交易所偶尔会由于清算失误或网络重传发布数据修正（例如补录历史资金费或修正异常成交价）。验证底层系统具备不可篡改性与对账留痕。
- **前置与注入条件**：
  - 对一笔已经平仓结算并记录在 `paper_realized` 的历史交易，向底层模拟插入一条新的修改后费率事件，尝试覆盖已计提的资金费金额。
- **系统预期反应**：
  - 已归档的历史账本行严格禁止被 UPDATE 改写；
  - 资金费结算采用集合差集与唯一索引（`INSERT OR IGNORE`），拒绝静默覆写；
  - 若确需修正，必须向 `paper_correction` 插入独立的人工或系统调整审计记录，维持账本复式平衡。
- **通过断言**：
  ```python
  assert original_realized_row["net_pnl"] == unmodified_pnl
  assert correction_table.count() >= 1
  assert audit_reconciliation_pass == True
  ```

### TC-04 重复决定拦截 (Duplicate Decision Flooding)

- **测试意图**：防范由于网络重试、多线程竞争或 AI 决策代理误触发，在同一 K 线周期对同一持仓或候选连续发出多次调整指令。
- **前置与注入条件**：
  - 模拟 AI 客户端在毫秒级别内并发发送 3 个针对同一 `position_id` 的调仓请求：
    - Request 1: `trail_d = 0.025`
    - Request 2: `trail_d = 0.025` (完全相同)
    - Request 3: `trail_d = 0.040` (冲突参数)
- **系统预期反应**：
  - Request 1 正常处理并落库；
  - Request 2 命中幂等键（Idempotency Key / Ref Bar），返回已缓存结果，不重复写库；
  - Request 3 触发频控熔断或单周期冲突拒绝：`rejected_duplicate_decision_in_same_cycle`。
- **通过断言**：
  ```python
  assert position["trail_d"] == 0.025
  assert order_history_table.count(position_id) == 1
  assert len(rejected_responses) == 2
  ```

### TC-05 过期决定丢弃 (Stale Decision Expiry)

- **测试意图**：AI 模型（尤其大语言模型）推理可能出现严重卡顿（如生成耗时达 10 分钟）。确保当模型返回指令时，若市场时效窗口已过，系统坚决拒绝执行。
- **前置与注入条件**：
  - 突破候选产生于 `10:00:00`，成交有效窗口截止于 `10:15:00`（`MAX_FILL_LAG_MS = 15分钟`）。
  - AI 决策代理由于排队与重试，在 `10:16:30` 才返回了 `ACCEPT` 入场指令。
- **系统预期反应**：
  - 路由与撮合引擎执行严格的时效校验：`current_time - decision_anchor > MAX_FILL_LAG_MS`；
  - 坚决拒绝生成订单，判定为过期抛弃：`rejected_stale_decision_exceeded_lag`；
  - 严禁产生“穿越时空的追单成交”。
- **通过断言**：
  ```python
  assert order_created == False
  assert candidate_status == "missed_fill_moment_no_backfill"
  ```

### TC-06 缺失指标容错 (Missing Indicators & Spec)

- **测试意图**：严格防范前文审计中查出的“合约规则缺失静默兜底为 0.01”以及“缺失 ATR/资金费率静默按 0 计算”等放水行为。
- **前置与注入条件**：
  - 注入一个合约元数据中缺失 `price_step` 的未知币种；
  - 或者构造一笔缺失资金费率或标记价格的 8h 结算事件。
- **系统预期反应**：
  - 坚决拒绝静默兜底（Zero-Fallback Principle）；
  - 针对合约规格缺失：抛出 `missing_contract_spec` 并阻断开仓/平仓计算；
  - 针对资金费率缺失：在 `paper_funding_gap` 写入不可篡改缺口标记，严禁补 0 冒充结算完成。
- **通过断言**：
  ```python
  assert "or {'price_step': 0.01}" not executed
  assert gap_table.count() >= 1
  assert execution_error == "missing_contract_spec"
  ```

### TC-07 模型超时与崩溃 (Model Timeout & Failure Resilience)

- **测试意图**：验证外部 AI API 彻底断网、返回 HTTP 500、超时或吐出乱码时，系统核心撮合主进程不会崩溃，且能平滑降级到基准规则。
- **前置与注入条件**：
  - Mock AI 代理接口分别返回：
    - Case A: 挂起 60 秒不返回（超时模拟）；
    - Case B: 返回 HTTP 502 Bad Gateway；
    - Case C: 返回非合规 JSON（如 Markdown 截断文本 `{"action": "ACC...`）。
- **系统预期反应**：
  - 客户端熔断器在设定阈值（15 秒）刚性超时退出；
  - 系统捕获异常并平滑降级（Safe Fallback）：
    - 针对候选准入：保守降级为拒绝入场（Reject）；
    - 针对跟踪止损：降级采用固定对照组 A 规则（$d=0.03$）兜底推进；
  - 统一运行时主循环不受任何影响，继续健康轮询。
- **通过断言**：
  ```python
  assert unified_runtime.is_alive() == True
  assert fallback_triggered == True
  assert active_position.stop_updated == True  # 降级由固定规则安全更新
  ```

### TC-08 账户状态异动 (Unsynchronized Account State)

- **测试意图**：防范由于外部强平、手续费扣除或多币种浮亏导致实际账户可用资金骤降时，AI 模型仍基于旧的富余资金做出大额开仓决定。
- **前置与注入条件**：
  - AI 决策时获取的账户快照显示可用资金为 4,000 USDT，计算计划开仓名义价值 400 USDT。
  - 在 AI 决策返回的瞬间，其他持仓遭遇止损使得账户现金骤降至 1,000 USDT，且已达单日名义敞口上限。
- **系统预期反应**：
  - 执行引擎在接收到 AI 指令后，必须执行**最终执行态防线检查（Pre-Open Gatekeeper）**；
  - 重新读取最新的物理账本与动态权益，发现名义敞口超标或资金不足；
  - 坚决否决该入场指令：`rejected_insufficient_equity_or_exposure_limit`。
- **通过断言**：
  ```python
  assert order_submitted == False
  assert rejection_reason == "risk_limit_exceeded"
  ```

### TC-09 越权调整拦截 (Unauthorized Action Sandboxing)

- **测试意图**：防范 AI 模型产生“幻觉”或越权意图，尝试修改超出协议授权范围的参数或执行危险动作。
- **前置与注入条件**：
  - 构造包含非法越权字段的 AI 响应体：
    - Attempt 1: 试图调大单笔风险到 $5.0\%$（授权上限为 $0.6\%$）；
    - Attempt 2: 试图将跟踪止损 $d$ 调整为负数 $-0.05$（逆向放宽止损）；
    - Attempt 3: 试图越权发起“清空全账户所有其他持仓”的未授权动作；
    - Attempt 4: 试图修改冻结的核心手续费率或初始本金。
- **系统预期反应**：
  - 严密的沙箱校验网关（Sandbox Validator）识别出越界参数与未定义动作；
  - 拦截所有非法请求，将参数重置并报警：`unauthorized_parameter_override_rejected`；
  - 记入安全审计日志。
- **通过断言**：
  ```python
  assert validation_pass == False
  assert applied_risk_fraction <= 0.006
  assert applied_trail_d >= 0.02
  assert "security_violation_logged" in audit_events
  ```

### TC-10 重启与断点恢复 (Crash Continuity & Recovery)

- **测试意图**：验证当统一运行时因服务器宕机突发重启后，动态策略系统能否完整恢复决策轨迹，不漏单、不重单、不产生无主孤儿订单。
- **前置与注入条件**：
  - 在持仓存续期间，强制 kill -9 杀死主运行进程；
  - 并在停机期间模拟产生两根已闭合 15m K 线；
  - 重新拉起 `UnifiedRuntime.bootstrap()`。
- **系统预期反应**：
  - 系统启动时从 SQLite 数据库加载物理持仓与未决挂单；
  - 识别出停机期间产生的 15m K 线，连续遍历补查是否有击穿止损；
  - 对历史已处理过的候选信号严格通过 `paper_pending / paper_processed / paper_position` 查重过滤，不重复发起委托；
  - 恢复动态策略的当前参数快照，保证生命周期延续。
- **通过断言**：
  ```python
  assert recovered_runtime.open_positions_count == previous_count
  assert duplicated_orders_count == 0
  assert missed_exit_detected_and_handled == True
  ```
