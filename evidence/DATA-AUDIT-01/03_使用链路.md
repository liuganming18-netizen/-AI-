## 二、两条读取链（不能混为一谈）

工程里有两套完全独立的取数路径，**从来没有逐值比对过**：

| | 回放链（回测） | 读接口链（接口/回测服务） |
|---|---|---|
| 入口 | `EventTrendRunner.load_symbol_data` | `MarketDataRepository.from_archive` |
| K 线 | 直接 `glob` 读 parquet 年度分片 + `live.parquet`，`drop_duplicates("open_time")` | 先查 SQLite 热库；不足 `limit` 再查 parquet（DuckDB） |
| 持仓量 | 直接读 `parquet/oi/{币}/*.parquet` | 热库 `oi_history` → 不足则 parquet |
| 资金费 | 读 `parquet/funding/binance/um/{币}.parquet`（**平铺路径**） | `parquet/funding/binance/um/{币}/*.parquet`（**目录路径，不存在**） |
| 4h 预热 | `idx_start_4h − 220` 根 | 不涉及（按 `warmup_bars` 参数，默认 240） |

**后果**：资金费在两条链上**一条能读到、一条读不到**（实测：回放链能读，接口链冷读 0 行、退回热库）。
热库只到 2022-01-01，冷档能到 2020-01-01 ⇒ **接口链拿不到 2020–2021 的资金费**。

## 三、实时链路的数据来源（当前生效的那条）

`框架/backend/unified_runtime.py` 启动时：

1. **初始化（bootstrap）**：读 `WX_HISTORY_DAYS`（默认 **180 天**）的 **1h / 4h**，来源是
   `history_loader.MergedHistory`（冷层 parquet + 热库合并，同 key 热库优先）。
   冷层不可用时退回「仅热库」，并如实写进 `bootstrap.data_source`。
2. **ATR**：用读到的**全部 4h**（180 天约 1,079 根）连续递推——与回测"全历史连续序列"同源。
3. **箱体/ER/突破量**：用**重放深度** `WX_STATE_REPLAY_HOURS`（默认 2,880 小时 = 120 天）。
4. **增量（step）**：只读热库；`PoolMarketWatcher` 用 `candle_heads` 全局水位做早退。
5. **15m**：入场/止损/跟踪时从热库读 15m 序列。

窗口数字：`warmup_ms = (atr_warmup_bars×4 + breakout_max_total_hours + cooling_hours) × 1h`
= `(200×4 + 336 + 24) = 1,160 小时 = 48.3 天`（声明窗口）；
实际生效的是 `replay_ms = max(1160h, 2880h) = 2,880 小时`。

## 四、逐项证据（可直接跳到代码行）

### 4.1 4h / 1h / 15m 三周期

- 箱体只用 **4h**：42 根、宽度 2–8 倍 ATR、ER ≤ 0.30（`state_machine.check_and_form_box`）。
- 事件只用 **1h**：扫低 168h 内、回踩 72h 内、突破 336h 内、总量不超 14 天。
- 执行只用 **15m**：突破 1h 收盘后**下一根** 15m 开盘入场（`entry_delay_15m_bars=1`）。
- 跟踪止损看 **4h 最低价**：`trailing_lookback_4h_bars=1`，即只看最近 1 根 4h 的 `low × 0.95`。

### 4.2 成交额（唯一进入风险检查的"量纲"字段）

`trading_core/engine.py:496-525`：

```
prev_qv = quote_volume[入场 bar 的上一根]
cap_notional = participation_rate × prev_qv
cap_qty      = cap_notional / entry_price
若 prev_qv 缺失 ⇒ 直接拒单（reason=participation_volume_unavailable），不用 0 冒充
```

实盘侧同一逻辑在 `wx_execution.apply_order_rounding`，参数来自 `paper_engine.py:190`
（实盘视图是 **1%**，回测冻结配置是 **0.1%**——两个值不同，属已登记的差异）。

### 4.3 持仓量：当前**不参与任何判断**

- 实时：`unified_runtime.py:557` 调用 `process_1h_bar(... oi_timestamps=np.array([]), oi_values=np.array([]))`
  ⇒ 状态机拿到的是**空数组**。
- 回测：`runner.py:620` FT-LOW4H 分支写死 `enable_oi_filter=False`，且 `sm_a = sm_b = engine.sm`
  ⇒ **A/B 两组用的是同一份候选**，"A 组结果"实际是 B 组结果。
- 运行态佐证：当前运行时漏斗 `OI_UNAVAILABLE = 0`、`OI_REJECTED = 0`
  （`out/16_当前运行路径.json`）——如果 OI 门槛在执行，这两个计数不可能在 8,007 个箱体、
  1,940 次扫低、1,181 次回踩的历史回放中全为 0。

### 4.4 资金费：只在平仓时结算

- `paper_engine.py` 有 `accrue_funding`（持仓期逐次计提）和 `_settle_funding`（平仓时结算）。
- 但 `accrue_funding` 的**唯一调用方是 `live_worker.py:379`**（旧 worker），
  当前运行时 `unified_runtime.py` 调用的账本函数只有
  `open_position / advance_pending / advance_position_trailing / check_position_exit_on_bar / new_entry_gate`。
- ⇒ **当前路径下资金费在平仓那一刻一次性补记**，持仓期间账本权益不反映资金费。
  数值最终是对的（`_settle_funding` 会遍历整个持仓期），但**过程指标（浮盈、权益曲线）会偏高**。

### 4.5 多空比 / 大户：9.28 GB 零读取

全仓检索 `metrics/binance`、`parquet/metrics` 的结果：命中全部在 `evidence/` 下的研究脚本
（`FLOW-OI-01`、`FT-FACTOR-*`、`DATA-UI-01` 等），**`框架/backend` 与 `策略/` 无一处读取**。

### 4.6 聪明钱：只出页面

读取方只有 `adapter.py`、`metrics_api.py`、`gateway_ext.py`、`api/routes.py`、`public_market_read.py`，
全部是 HTTP 响应组装。策略层零引用。

## 五、结论：一句话概括"用了什么"

- **真正决定开不开仓的**：4h 的箱体与 ATR、1h 的价格与量能、15m 的入场价。
- **决定开多大的**：15m 成交额（参与率上限）+ 权益风险预算。
- **只影响成本数字的**：资金费、标记价。
- **存着但一点没用上的**：持仓量（当前）、多空比/大户（全部）、成交笔数、主动买卖量。
- **只能看的**：聪明钱、实时行情、流通量。
