# 06 · 完整接入方案（设计 / 依赖 / 阻塞）

> 对应工单第 7 条：**给出完整接入设计、依赖与阻塞。历史数据必须可查询和回放；
> 指标可按规则读取窗口，但不能将固定短窗口冒充全部历史。**
>
> 本文件只做设计与取证，**不含任何施工**。所有"要改哪一行"都是指路，不是改动记录。
> 所有数字来自 `out/` 与本单实测，可逐条回查。

---

## 一、方案定位

先说清楚这份方案**不是**什么：

- 不是"把 OI 开关打开"。开关只是 13 个阻塞里的第 1 个，单独打开会让每个突破都判 `OI_UNAVAILABLE`。
- 不是"补下载"。5m 只有 1 年、指标停在 10-14，这些是**归档链断了**，不是缺下载。
- 不是"加个字段就完事"。真正的缺口是**"某条数据在某个决策时刻是否可得"这件事从来没有被记录过**。

要解决的是三件事，按顺序：

1. **能不能读到**（存储与读接口）——现在有 3 处读不通或读不到；
2. **读到了能不能信**（时间语义与去重）——现在没有"何时可得"的证据；
3. **信了能不能用**（策略接入与回放）——现在生产路径根本没接。

## 二、目标态：五条可验收标准

接入完成不看"代码改了多少行"，看这五条能不能当场验：

| # | 标准 | 怎么验（可执行） |
|---|---|---|
| T1 | **每类数据都有唯一读接口**，且能回答"某币某时刻有没有值、值从哪来、何时可得" | 对 526 币 × 12 类数据各取 1 个点，返回里必须含 `value / source / event_time / published_at / fetched_at / revision` 六项，缺一即不合格 |
| T2 | **历史可回放**：任意 `[t0,t1]` 可按规则取到，且返回实际覆盖区间 | 取 3 个币 × 3 个区间（含 2020 年、2024 年、本月），返回必须带 `actual_start/actual_end/n_bars/coverage_ratio` |
| T3 | **PIT 合格**：策略只用 `published_at ≤ 决策时刻` 的记录 | 随机抽 200 个历史决策点，逐点检查所用每一行的 `published_at`，**0 例超前** |
| T4 | **决策可审计**：每个信号能回溯到具体数据行与窗口 | 抽 20 个信号，能列出它用到的每一行主键与窗口起止 |
| T5 | **展示与决策分离**：页面每个数据块标注"参与决策/仅展示/未接入" | 页面上 12 个数据块逐块核对徽标，与实际读代码一致 |

T3 是硬门槛。**当前 2,284 份回测摘要里 `pit_qualified=True` 是 0 个**（见 `05`），
所以这一条现在不成立，本方案的大部分工作量都花在让它成立。

## 四、接入设计

### 4.1 存储层：定死"谁是唯一事实源"

现在同一件事有两份数据、两个来源，必须定唯一事实源，否则任何特征都会重复计数。

| 数据 | 唯一事实源 | 处置 |
|---|---|---|
| 持仓量 | `oi_history`（`period='5m'`）+ 冷档 `oi/` | `metrics.sum_open_interest` 标为**派生参考**，禁止当独立特征 |
| 资金费 | `funding_history` | 冷档 `funding/` 只做长期备份，读路径可回退 |
| 价格 | `candles` 视图（= `candle_versions` JOIN `candle_heads`） | 冷档 `candles/` 存全版本，读时**必须**用 `candle_heads` 过滤 head |
| 大户指标 | 冷档 `metrics/` | 需要新开一条 5m 序列表承接实时（见 4.2） |

配套的两条硬规则：

- **去重键**：K 线按 `(exchange, market, symbol, timeframe, open_time, source_id)`；
  OI/指标按 `(symbol, ts)` 取 `ts` 最大的一条，**不插值、不补 0**。
  15m 2024 年那 2,688 根/标的重复、BTC 2020–2021 那 75,255 行重复（`01` §7.3 A4/A5）都靠这条规则消掉。
- **零值不当观测**：`sum_open_interest=0` 的行（BTC 473 行、CVC 709 行）在算增长率前必须剔除，
  否则除零出 inf（`01` A7）。

### 4.2 归档链：三个必须补的口子

**口子一：冷档导出停摆。**
`_state.json` 里 `last_run.stopped = "free 11.958 GiB < reserve 12.0"`，冷档 K 线停在 2026-10-18，
热库已到 2026-10-25 ⇒ 冷档落后 7 天。当前磁盘剩 21.9 GB，闸门已满足，**可以续跑**（需批准）。

**口子二：大户指标序列断更。**
冷档 `metrics/` 526/526 币全部停在 2026-10-14；而实时采集器的公开扩展循环
（`realtime_collector.py:2290`）写的是"**只写本机可读快照，不落库、不写历史**"。
⇒ 这类数据现在是"有 6 年存量、没有增量"。
要接进策略，必须先有一条 5m 序列。两条可选路径：

- 甲：采集器把比率块追加到 `metrics` 同构的序列表（推荐，与存量同构，能直接接续）；
- 乙：只对页首 60 标建序列（成本低，但覆盖不足 526 池，只能做研究不能做全池筛选）。

**口子三：持仓量 snapshot 未归档。**
`oi(period='snapshot', prefer='cold')` 返回 0 行——冷档只存 5m 序列。
要么把 snapshot 一起归档，要么在接口层明确声明"snapshot 仅热层近 44 天"，
**不许**让调用方以为它和历史一样长。

### 4.3 索引层：`_catalog.json` 重建

现状：32,920 条登记，**11,471 个磁盘文件未登记、1,909 条登记指向不存在的文件**（`out/04`）。

关键判断（这一条改变了优先级）：**读路径不查索引**。
`market_repository.py` 的 `_flat_shards` / `_candle_shards` / `cross_section` 全部直接 glob 目录，
所以索引失效**不影响查询**。受影响的是三处：

| 消费者 | 症状 |
|---|---|
| `datacenter_service.py:25` | 数据中台页面按索引统计 ⇒ 少算 11,471 个文件 |
| `metrics_api.py:1341` | 数据核验页报 `unverified` 或数量对不上 |
| `ops/version_manifest.py:32` | 发布版本 manifest 与实际磁盘不一致 |

⇒ 索引重建属于**展示与发布正确性**，不是查询阻塞。优先级放在第二批，不必抢在接线之前。
重建方式：遍历 `parquet/*/*/*/*`，读每个 parquet 的 footer 取 `rows`、算 `bytes`/`sha256`、
从 schema 取 `columns`，写回 `{shards:{相对路径:{...}}}`。42,482 个文件、20 GB，
单次可完成；`_catalog.json.bak-20261024T0333Z` 已存在，重建前再留一份即可回退。

### 4.4 读接口层：补三个方法 + 改一处路径

`MarketDataRepository` 现在只有 `candles` / `oi` / `funding` / `cross_section` 四个公开方法。

| 动作 | 位置 | 内容 |
|---|---|---|
| 新增 `metrics()` | 新方法 | 冷档读 `metrics/*/*/*/*.parquet`，支持字段选择、区间、`limit`；返回带 `fetched_at`（现为 `None`，须显式标"未知"而不是留空） |
| 新增 `coverage()` | 新方法 | 按 `(symbol, dataset)` 返回该币的可用区间（口径同 `out/10`），**让调用方不必假设全局交集** |
| 新增 `pit()` | 新方法 | 输入 `(rows, decision_ts)`，返回可用/超前行数与原因；统一 PIT 判定，禁止各调用方自己写 |
| 修 `_flat_shards` | `market_repository.py:127` | 现在拼 `funding/binance/um/BTCUSDT/` 再 glob `*.parquet`，但磁盘是 `funding/binance/um/BTCUSDT.parquet` 平铺。**加一条平铺分支**即可，实测 `len(shards)==0` ⇒ 冷读 0 行 |
| 明确 `oi(period='snapshot')` | `market_repository.py:208` | 冷档无此序列，接口须返回"仅热层"标记，不许静默返回空列表 |

补完后 `oi` 的冷读已验证可用（2024-01、2025-06 各返回 50 行，`source='binance.archive.metrics'`），
`candles` 冷读也可用（2024-01 返回 50 根）。**唯一读不通的就是 funding 冷档**，且它现在被热库兜着。

### 4.5 时间语义：四时间戳落库规范（T3 的根）

现状（`01` §八）：

| 数据 | 事件时间 | 发布/可得时间 | 采集时间 | 修订版本 |
|---|---|---|---|---|
| K 线（热库） | `open_time`/`close_time` | `available_at` 填充 49.6%，且**是本地入库时刻**，比收盘晚 12 毫秒到 75.8 天 | `sources.imported_at` | `source_id` |
| K 线（冷档） | 同上 | **全空** | 无 | `source_id` |
| 持仓量 5m | `ts` | **无字段** | `fetched_at` 44.2%（2026-09 全空） | 无 |
| 持仓量 snapshot | `ts` | 无 | `fetched_at` 100% | 无 |
| 资金费 | `funding_time` | 无 | `fetched_at` 100% | 无 |
| 大户指标 | `ts` | 无 | **无字段** | 无 |

规范（新增字段，不改语义）：

```
event_time      交易所事件时刻（K线 close_time、OI 桶起点、funding 结算点、比率 5m 槽位）
published_at    交易所可获取时刻
fetched_at      本地采集时刻（写入即打，采集器统一负责）
revision        source_id / version，用于识别同一事件的多个版本
```

`published_at` 的推导规则（**必须标 `derived`，不能冒充交易所原值**）：

| 数据 | 推导规则 | 保守性 |
|---|---|---|
| K 线 | `close_time + 1s` | 币安 K 线在收盘后才可获取，+1s 是下界 |
| 持仓量 5m | 桶起点 `+ 5min` | `openInterestHist` 的 5m 桶在桶结束后才出现 |
| 资金费 | 取 `funding_time` 本身 | 结算值在结算时刻确定 |
| 大户指标 5m | 桶起点 `+ 5min` | 同 OI |

**历史部分不可能事后拿到真实发布时刻**——这一点必须写在数据字典里，
结论只能是"保守下界 + 计算不超前"，不能声明"当时确实可得"。
这也正是 `05` 里 2,284 份摘要 `pit_qualified=True` 全为 0 的原因：字段根本没填。

### 4.6 窗口读取规则（工单明确要求）

**禁止**用固定根数（如 `limit=200`）当"历史"。每类数据必须声明一个三元组：

```
lookback        回看长度（如 OI 6h、ATR 14 根 4h）
min_bars        最少根数，不足即判 insufficient
max_staleness   最大允许陈旧度（如 15 分钟）
```

读取函数必须返回：

```
{values, actual_start, actual_end, n_bars, coverage_ratio, insufficient_reason}
```

`coverage_ratio < 声明阈值` 时**必须显式返回 `insufficient`**，
不许静默降级成"用更短的窗口凑一下"——那正是"固定短窗口冒充全部历史"。

按现有策略口径（`event_trend_v0_1/config.py`）落实：

| 用途 | lookback | min_bars | max_staleness | 不足时行为 |
|---|---|---|---|---|
| 箱体 | 42 根 4h | 42 | 8h | 不建档（现有行为，保留） |
| ATR | 14 根 4h | `atr_warmup_bars` | 8h | 不开闸（现有行为，保留） |
| 扫低 | 168h | 依 1h | 2h | 不判 |
| 回踩 | 72h | 依 15m | 1h | 不判 |
| 突破放量 | 20 根 15m | 20 | 1h | 不判 |
| **OI 6h 增长** | 6h（`oi_lookback_hours=6`） | 6 个 1h 点或 72 个 5m 点 | **900s**（`oi_max_time_distance_sec`） | 判 `OI_UNAVAILABLE`（fail-closed，保留） |

### 4.7 策略接入：三档 + 影子模式

不同数据的证据强度差得很远，不能一把全接。分三档：

**P0 · 成本类（资金费、标记价）——可直接接**
只影响持仓成本，不改信号方向。现在已经在用，只需把 `published_at` 补齐、把冷读路径修好。
风险：低。验收：抽 100 笔持仓，逐笔重算成本，误差应为 0。

**P1 · 确认类（持仓量 6h 增长）——先影子，不拦单**
OI 是唯一"数据齐、语义清、但没接线"的一项（`01` §7.4 N1：526/526 币 5m 序列健康）。
设计一个**影子通道**：

```
生产路径（不动）：sm  ← enable_oi_filter=False，喂空数组（现状）
影子路径（新增）：sm_shadow ← enable_oi_filter=True，喂真实 6h OI 窗口
每条 1h 收盘：把 shadow 的判定（PASS / REJECT / UNAVAILABLE + 增长率 + 阈值 + 时间距离）
            写入独立记录，不影响任何下单
```

影子模式的好处是**零风险拿到冻结规则 §7 要的那份对照数据**：
"共同事件上 OI 通过/拒绝、数值、阈值、时间、被过滤事件原本会赚/亏多少"。
现在这份数据一份都没有，因为 `sm_a = sm_b`（`runner.py:625`）让 A/B 同源。
跑够样本（建议 ≥ 500 个共同事件）再裁决 A 还是 B，比直接开开关安全得多。

**P2 · 研究类（大户指标、taker、成交笔数）——先补序列，不进生产**
这三类现在是"零读取方"，且指标序列停在 2026-10-14（N3）。
在 4.2 的口子二补好之前，任何"用大户指标做筛选"的方案都是空谈。
补好后先做研究（是否能解释突破后的续涨），不进生产判断。

### 4.8 回放层：两条链必须逐值对齐

现在有两条独立读取链，**从未逐值比对**：

| 链 | 入口 | 数据源 |
|---|---|---|
| 回放链 | `EventTrendRunner.load_symbol_data` | 直读 parquet |
| 读接口链 | `MarketDataRepository` | sqlite 热层 + parquet 冷层 |

风险很直接：同一个历史窗口，回放用一套数、接口用另一套数，两边结论无法互证。
必须先做一次比对（只读、无风险）：10 币 × 4 周期 × 1,000 根，**要求逐值相等**；
不等的地方要能解释（去重规则、head 版本、冷热边界）。

回放还有两条硬规则：

- **按逐币区间取数**，不用全局交集。四者齐全的全局交集只有 13.7 天，中位 656.5 天（`out/11`），
  用全局交集等于把 98% 的历史扔掉。
- **窗口必须声明并返回实际覆盖**，同 4.6。

### 4.9 展示层：徽标制度

页面每个数据块挂三种徽标之一，且必须与 `03_使用链路.md` 的四态判定一致：

| 徽标 | 含义 | 当前应挂 |
|---|---|---|
| **参与决策** | 改了它会改信号 | 4h/1h/15m 价量、15m 成交额 |
| **仅展示** | 读了但不进判断 | 聪明钱、当前持仓量、多空比 |
| **未接入** | 没有读取方 | 成交笔数、taker、大户指标、OI snapshot |

这条不是形式主义：`05` 里"全池 0 候选"那次误判，根子就是**把页面显示当成了策略使用**。

## 六、阻塞清单（13 条，按解除成本排序）

每条给：现象 / 证据 / 影响 / 解除条件 / 不解的后果。

### B1 · `enable_oi_filter` 硬编码关闭，无外部入口
- **现象**：三处构造默认 `False`，`argparse` 里没有该开关，`runtime` 不传参。
- **证据**：`unified_runtime.py:353 / 656 / 2143 / 2857 / 2836-2841`。
- **影响**：生产跑的是消融组 B，不是冻结规则的主策略 A；页面与报告都看不出这一点。
- **解除**：加 `--oi-filter {on,off,shadow}` 参数，默认保持 `off`（不改行为），并把取值写进 run note。
- **不解**：A/B 对照永远做不了，"OI 有没有用"永远无答案。

### B2 · 实时链路喂空 OI 数组
- **现象**：`process_1h_bar(..., oi_timestamps=np.array([]), oi_values=np.array([]))`。
- **证据**：`unified_runtime.py:557`。**注意**：热库 OI 是新鲜的（526/526，520/526 一小时内更新），
  所以这是**线没接**，不是**数据没采**。旧说法"实时链路没有 OI 采集"已被实测推翻（`01` §7.4 N1）。
- **影响**：即便打开开关，每个突破都判 `OI_UNAVAILABLE`（fail-closed）。
- **解除**：在调用点按 4.6 的窗口规则取 6h OI 窗口；或走影子通道先不拦单。
- **不解**：开关打开也没用。

### B3 · 两条读取链从未逐值比对
- **证据**：`EventTrendRunner.load_symbol_data` 直读 parquet；`MarketDataRepository` 走热+冷。
- **影响**：回放结论与接口结论无法互证。
- **解除**：10 币 × 4 周期 × 1,000 根逐值比对（只读，可立即做）。
- **不解**：任何"数据一致"的声明都没有依据。

### B4 · PIT 字段缺失（最重的一条）
- **现象**：冷档 `available_at` 全空；冷档 OI `fetched_at=None`；热库 `oi_history.fetched_at` 池内 57.6% 为空；
  热库 `available_at` 填充 49.6% 且是**入库时刻**不是发布时刻。
- **证据**：`01` §八、`out/02b_四时间戳填充.csv`、`out/13`。
- **影响**：`05` 里 2,284 份摘要 `pit_qualified=True` 全为 0。策略只能声明"计算不超前"。
- **解除**：按 4.5 落四时间戳；历史部分用推导规则并标 `derived`。
- **不解**：所有 PIT 声明都不成立，回测结论不能对外。

### B5 · 资金费冷读路径不符
- **现象**：`_flat_shards` 拼 `funding/binance/um/BTCUSDT/` 再 glob，磁盘是 `funding/binance/um/BTCUSDT.parquet`。
- **证据**：`market_repository.py:127`；实测 `len(shards)==0`、冷读 0 行、热读 5 行。
- **影响**：**当前零损失**（`funding_history` 覆盖 2022-01-01 → 2026-10-25，2,120,838 行）。
- **解除**：加平铺分支。
- **不解**：热库一旦轮转或重建，资金费历史立刻全断。

### B6 · 冷档导出停摆 7 天
- **现象**：`_state.json` `last_run.stopped = "free 11.958 GiB < reserve 12.0"`；冷档 K 线止于 2026-10-18，热库到 2026-10-25。
- **影响**：冷档落后；一旦热库轮转，10-18 之后的数据两边都没有。
- **解除**：当前剩 21.9 GB，闸门已满足，续跑即可（**需批准，本单不跑**）。
- **不解**：缺口每天扩大。

### B7 · `_catalog.json` 失效
- **现象**：11,471 个文件未登记、1,909 条悬空、`metrics` 1,647 个文件不在索引里。
- **影响**：**不影响查询**（读路径直接 glob）；影响数据中台展示、核验页、发布 manifest。
- **解除**：扫描重建。
- **不解**：页面数字长期少于真实磁盘。

### B8 · 大户指标序列断更 + 实时不落库
- **现象**：冷档 526/526 币 `max(ts) ≤ 2026-10-14`；实时公开扩展"只写快照、不落库、不写历史"。
- **证据**：`realtime_collector.py:2290` 的 docstring 原文；duckdb 全池实测 127,973,455 行。
- **影响**：这类数据"有存量没增量"，无法做任何时间序列特征。
- **解除**：二选一（同构序列表 / 页首 60 标序列）。
- **不解**：9.28 GB 永远只能看不能用。

### B9 · 持仓量双源 + snapshot 未归档
- **现象**：`metrics.sum_open_interest` 与 `oi_history` 同一件事两份；`oi(period='snapshot', prefer='cold')` 返回 0 行。
- **影响**：当独立特征会重复计数；调用方会误以为 snapshot 也有长历史。
- **解除**：定 `oi_history` 为唯一事实源；接口显式声明 snapshot 边界。
- **不解**：特征重复计数，OI 增长率算两遍。

### B10 · `sm_a = sm_b` 使 A/B 同源
- **证据**：`runner.py:625`，注释写着"与模拟盘使用同一流式信号入口；B 变体不要求 OI"。
- **影响**：FT-LOW4H 线上 A/B 对照不成立，`05` 里 22 个直接受影响的 run 都沾这条。
- **解除**：拆成两个引擎实例（`sm_a` 开 OI、`sm_b` 关 OI）。
- **不解**：跑再多回测也回答不了 OI 的价值。

### B11 · 5m 只有 1 年
- **现象**：5m 覆盖 551 组合、2025-10-04 起，缺失 0 根但起点就是 1 年前。
- **影响**：任何"5 分钟精度 + 3 年以上"的设计都缺数据。
- **解除**：回填（**需批准，本单禁下载**）；或把设计降到 15m。
- **不解**：5m 级回放只能做 1 年。

### B12 · `realtime_quotes` 通用三时间戳冻结
- **现象**：814 行 `event_time`/`received_at`/`fetched_at` 全停在 2026-10-05 04:44；
  `price_event_time`/`mark_event_time`/`updated_at` 实测到 2026-10-25 17:50。
- **影响**：任何用 `event_time` 判新鲜度的读取都会误判"20 天没更新"。
- **解除**：修写入，或在读取侧改用 typed 列并显式声明。
- **不解**：健康检查会漏报或误报。

### B13 · 重复行未在读取层统一去重
- **现象**：15m 2024 年 2,688 根/标的双版本；BTC OI 2020 年 100% 重复（75,255 行）。
- **影响**：不去重的聚合直接翻倍。
- **解除**：把 4.1 的去重键固化进读接口，而不是靠调用方自觉。
- **不解**：每个新写的分析都要重新踩一次。

## 七、依赖与施工顺序

依赖关系（箭头是"必须先有"）：

```
B3 逐值比对 ──┐
B5 funding 路径 ─┤
B7 索引重建 ─────┼──> 4.3/4.4 读接口补齐 ──> B4 四时间戳 ──> 4.6 窗口规则
B9 双源归一 ─────┘                                        │
                                                          v
B6 冷档续跑 ──> 冷档完整 ─────────────────────────> 4.8 回放对齐
                                                          │
B8 指标序列 ──> 4.2 口子二 ──> P2 研究类                  v
                                              B2 接线 ──> 影子模式 ──> B1 开关 ──> B10 拆 A/B
```

分四批，每批都能独立验收、独立回退：

| 批 | 内容 | 风险 | 是否需要批准 | 验收 |
|---|---|---|---|---|
| **批 0**（只读，无改动） | B3 逐值比对、B7 索引重建预演、B4 覆盖率量化、B12 列名核对 | 无 | 不需要 | 产出比对报告；索引预演不写盘 |
| **批 1**（改代码不改行为） | B1 加开关（默认 off）、B5 平铺分支、B9 双源归一、B13 去重键、4.4 三个新方法 | 低（默认路径不变） | 需要 | 现有回测结果逐位不变 |
| **批 2**（改行为） | B6 冷档续跑、B2 接 OI 到影子通道、4.5 四时间戳落库 | 中（写盘 + 新字段） | 需要 | 影子记录开始产出；冷档追平热库 |
| **批 3**（研究） | B10 拆 A/B、影子样本够 500 后做对照、B8 指标序列接入研究 | 中 | 需要 | 能回答"OI 拦掉了多少、那些本来赚还是亏" |

**批 1 的验收标准要特别硬**：`enable_oi_filter` 加参数但默认 `off`，
所以**同一批回测的候选数必须一模一样**。这是"改了代码没改行为"的唯一证据。

## 十、需要用户裁决的四件事

本单不施工，但这四件必须有人拍板，否则方案落不了地：

1. **生产跑 A 还是 B？**
   - 跑 A ⇒ 必须先做批 1 + 批 2（接 OI、补 PIT），否则每个突破都被 fail-closed 打死；
   - 跑 B ⇒ 必须在页面/报告明确标注"当前为消融组，未使用持仓量门槛"，停止把结果称作主策略。
2. **`runner.py` 的 `sm_a = sm_b` 拆不拆？** 不拆就永远回答不了"OI 有没有用"。
3. **大户指标要不要接？** 要接就得先补实时序列（B8），代价是采集器要新增落库路径；
   不接就该在页面上标"未接入"，别再出现在数据资产宣传里。
4. **5m 要不要回填 3 年？** 需要下载，本单禁止；不回填就把 5m 相关设计降到 15m。

> 以上四项本单只列证据与选项，不代做决定。
