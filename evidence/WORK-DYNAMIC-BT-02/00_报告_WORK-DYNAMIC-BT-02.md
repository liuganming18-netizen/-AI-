## 3. 二、逐笔订单与成交的来源核实

### 3.1 结论：**是真订单对象，不是把汇总拆两行**

6,790 条订单行 = 3,395 笔 × **恰好 2 条**（1 入 1 出，`orders_per_trade_distribution = {"2": 3395}`）。
来源是 zip 内 `backtest-result-*.json` 的 `trade.orders`，**7 个字段逐字未改**：
`amount / safe_price / ft_order_side / order_filled_timestamp / ft_is_entry / ft_order_tag / cost`。

「不是拆出来的」有硬证据 —— 四条公式在 6,790/6,790 行上同时成立：

| 校验 | 通过 | 最大偏差 |
|---|---|---|
| `cost = amount × price × (1 + fee_side)` | **6,790 / 6,790** | 4.96e-14 |
| `amount = trade.amount` | 6,790 / 6,790 | 0 |
| `price = trade.open_rate / close_rate` | 6,790 / 6,790 | 0 |
| `order_filled_timestamp = trade.open/close_timestamp` | 6,790 / 6,790 | 0 |
| `ft_order_tag = enter_tag / exit_reason` | 6,790 / 6,790 | 0 |
| **逐笔盈亏 = amount×(close−open) − 双边费 + funding** | **3,395 / 3,395** | 5.00e-9 |

最后一条最关键：拆出来的两行不会自带独立的 `cost` 浮点尾数，也不可能**加上 funding 后**正好还原
引擎的 `profit_abs`。5.00e-9 的残差是引擎自己 `round(profit_abs, 8)` 造成的（`trade_model.py:1198`），
上界 `0.5e-8`，实测正好贴界。

与 BT-01 `14_订单与逐次成交_全部.csv.gz` 逐行比对：**0 增行、0 改值**，价格/数量差 0，`cost` 差 ≤5.7e-14（2 ULP）。

### 3.2 三类来源（逐行标注在 `02_逐笔订单核对.csv.gz` 的 `source` / `*_status` 列）

| 类别 | 字段 | 说明 |
|---|---|---|
| **引擎原始** | orders 的 7 个字段、trade 的 `fee_open/fee_close/funding_fees/exit_reason` | 逐字来自原始导出 |

### 4.3 为什么这不是「放宽标准换通过」

1. **全精度→全精度的比对本身就通过**：`fsum` vs 引擎 `profit_total_abs` 最大差 **8.5e-14**，期末权益 **4.5e-13**
   ⇒ 计算层面**没有差异**，不存在「算错了靠容差盖住」。
2. **5e-5 被证明 100% 来自报告层取整**：把全精度结果按 4 位小数取整后，与 BT-01 表值**逐字相等**，
   Σprofit **45/45**、maxDD **45/45**、Sharpe **45/45**。若真有计算差异，取整后不可能字字相同。
3. **1e-6 对 4dp 表是不可满足的**：任何 4 位小数的表都不可能满足 1e-6 的一致性要求。
   拿 1e-6 去判 4dp 表不是「更严格」，而是把标准定到无法满足再宣布失败。
4. **新增了更硬的判据**：「取整后逐字相等」比「差值 ≤ 某阈值」更强 —— 它排除了「碰巧落在阈值内」。

### 4.4 顺带查出并归因的一处真实差异（不是舍入）

`04` 曲线（含浮盈，00:00 采样）与引擎钱包余额（已实现）逐日比对：
50,670 个日界里 **61 个** 差 >1e-9，**且 61/61 全部发生在「00:00 整点恰好有开/平仓」的日界**，
最大 123.17 USDT。原因：BT-01 把该时刻的平仓计入当日，引擎 00:00 快照早于平仓入账。
明细 `out/20b_日界差异明细.csv`。**只影响该日瞬时值，不影响期末权益与逐笔盈亏**（期末差 4.5e-13）。

### 4.5 定义差异（禁止混用，不算错误）

- 本单 maxDD = 含浮盈日权益的最大回撤；引擎 `max_drawdown_account` 基于**已实现**余额、15m 粒度
  ⇒ 例如 `DYN_Vs06_Z04`：本单 **−5.43%**，引擎 **5.04%**（引擎报正数幅度）。两者不可互相当校验。

### 5.3 仍未闭合的 1 处缺陷（前端，属反重力）

**现象**：点「15m」显示 `2548 根（15m 原始）`、点「30m」显示 `2548 根（30m 聚合）`，与「1h」的 2548 根**完全相同**；
而后端同一 focus 下 15m 原生是 **10,192 根** ⇒ **15m / 30m 两个视图画的是 1h 的 K 线、贴了错的周期标签**。

**根因**（已定位到行）：`UI界面/web/src/utils/candles.ts` 的 `bucketCandles(candles, bucketSec, sourceSec=900)` 默认把载荷当 15m 源；
而页面调 `/chart` 时**不传 `timeframe`**，后端按默认 `1h` 返回 ⇒ 15m（`900<=900` 原样返回）、30m（`1800>900`，把 1h 再按 30m 分箱，根数不变）都错。

**影响面**：只有 15m / 30m；1h / 4h / 8h / 12h / 日线不受影响（桶≥1h，聚合已复算全等）。

**修法（二选一，本单未改前端）**：
- **A**：请求带周期 `labGetChart(id,{focusMs,symbol,timeframe:当前周期})`，并把 `sourceSec` 设为 `TF_SECONDS[chart.display_timeframe]`；比载荷更细的周期禁用。
- **B**：保持只取 1h，把 15m/30m 按钮禁用（`available=false` + 原因），与现有 1m/5m 的处理一致（宁可禁用，不给假图）。

### 5.5 追加：用户截图「K线1小时线居中」已修（BT-KLINE-CENTER-01）

用户发来 ACHUSDT 1h 截图（18 根挤在左侧、右侧大片空白）并配文「K线1小时线居中」。已定位、修复、并逐像素验证。

**先纠正一个容易误判的点**：这不是「数据只有 18 根」造成的。首屏本来就是铺满的（右空 0.9%），
是**窗口尺寸变化**之后才长出的空白 —— 复现路径 `1668 → 1200 → 1668`，同一步右空 **45%、只剩 10 根可见**。

**根因**（有官方源码 + 中间态读数，不是推断）：`lockVisibleTimeRangeOnResize: true` 锁的是**时间窗**
（官方 `_private__setWidth` 里 `barSpacing *= newWidth / oldWidth`），而 `fixLeftEdge: true` 的补偿分支
`rightOffset -= Math.round((oldWidth - newWidth) / barSpacing) + 1` 在**变宽**时变成「加」，
实测把 `rightOffset` 从 2 顶到 10 ⇒ 右侧凭空多出 8 根空档（8/18 ≈ 44%）。
原注释「保留 `barSpacing`」是反的，已一并改正。

**修法**：挂载 effect 里加 `ResizeObserver` 收口（`LightweightChart.tsx`，4 处改动，见
`patches/01_前端改动记录_BT-KLINE-CENTER-01.md`）：复位 `rightOffset` → 数据装得下就按数据域重新铺满 →
装不下（用户放大过）就只贴右缘、不动缩放级别。用户已拖到历史视窗时**一律不碰**（沿用既有 `followRef` 语义）。

| 不吃缩放（反向保护） | 2548 根场景 9.0px→9.0px、18 根场景 81.0px→81.0px，相对变化 **0.0%** |
