## 二、关键发现：01 的改动⑥在生产链路上**没有调用者**

这是本次分析最重要的发现，直接影响「重载哪些进程」。

| 事实 | 证据 |
|---|---|
| `live_worker.advance_paper` 只在 `live_worker.run_once` 里被调用 | `live_worker.py:515` `out["paper"] = advance_paper(T=T, log=log)` |
| `run_once` 只在 `live_worker.py` 自己的 `main()` 里被调用 | `live_worker.py` 末尾 `__main__` → `run_once(**kw)` |
| **生产代码没有任何一处 import `live_worker`** | 全仓 `grep "import live_worker"` 只命中 `verify_exec_wiring.py:89`（验证脚本，非生产） |
| `backtest_worker.py` 里既无 `live_worker` 也无 `advance_paper` | 该文件 grep 结果为空 |
| 真正的挂单推进由 Runtime 驱动 | `unified_runtime.py:2339` `UnifiedExecutionDaemon.execute_cycle` → `PE.advance_pending(T=now_ms)` |

**结论**：01 改动⑥（`live_worker.py:362-366` 的 `available_at` 不伪造 + `epoch_ms=floor_ms`）
**改在一个生产环境不会执行的函数里**。它不影响本次重载的效果，也**不能**拿它当「已生效」的证明。
真正影响下单行为的是 ①②③④（Runtime 进程）与 ⑤（API 进程）。

## 三、每个命令的连带影响（逐条实测读码）

| 命令 | 停什么 | 起什么 | 采集器 | Worker | 是否可用于本单 |
|---|---|---|---|---|---|
| `sh start.sh status` | — | — | 只探测 | 只探测 | 可用于观测 |

**逐条读码依据**：
- `stop()` 三步顺序：Runtime（`service_manager.py:912-946`）→ Worker（`:948-977`）→ API（`:979-1017`）；
  第 4 步注释明写「采集器默认不碰（避免误停采集器）」（`:1019-1029`）。
- `stop()` 每步都做**身份核验**：cmd 必须含 `unified_runtime.py` / `backtest_worker.py` / `adapter.py`，
  且 cwd 必须在 `backend_dir` 或 `project_root` 下（`:927`、`:958`、`:990`）；
  身份不符 ⇒ `rejected_unverified` + 抛错，**不盲杀**。

## 五、最小范围受控重载方案（本单采用）

**不动 Worker、不动采集器，只重启 Runtime + API。**

| 步骤 | 动作 | 理由 |
|---|---|---|
| 1 | 已存 `baseline/` 一致性快照（步骤1已完成） | 回滚锚点 |
| 2 | 隔离断言全通过（步骤5前置，见 `out/07_隔离断言.md`） | 代码行为先证对，再上线 |
| 3 | 对 **68802** 发 SIGTERM（先核验 cmd 含 `unified_runtime.py`、cwd 匹配） | 让 ①②③④ 生效 |
| 4 | 对 **68764** 发 SIGTERM（先核验 cmd 含 `adapter.py`、cwd 匹配） | 让 ⑤ 生效 |
| 5 | `ENABLE_PAPER_RUNTIME=1 sh start.sh` | 起 API + Runtime；Worker 存活 ⇒ 自动复用；采集器只探测 |
| 6 | 记录新 PID / 启动时刻 / 加载证明 / API 实测 | 步骤4 交付 |
| 7 | 等一次正常扫描水位推进（1h 或 15m 边界） | 自然行为证据 |

**为什么不用 `restart`**：`restart = stop + start`，`stop` 会连带停掉 Worker（68775）。
Worker 承载的是回测任务队列（6222 条 jobs），停它会中断在跑的回测，属于**扩大重启范围**，
违反工单「若做不到隔离范围，停止并报告主代理，不扩大重启范围」。

**为什么可以直接 SIGTERM 而不用 `stop`**：`stop()` 的额外价值是清理 pidfile 与写 `service_meta`；
直接 SIGTERM 后，`start()` 会检测到 pid 已死并重新拉起，同时重写 pidfile 与 meta
（`service_manager.py:790`、`:812`）。差别只在于 meta 里会短暂残留「running」旧记录，
不影响启动判定（`start()` 用 `is_pid_alive()` 而非 meta 决定是否启动）。

**回滚方式**：把 `baseline/` 里的源码哈希对应的版本恢复（当前改动未提交，`git checkout` 会**丢掉 01 的修复**，
故回滚不采用 git，而是先备份当前 5 个文件，再用 `cp` 还原），然后按同样步骤重启 Runtime + API。
**绝不**用整库快照覆盖当前账本（工单禁止）。
