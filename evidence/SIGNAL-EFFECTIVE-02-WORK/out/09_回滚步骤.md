## 一、先分清「回滚到什么」

| 层级 | 目标状态 | 手段 | 代价 |
|---|---|---|---|
| **L1 回滚本单** | 撤掉「重载」这个动作本身 | **不需要改代码**，代码与重载前逐字节相同；只要按同样范围重启进程即可（会重新加载同一份代码） | 无（等于白重启一次） |
| **L2 回滚到 01 修复前** | 回到提交 `9e3bc14b` 的后端代码 | `git checkout -- <5 个文件>` + 重启 Runtime/API | **会同时丢掉 01 的六处修复和 X1–X4 的既有改动**，且无法区分恢复 |
| **L3 账本回滚** | 撤掉账本里的记录 | **禁止**用 `baseline/paper_3a_snapshot.sqlite3` 覆盖当前账本；只能用 `paper_correction` **追加更正**（保留原始行） | 见工单禁止项 |

**本单只部署了「进程变更」，没有改代码**，所以 L1 是唯一真正属于本单的回滚动作。
L2/L3 属主代理/用户层级，本单不执行，但把命令写清以便需要时精确操作。

## 二、L1：回滚本单（撤掉重载）

**适用场景**：重载后出现异常，想回到「重载前」的进程状态。
**注意**：代码不会变（本来就没改），只是让进程重新加载同一份文件。

```sh
cd /Users/boos/Desktop/威科夫因子共振趋势/框架/backend

# 1) 核验目标进程身份（不得盲杀）
/Users/boos/.workbuddy-ai/binaries/python/envs/default/bin/python - <<'PY'
import psutil
for p in psutil.process_iter(["pid","cmdline","cwd","create_time"]):
    try: cl=" ".join(p.info["cmdline"] or []); cwd=p.info["cwd"] or ""
    except Exception: continue
    if "框架/backend" not in cwd: continue
    for k in ("unified_runtime.py","adapter.py","backtest_worker.py","realtime_collector.py"):
        if k in cl:
            print(p.info["pid"], k, p.info["create_time"])
PY

# 2) 只停 Runtime 与 API（不动 Worker、不动采集器）
kill -TERM <runtime_pid>
kill -TERM <api_pid>
# 等两者退出（最多 40s）

# 3) 拉起
ENABLE_PAPER_RUNTIME=1 sh start.sh --enable-paper
```

**验收回滚成功**：`service_meta_8787.json` 里 api/runtime 的 pid 与 `started_at` 更新；
`live_run` 三水位逐位不变；`paper_pending` / `paper_position` 行数不变。

**L2 的确定代价（必须先告知用户）**：
- 289 条研究信号**保持** `historical_research` 身份（那是数据，不是代码），
  但**代码级的 `approved` 判据会消失** ⇒ 页面「当前区」与路由扫描都少一道屏障，
  只剩 `executable_state` / `role` / `arm` / `available_at` 四层在挡；

**L2 之后如果要恢复**：把 `/tmp/se02_before_L2` 里的 5 个文件 `cp` 回原位，再重启一次。
`baseline/src_at_reload/` 是更早的同一份备份，可互为校验（sha256 应一致）。

## 四、L3：账本（**禁止整库覆盖**）

工单原文：「**禁止**用旧整库快照覆盖当前账本，禁止恢复历史 `recovered/enterable`、伪造 `available_at` 或移除 approved/仓位保护。」

所以：

- `baseline/paper_3a_snapshot.sqlite3` 等快照**只能用于只读比对**，**不得** `cp` 回去覆盖；
- 若确实需要撤销某笔记账，只能走 `paper_correction` **追加更正行**（保留原始行，可审计）；
- 若需要强平，必须由用户明确指令，且走正常退出路径（不得直接改 `paper_position.status`）。

## 五、回滚失败的处置（不做破坏性恢复）

若重启后 API 起不来或 Runtime 崩溃：

1. **保留现场**：不要删 pid 文件、不要清 `locks/`、不要覆盖账本；
2. 读 `logs/backend-8787.log` / `logs/runtime-3a-8787.log` 末尾 500 字，原样记录；
3. 若属代码问题 ⇒ 按 L2 回退 5 个文件后重启；
4. 若属配置问题（`approved_params()._config_valid == False`）⇒ 不启动，报主代理，
   **不得**为了启动而放宽配置校验；
5. 采集器（pid 42278）与既有挂单/持仓管理**不受影响**，不需要也不允许停它们。
