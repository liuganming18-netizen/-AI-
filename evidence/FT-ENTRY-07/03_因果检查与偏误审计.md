# FT-ENTRY-07 因果检查与偏误审计报告

> **审计对象**：FT-ENTRY-07 C 路线企稳确认对照（C0、C1、C2 共 27 组实验）  
> **执行环境**：Freqtrade 回测系统（Python 3.11, Binance Futures 模式）  
> **审计结论**：**通过全量因果律与防偏误检查，未发现前视偏误、未发现止损漂移、未发现违规内部补成交。**

---

## 1. 信号判定与执行时序审计（因果律核验）

### 1.1 时序流水线定义
```
[T0: 原信号 1h K线] ---> [T1 = T0 + 1h: 确认 1h K线闭合] ---> [T2 = T1 + 15m: 执行 15m K线开盘撮合]
       (产生待确认事件)              (执行 C1/C2 判定)                     (挂单成交)
```

### 1.2 时间戳交叉核验结果
- **核验规则**：对于每一笔成交的 C1/C2 交易，其实际成交时间戳 `open_timestamp` 必须严格满足：
  $$\text{open\_timestamp} = \text{confirm\_time\_ms} + 900,000 \text{ ms}$$
  即成交必须发生在确认 1h K 线闭合时刻之后的第 1 根 15m K 线（+15分钟）。
- **核验抽样与全量扫描**：
  - 扫描 C1 与 C2 各组 `trades_*.csv` 与 `audit_confirmation_*.csv`；
  - 所有成交订单的 `open_timestamp` 均精确等于 `confirm_time_ms + 15m`；
  - **绝无任何一笔订单在确认 K 线闭合前成交**，彻底排除了利用未闭合 K 线偷跑信号的可能。

---

## 2. 避免前视偏误与成交价格审计

### 2.1 禁止确认 K 线内部低点回溯补撮合
- **检查内容**：确认 K 线的最低价通常低于其收盘价，回测系统严禁使用确认 K 线内部的 `low` 作为成交价格。
- **审计发现**：
  - 系统使用既定 15m 柱执行逻辑，在确认 K 线完成后的下一根 15m 柱以开盘市价（`open_rate`）撮合成交；
  - 经逐笔对比，所有成交价格均为确认柱收盘之后的真实 15m 市场价，无任何回溯低点滑点美化。

### 2.2 单周期确认与严禁滚动等待
- **检查内容**：确认期仅限紧接着的**第 1 根 1 小时 K 线**。若该根不符合条件，是否被立即废弃？
- **审计发现**：
  - 状态机中设置待确认状态生命周期严格为 1 个周期（1小时）；
  - 若确认失败，事件状态直接迁移至 `EventState.REJECTED` 并彻底终结；
  - 审计日志全量记录了拒绝原因（如 `outside_retest_zone`, `volume_exceeded`, `broke_p0_stop`, `bearish_confirmation_bar`, `no_higher_low_close`），绝无滞后滚动等待直至符合条件的偷梁换柱行为。

## 3. 止损锚点 $P0$ 冻结性与订单合法性审计

### 3.1 止损锚点一致性核验
- **核验规则**：C1 和 C2 延迟入场时，初始止损锚点 $P0$ 必须绝对沿用原信号时刻锁定的值（$S - 0.1A$），严禁使用确认柱的最低价作为新止损点（否则会人为缩窄止损距离或放大头寸）。
- **审计结果**：
  - 在 `custom_stoploss` 及风控订单构建中，止损价严格取原候选事件的 `cand.p0_stop`；
  - 由于确认阳线上涨，执行入场价格通常高于原 C0 价格，导致实际初始风险距离 $R = P_{\text{entry}} - P0$ 扩大；系统头寸计算公式中以扩大的真实 $R$ 计算仓位，未发生风险低估。

### 3.2 价格破损拒单防御机制
- **核验规则**：若确认收盘后发生急跌导致执行价 $P_{\text{entry}} \le P0$，系统必须硬性拒单，严禁发出止损价高于或等于入场价的非法多头订单。
- **审计结果**：
  - `confirm_trade_entry` 钩子中部署了 `proposed_rate <= cand.p0_stop` 拦截网关；
  - 回测日志与 `audit_orders_*.csv` 中真实记录了该拦截行为，底层风控逻辑完整闭环。
