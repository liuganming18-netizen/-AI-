## 第一层：已有刚性验收门禁清单 (Mandatory Launch Gates)

以下 7 项门禁属于当前代码库中已查实、经隔离复现确证的硬性执行与架构缺陷。在后续专门的**代码修复工单**中未逐一修复、未提供回归证据前，全系统处于 🔴 **硬性阻塞** 状态：

### Gate 01: 跳空开盘成交价契约闭环
- **阻塞现状**：`paper_engine.py:2299` 在跌破止损时硬编码将 `raw_price = cur_stop` 传入平仓，开盘跳空暴跌被美化为完美止损价成交，低估单笔亏损达 5.2%（虚增净值 4.945 美元/单位）；
- **解除标准**：在 `check_position_exit_on_bar` 中补齐开盘跳空判定：
  ```python
  if bar_open <= cur_stop:
      raw_price = bar_open  # 跳空跌破按开盘价撮合并计不利滑点
  ```
- **验证证据**：在隔离测试中跑通跳空开盘用例，验证 `paper_fill` 中成交价等于 `bar_open * (1 - 0.0005)`；
- **状态**：🔴 **阻塞中 (BLOCKED)**。

### Gate 02: 中间十五分钟线正序遍历扫描闭环
- **阻塞现状**：`unified_runtime.py:2101` 与 `paper_loop.py:210` 使用 `ORDER BY open_time DESC LIMIT 1`，服务停顿或网络波动后仅读取最新 K 线，中间跌破止损随后反弹的 K 线被彻底漏检，发生穿透存活；
- **解除标准**：废除 `LIMIT 1`。持仓记录持久化 `last_checked_15m_open_time`，每次拉取大于上次检查时间且已闭合的全部 K 线，**强制按 `open_time ASC` 顺序遍历撮合**；
- **验证证据**：在存在触止损中间线且最新线反弹的隔离行情下，验证持仓在中间线处被准确平仓；
- **状态**：🔴 **阻塞中 (BLOCKED)**。

### Gate 03: 统一主循环挂载资金费计提与账户回撤熔断
- **阻塞现状**：`UnifiedRuntime.step_once` 与 `UnifiedExecutionDaemon.execute_cycle` 中，`accrue_funding` 与 `enforce_drawdown` 的调用次数为 **0**。模拟盘持仓存续期资金费从未主动计提，20% 账户级最大回撤熔断完全脱幅；
- **解除标准**：在 `step_once` 每个执行周期中，显式挂载资金费实际结算时钟检查（调用 `PE.accrue_funding`）与账户回撤熔断检查（调用 `PE.enforce_drawdown`）；
- **验证证据**：持仓跨越真实结算时间点后，`paper_funding` 产生计提行且扣减现金；净值回撤超 20% 时，账户状态变更为 `locked` 并生成清仓指令；
- **状态**：🔴 **阻塞中 (BLOCKED)**。

### Gate 04: 合约精度零兜底与异常阻断
- **阻塞现状**：`paper_engine.py:2404` 存在 `limits = contract_limits(symbol) or {"price_step": 0.01}`，当标的规格缺失时静默采用 0.01，违背零兜底准则；
- **解除标准**：彻底删除 `or {"price_step": 0.01}`。当 `contract_limits(symbol)` 为 `None` 时，显式返回错误或抛出 `ContractSpecMissingError`，阻断非法委托；
- **验证证据**：向引擎传入未配置标的，系统明确拒绝并返回拒单原因，账本无更新；
- **状态**：🔴 **阻塞中 (BLOCKED)**。

### Gate 05: 回测逐笔跟踪止损因果强隔离
- **阻塞现状**：`engine_adapter.py:146` 使用全量候选集合 `starts` 计算跟踪线，同标的后一笔持仓错误借用了入场前已闭合的 4h K 线（影响官方回测 3,346 笔持仓）；
- **解除标准**：跟踪止损通道数组构建必须与单笔持仓入场时刻逐笔绑定（Trade-by-trade binding），严禁同标的多笔交易跨生命周期借用；
- **验证证据**：单标的多候选回测在单笔独立运行时与联合运行时，输出的跟踪止损序列完全一致；
- **状态**：🔴 **阻塞中 (BLOCKED)**。

### Gate 06: 10 大反例用例库回归 100% 全绿
- **阻塞现状**：本工单已编制并验证了 CE-01 至 CE-10 隔离探针，但生产业务代码尚未完成上述修复；
- **解除标准**：在业务代码修复完成后，运行 `run_counterexamples_isolated.py`，10 大反例必须 **100% PASS**；
- **状态**：🔴 **阻塞中 (BLOCKED)**。

### Gate 07: 页面恢复信号与后端订单终态一致性
- **阻塞现状**：系统重启恢复候选时，后端通过跨库 ATTACH 终态拒单进行过滤，而前端若纯靠客户端 `isCurrentSignal` 会出现资格判断分叉；
- **解除标准**：前端展示有效交易信号必须完全基于后端权威 `/signals` 响应，严禁在前端脱离订单终态做独立推导；
- **状态**：🔴 **阻塞中 (BLOCKED)**。

## 第二部分：新增待审建议清单 (Pending Review Proposals)

以下三项指标是在系统设计中提出的高价值优化建议。**本清单郑重声明：以下建议目前仅为待审提案（Proposals），必须提交评审委员会讨论并出具正式审批决议后方可纳入验收体系，严禁将其作为已生效标准**：

### Proposal 01: 样本外前向实时检验 30 天建议 (Pending Review)
- **提案内容**：建议在全系统业务缺陷修复完毕后，启动为期不少于 **30 个连续自然日** 的实盘/模拟盘样本外前向盲测；
- **提出依据**：
  - 主流开源与商用大语言模型（GPT-4、Claude、DeepSeek 等）预训练语料已包含历史全量行情；
  - 传统历史切片回测极易受到“记忆泄露（Data Contamination）”影响，产生过拟合虚假有效性；
  - 只有在模型完全未见过的未来前向实时数据流中取得的超额收益，才能证明其真实推理有效性；
- **当前状态**：🟡 **待审建议 (Pending Review)**；
- **审批建议**：待评审委员会讨论是否将 30 天前向作为动态策略上线前的必要准入期。

### Proposal 02: 模型推理响应 P95 $\le 15$ 秒性能建议 (Pending Review)
- **提案内容**：建议将 AI 动态策略的决策推理服务等级协议（SLA）定为：P95 响应延迟 $\le 15\text{s}$，超时必须执行 Fail-Closed 安全拒单；
- **提出依据**：
  - 本交易系统运行于 15m 明细周期，新 K 线生成后至次根开盘仅有极短窗口；
  - 若模型推理耗时过长（例如超过 1 分钟），会导致订单严重滞后于行情，产生不可控的恶性滑点；
  - 15 秒是保证高可用与安全撮合的合理工程分界线；
- **当前状态**：🟡 **待审建议 (Pending Review)**；
- **审批建议**：待工程团队对模型 API 延迟分布完成实际压测后正式定标。

### Proposal 03: 净超额收益覆盖 3 倍 API Token 成本经济学建议 (Pending Review)
- **提案内容**：建议在核算 AI 动态组（Group C）相对于规则动态组（Group B）的有效性时，引入经济学硬约束：
  $$\Delta \text{Net Profit} = \text{Net Profit}_{\text{Group C}} - \text{Net Profit}_{\text{Group B}} \ge 3 \times \text{Cost}_{\text{API Token}}$$
- **提出依据**：
  - 商业量化系统不仅追求理论收益，更必须考量总体拥有成本（TCO）；
  - 调用外部大语言模型产生实际真金白银的 Token 费用；
  - 若 AI 策略微弱战胜简单规则，但其微额收益全部被 API 成本吞噬（甚至倒贴 API 费用），则在商业上毫无落地价值；
  - 设定 3 倍安全边际是量化工程界的通用审慎惯例；
- **当前状态**：🟡 **待审建议 (Pending Review)**；
- **审批建议**：待财务与量化委员会核算单次决策 Token 单价与预期交易频次后确定是否纳为验收门槛。
