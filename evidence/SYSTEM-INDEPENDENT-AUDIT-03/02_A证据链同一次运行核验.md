# 02｜交付证据链的「同一次运行」核验 —— **不通过**

> 工单原文：「独立确认 jobs_db 及全部运行路径隔离，**核对日志、PID、打开文件、源码版本属于同一次运行**。」
>
> 这一条是 A 的关键。能力成立（`01`），但**交付无法证明它在同一次运行里成立**。本文给三条独立证据。

---

## 1. 证据一：交付 JSON 自己记下了生产库被打开，却判「隔离完好」

`evidence/SYSTEM-ISOLATION-03/path_isolation_evidence.json` 的核心字段：

```json
"subprocesses": {
  "worker": {
    "pid": 25029,
    "opened_files": [
      ".../数据/任务队列/jobs.sqlite3-shm",
      ".../数据/任务队列/jobs.sqlite3.lock",
      ".../数据/任务队列/jobs.sqlite3",
      ".../数据/任务队列/jobs.sqlite3-wal"
    ],
    "visited_daily_paths": [],
    "isolation_intact": true          ← 问题在这
  }
},
"daily_paths_checked": [
  ".../数据/paper",
  ".../数据/市场数据/db/market_v2.sqlite3",
  ".../框架/backend/live/live_signals.sqlite3"
],
"isolation_verified": true
```

**worker 的 `opened_files` 里明明白白有 4 个生产任务队列句柄**（主库 + WAL + SHM + 锁），但 `isolation_intact` 仍是 `true`，`visited_daily_paths` 是空数组。

原因在 `daily_paths_checked`：**只有 3 项，没有 `数据/任务队列/`**。判定逻辑拿「打开的文件」去比对这 3 项，任务队列不在比对集里，于是「没命中」= 隔离完好。

这不是笔误，是**判定集漏项导致的假阳性**：

| 实际被打开的生产路径 | 在 `daily_paths_checked` 里？ | 结果 |
|---|---|---|
| `数据/paper` | 是 | 未命中 |
| `数据/市场数据/db/market_v2.sqlite3` | 是 | 未命中 |
| `框架/backend/live/live_signals.sqlite3` | 是 | 未命中 |
| **`数据/任务队列/jobs.sqlite3`** | **否** | **不参与比对 ⇒ 漏检** |

**工单要的正是「jobs_db 隔离」。而这份证据的判定清单里恰好没有 jobs_db 的位置。** 检查项与被检对象错位，等于没检。

---

## 2. 证据二：JSON 里的 PID/端口，不在测试日志里

两份交付文件描述的**不是同一次运行**。

| 来源 | 端口 | PID |
|---|---|---|
| `path_isolation_evidence.json` | **64293** | api **25026** / worker **25029** |
| `test_commands_and_outputs.log` Test 1 | 64313 | api 25121 / worker 25125 |
| `test_commands_and_outputs.log` Test 2 | 64319 | api 25157 / worker 25160 |
| `test_commands_and_outputs.log` Test 3 | 64323 | api 25201 / worker 25204 |

- JSON 的端口 64293 **在日志里零出现**；
- JSON 的 PID 25026/25029 **比日志里最早的 PID（25121）还小**；
- 日志里 6 个测试实例（64313/64319/64323/64330/64334/64346…）**没有一个**出现在 JSON 里。

也就是说：`path_isolation_evidence.json` 是**另一次独立运行**的产物，不属于 `test_commands_and_outputs.log` 记录的任何一次。而 `test_system_isolation_03.py` 本身**不产出**这个 JSON（全文无 `json.dump` 到该文件、无 `daily_paths_checked`、无 `isolation_verified`）—— 它来自一段**未交付的临时脚本**。

按工单「核对日志、PID、打开文件、源码版本属于同一次运行」：

| 要素 | 是否同一运行 |
|---|---|
| 日志 | ✗（JSON 的实例不在日志中） |
| PID | ✗（25026/25029 vs 25121+） |
| 打开文件 | ✗（JSON 记录的句柄来自另一实例） |
| 源码版本 | ✗（见 §3） |

## 3. 证据三：按交付的测试脚本 + 当前源码，Test 2 不可能通过

`test_system_isolation_03.py` 的 `setUp()`（第 49-68 行）**从不设置 `jobs_db`**，也**不设 `JOBS_DB` 环境变量**（只 `os.environ.pop("EFFECTIVE_VIEW")`）。

而 Test 2 的构造（第 180-191 行）：

```python
cfg = SM.ServiceConfig(
    port=self.port, py=self.py,
    is_isolated=True,
    market_db=..., live_db=...,
    paper_ledger_dir=..., paper_lock_dir=...,
    pid_dir=..., log_dir=...,
    check_collector=False
)                       # ← 没有 jobs_db=
```

用当前磁盘上的 `service_manager.py`（SHA `ddd02d32…`）跑这个构造，`resolve_paths()` 第 109-110 行必然把 `jobs_db` 记入 `missing`，第 116 行抛异常。实测（`out/A1_resolve_paths.json` → 场景 S1）：

```
已阻断  RuntimeError: 隔离模式缺少必要路径配置：['jobs_db']，拒绝启动，禁止退回日常目录
```

但交付日志写的是：

```
[Test 2] 子进程打开文件核验通过：API PID=25121, Worker PID=25125，均未访问日常路径。
Ran 5 tests in 7.005s
OK
```

**当前源码下 Test 2 必崩，日志却说通过。** 结论只有两种可能：

1. 日志是用**另一个版本的源码/脚本**跑出来的（源码版本不属于同一次运行）；
2. 运行时环境里存在 `JOBS_DB` 环境变量（但那样 `jobs_db` 会指向某路径，而 `configured_paths` 里却没有 jobs_db 这一项，同样矛盾）。

无论哪一种，都推翻「同一次运行」。并且能解释 §1 的现象：**如果当时 `resolve_paths()` 还没有 jobs_db 强校验，`is_isolated=True` 且 `jobs_db=None` 会走非隔离分支填充默认值 ⇒ jobs_db = 生产任务队列 ⇒ worker 打开生产库四句柄**。这与 JSON 里记录的实际句柄完全吻合。

## 4. 旁证：生产任务队列在隔离测试窗口内被写过

| 事实 | 值 |
|---|---|
| `数据/任务队列/jobs.sqlite3` mtime | **2026-10-23 14:33:46** |
| 隔离证据 JSON 时间戳 | `2026-10-23T06:36:01Z` = 北京时间 **14:36:01** |
| `test_commands_and_outputs.log` / `version_hash.txt` 生成时刻 | 14:36:30 ~ 14:37 |

生产任务队列在隔离测试进行期间（14:33）被写入。这与 §1「worker 打开生产 jobs 四句柄」互为印证：**那次运行确实写了生产任务队列**，只是检查清单没查它。

> 注：14:33:46 也可能来自其他并发任务。此条只作旁证，不作为单独定罪依据。

## 5. 交付日志的其他可疑点

| # | 现象 | 说明 |
|---|---|---|
| L-1 | `version_hash.txt` 只含 git status，`service_manager.py`/`test_system_isolation_03.py` 均为 `??` | 未跟踪文件无法用 commit 绑定；全文件无 SHA-256 |
| L-2 | `service_manager.py` mtime 14:52:44 > 交付 14:36:30 | 交付后 16 分钟被改，本次结论只能绑 SHA |
| L-3 | `test_commands_and_outputs.log` 6 个套件输出**首尾相接**，无任何命令起始/结束时间戳 | 无法判断是否为一次连续运行；`Ran 5 tests in 7.005s` 与后续用例输出之间无时间锚点 |
| L-4 | README 称「缺少 6 项必要路径」，代码实为 7 项（含 jobs_db） | README 与代码未机械对账 |
| L-5 | README 称「全量 100% 通过」，但 Test 2 在当前源码下必崩 | 见 §3 |

## 6. 这一节怎么影响总判定

| 工单要求 | 判定 | 依据 |
|---|---|---|
| jobs_db 隔离（能力） | **通过** | `01` A-1/A-2/A-3 独立实测 |
| jobs_db 隔离（交付证据） | **不通过** | §1 判定集漏项、§2 PID 不同批、§3 Test 2 不可能通过 |
| 全部运行路径隔离（能力） | **通过（有边界）** | `01` A-3；边界 = `MARKET_ARCHIVE` |
| 日志/PID/打开文件/源码 **同一次运行** | **不通过** | §2、§3、§4 三条独立证据 |

**一句话**：隔离这件事**现在是对的**，但交付**证明不了它当时是对的**，而且交付自己记录的画面（worker 打开生产库）与它自己的结论（隔离完好）**互相矛盾**。

按工单「阻止旧对象、漏检和证据拼接再次进入通过结论」——这一份正是「漏检 + 拼接」的样本：**漏检**（判定集无 jobs_db）+ **拼接**（JSON 与日志不同批）。A **不通过**。
