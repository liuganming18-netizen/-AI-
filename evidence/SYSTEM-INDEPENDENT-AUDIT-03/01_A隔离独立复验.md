## A-1｜`resolve_paths()` 五场景纯函数验证 —— **通过**

不启动任何进程，只构造 `ServiceConfig` 调 `resolve_paths()`。这样能干净地分开「校验逻辑」与「进程行为」。

| S2 | `is_isolated=True` + `jobs_db=生产任务队列` | **已阻断** `RuntimeError: 隔离模式严禁使用日常数据/状态目录：jobs_db -> '…/数据/任务队列/jobs.sqlite3'` | — |

### 边界：一个未闭合的泄漏点

| 项 | 实测 |
|---|---|
| `MARKET_ARCHIVE` 是否被 `shared_env` 设置 | **False**（`out/A3` → `环境注入检查`） |

4. `project_paths.MARKET_ARCHIVE` 默认值 = 生产 parquet（`project_paths.py:47`）。

## A-4｜子进程环境变量解析（4 组对照）—— 证明「隔离完全靠注入」

在**独立子进程**里 `import live_store`，看模块级常量解析到哪。这一步回答「模块级常量 `LEDGER_DIR = get_ledger_dir()` 到底靠不靠得住」。

| 组 | 注入内容 | `LEDGER_DIR` | `MARKET_DB` | 初始权益 |
|---|---|---|---|---|
| 组1 | 全量 6 项 | `<ISO>/paper_ledger` ✅ | `<ISO>/market/market_iso.sqlite3` ✅ | 5000.0 |
| 组2 | **漏掉 `PAPER_LEDGER_DIR`** | **`…/数据/paper`（生产）** ❌ | 隔离 ✅ | 5000.0 |
| 组3 | 裸环境（什么都不注入） | **`…/数据/paper`（生产）** ❌ | **`…/数据/市场数据/db/market_v2.sqlite3`（生产）** ❌ | 5000.0 |
| 组4 | 全量 + `PAPER_INITIAL_EQUITY=2000` | `<ISO>/paper_ledger` ✅ | 隔离 ✅ | **2000.0** |

**三点结论**：

1. **模块级常量在正确环境下解析正确**。`LEDGER_DIR` 虽是 `import` 时求值（`live_store.py:54`），但 `shared_env` 在 `spawn` 时就注入了，子进程 import 时已能看到 ⇒ 不构成缺陷。
2. **隔离没有第二道闸**。漏传 `PAPER_LEDGER_DIR` 就静默回落生产账本（组2），没有任何告警。这与 A-1 的 S3 是同一类问题：**校验只在 `ServiceManager` 层，子进程层无兜底**。风险在于任何绕过 `service_manager` 直接起进程的脚本（如手工 `python unified_runtime.py`）都会读生产账本。
3. **`PAPER_INITIAL_EQUITY` 是有效的独立通道**（组4 得 2000.0），与 `risk.initial_equity_USDT` 是否生效**是两件事**，不可混为一谈。

**`get_lock_dir()` 补测**（函数名是 `get_lock_dir`，不是 `_lock_dir`）：

```
PAPER_LOCK_DIR=/tmp/_a4_locks  →  get_lock_dir() = /tmp/_a4_locks
                                  status_file_path('3a') = /tmp/_a4_locks/paper_runtime_3a_status.json
```

正确读环境变量，隔离成立。

## A-6｜`stop()` 的可靠性 —— **不通过（环境依赖）**

这是本次独立复现出来的、交付没提到的问题。

三次起实例，三次 `stop()` 全部失败，报同一句：

```
[!] 拒绝停止未知 worker 进程：pid=28686, cmd=''，身份无法确认为本实例
[!] 拒绝停止未知 runtime 进程：pid=28791, cmd=''，身份无法确认为本实例
[!] 拒绝停止未知 API 进程：pid=27983, cmd=''，身份不匹配
```

**根因**：`stop()` 的身份核验依赖 `get_process_cmdline()`（`service_manager.py:223-233`），它 `subprocess.check_output(["ps", ...])`，异常时 `return ""`。

本沙箱 `ps` 被拒：

```
$ ps -p 27983 -o pid=,command=
(eval):1: operation not permitted: ps
```

⇒ `cmd` 恒为空 ⇒ `"unified_runtime.py" in cmd` / `"backtest_worker.py" in cmd` 恒 False ⇒ **拒绝停止自己刚启动的进程**，且**没有降级路径**（不会退而用 `lsof` 取可执行路径，也不会用 pidfile 里的启动时刻兜底）。

**这是环境依赖，不是产品在正常环境必然坏**。交付日志里 `[✔] 停止本实例 API 服务 pid=25121` 说明交付环境 `ps` 可用。

**但它是真实脆弱点**：

- 失败模式是「拒绝停止」，不是「误杀」—— 方向安全，但会留下孤儿进程；
- `ps` 不可用的场景不止沙箱：受限容器、`/proc` 未挂载、`ps` 被安全策略拦截都会触发；
- `service_meta` 里因此留下 `"state": "rejected_unverified"`（见 `out/A3` 的 `service_meta_65505.json` 快照），后续 `status()` 会把该服务报成异常态。

**处置**：本审计用兜底自清理（只杀本次自己起的 PID，SIGTERM→SIGKILL）保证不留残留，三次均清理干净（`out/A2`、`out/A3` 的 `兜底清理` 字段）。**这不改变 `stop()` 本身的判定**：在 `ps` 不可用环境里，它不通过。
