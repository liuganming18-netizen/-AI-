## 四、v2 仍存在的四条「通过但证据强度不足」

1. **第 1 项是恒真断言**。`assert p_info["unifiable"] is False`（L190）断言的是 `SC.get_execution_paths()` **自己返回的字段**——字段写 False 就通过，并未验证三条路径在入口/执行器/参数来源/费用口径上**实际**不同。它证明的是「元数据里写了不可统一」，不是「实际不可统一」。
   （另：该元数据把模拟盘费用口径写成 `slippage_each_side (0.0005)`，即 **5 bps**，而冻结值是 `slippage_bps=3.0`。这是**对方自己声明的口径**，不是测试夹具的临时值，属需要裁决的偏离。）
2. **第 5 项的 `config_source` 是文件名派生的标签，不是内容身份**。实测值 `frozen_view_view_a` / `frozen_view_view_b`——任何命名为 `view_*.json` 的文件都会被标成「frozen view」。真正可核验的是同一行的 `config_fingerprint`（`80943cb3bb88` / `84c6abd9871c`）。读 `config_source` 判「用的是不是冻结视图」会误判。
3. **夹具视图用的是非冻结风险参数**，与 `FT-VALIDATION-02` 冻结集不符：

   | 参数 | 套件模板 | 冻结值 | 一致 |
   |---|---|---|---|
   | `slippage_each_side` | 0.0005 | `slippage_bps=3.0`（0.0003） | ✗ |
   | `entry_participation_previous_15m_quote_cap` | 0.01 | 0.001 | ✗（10 倍） |
   | `max_positions` | 10 | `max_active_positions=3` | ✗ |
   | `single_name_notional_equity_cap` | 0.10 | `max_notional_per_position=0.30` | ✗ |
   | `gross_long_notional_equity_cap` | 0.80 | `max_total_notional=0.90` | ✗ |
   | `portfolio_initial_stop_risk_cap` | 0.05 | `max_total_risk_budget=0.015` | ✗ |
   | `initial_equity_USDT` | 5000 | `initial_equity=2000` | ✗ |
   | `risk_per_trade_equity_fraction` | 0.005 | 0.005 | ✓ |
   | `fee_each_side` | 0.0005 | `taker_fee_bps=5.0` | ✓ |

   模板已标 `production_config: false` / `purpose: contract_audit_testing`，作为契约测试可接受；**但它意味着「冻结参数集能否被正确加载」从未被验证**，且 slippage 与参与率被写成比冻结值更宽松的数。
4. **全套直接调引擎推进方法，共 7 处**（L246/328/360 `_register_pending`、L345/377 `advance_pending`、L393/452 `advance_position_trailing`）。按工单纪律「测试脚本不得逐周期调用执行方法」，本套件**只能作配置契约关（A 关）证据，不能作自动运行关（C 关）证据**。其中 `PL.PaperExecutionDaemon(arm).run_forever()`（L290）只测**失败路径**，且无超时保护——一旦配置自检不再抛错，`run_forever` 会进入无限循环把套件挂住，而不是失败。

（v1 里「容差 0.05 过松」这一条在 v2 已修：改为 `PE._round_protect_price(..., price_step)` + 容差 `1e-4`，且 A 组用 BTC 的 0.1 步进、B 组用 ETH 的 0.01 步进。此项撤回。）
