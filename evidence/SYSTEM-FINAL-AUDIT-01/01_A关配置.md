## 一、A1：缺配置仍然静默开仓（最小复现）

### 复现 1：视图文件不存在

```
EFFECTIVE_VIEW=/tmp/wx_final01/view_missing.json        # 该文件不存在
PE.approved_params() → source = fallback_frozen_v2_2_conservative
                       s=0.05  d=0.05  max_holding_hours=720  portfolio_initial_stop_risk_cap=0.03
PE.open_position("3a","BTCUSDT", atr=1.0, origin="replay")
   → 未拒绝：paper_pending(pending_id=1, status=pending, stoploss_s=0.05, trail_d=0.05,
                          config_fingerprint=NULL)
```

**责任位置**：
- `框架/backend/paper_engine.py` **L182-199** `FALLBACK` 字典里写死了 `stoploss_s: 0.05` / `trail_d: 0.05`；
- **L233** `p = dict(FALLBACK)` —— 缺配置时**从兜底起步**，不是从空起步；
- **L662-665** 登记前的「强校验」只在 `s_val is None` 或 `<= 0` 时抛错，而 `s_val` 来自 `params.get("stoploss_s")`，兜底永远给得出 0.05 ⇒ **校验形同虚设**。

**影响**：配置缺失或损坏时，系统不会停，而是按**另一套规则**交易：`max_holding_hours=720`（冻结视图 240）、`portfolio_initial_stop_risk_cap=0.03`（视图 0.05）。账本里唯一能看出异常的只有 `config_fingerprint = NULL`，而它同时是「旧 schema 没这列」的表现，**无法区分**。

### 复现 2：视图存在但缺 `stops` 段（更隐蔽）

```
EFFECTIVE_VIEW=/tmp/wx_final01/view_no_stops.json      # 有 execution/risk，没有 stops
PE.approved_params() → source = frozen_view_view_no_stops     ← 标签写着「冻结视图」
                       s=0.05  d=0.05  max_holding_hours=720  ← 实际来自 FALLBACK
→ 静默登记挂单 pending_id=2
```

比复现 1 更危险：`source` 字段自称读到了冻结视图，**`stops` 段实际是兜底值**。任何只看 `source` 是否含 `frozen_view` 的验收脚本都会判「配置正常」。

### 唯一被拒绝的场景

`stops.stoploss_s = 0`（显式非法）→ 抛 `missing_parameter_stoploss_s`，`paper_pending` 无新行。
⇒ 校验**只对显式 0/None 生效**，对「字段整体缺失」无效，因为兜底把它填上了。

### 反重力文档与本轮实测的差异

`SYSTEM-CLOSELOOP-05/01_最小代码变更与根因说明.md` R1 写：「登记前执行强校验，若缺失必需止损参数直接显式拒绝，绝不生成死单」。
本轮实测：**只在 s 显式为 0/None 时拒绝**；`stops` 段缺失时由 `FALLBACK` 补值后照常开仓。**声明强于实现。**

## 二、A2：身份只贯穿到两层，订单层是断的

`PRAGMA table_info` 实测（隔离库，已迁移的新 schema）：

| 层 | `stoploss_s` | `trail_d` | `config_fingerprint` | 判定 |
|---|---|---|---|---|
| `paper_pending`（挂单） | 有 | 有 | 有 | 通过 |
| **`paper_order`（订单）** | **无** | **无** | **无** | **不通过** |
| `paper_fill`（成交） | 无 | 无 | 无 | 不适用（成交挂 `position_id`） |
| `paper_position`（持仓） | 有 | 有 | 有 | 通过 |
| `paper_stop_history`（轨迹） | 无 | 无 | 无 | 不适用 |

工单要求「参数身份贯穿**挂单、订单、持仓和重启**」。现在订单行**无法自证**它属于哪套配置：只能 `paper_fill → position_id → paper_position` 反查，且一旦持仓被归档/清理，订单的配置来源就永久丢失。

**重启**这一项：持仓带身份列，守护重启后按持仓固化值继续（C 关实测止损 98.8 保持、轨迹 3 条不变）⇒ 重启路径本身**通过**，但它靠的是 `paper_position`，不是 `paper_order`。

另：复现 1 的挂单 `config_fingerprint = NULL` ⇒ 兜底路径连挂单层身份也没写进去。

## 四、这一关为什么不能放行 B、C

- A1 不通过 ⇒ 任何一次「自动成交成功」都可能是在**兜底参数**下成功的，成交价/止损/持仓时长都不可归因到冻结视图。
- A2 不通过 ⇒ 订单行无法自证配置，事后审计无法只凭订单复算风险。
- 因此 B、C 两关的结论**只能标注「在明确给定配置（exp1/exp2）下成立」**，不能推广成「系统配置关已通过」。

## 五、修好这一关的最小改动方向（不代改代码）

1. `approved_params()` 缺视图或视图缺 `stops` 时**返回显式失败**（或 `source=fallback` 且调用方必须显式允许），不要静默补 s/d；
2. `_register_pending` 的校验改为判「`source` 是否为冻结视图」+「s/d 是否来自视图」，而不是判 `s_val is None`；
3. `paper_order` 增补 `config_fingerprint`（订单行自证），或在订单行落 `position_id` 以便反查；
4. 兜底路径在账本里显式标注 `params_source=fallback`（可查询，不靠 NULL 猜）。
