> 复验对象：`框架/backend/unified_runtime.py`（37,025 B，10:48）+ `paper_engine.py` / `paper_loop.py`（10:17）

## 一、结论

| 条款 | 判定 | 依据 |
|---|---|---|
| **C0** 从统一入口启动即自动运行 | **不通过** | `unified_runtime` 无任何启动脚本拉起，只被 `api/routes.py` 读状态 |
| **C1** 两组配置均完成自动成交、上移、有持仓重启、退出 | **通过** | 两组各一笔：成交 → 上移 → SIGKILL 硬崩 → 新进程接管 → 退出 |
| **C2** 测试不调交易推进方法、不手工写成交 | **通过** | 测试脚本对 `advance_pending`/`advance_position_trailing`/`check_position_exit_on_bar` **0 次调用**；推进由 `UnifiedRuntime.step_once` 内部完成 |
| **C3** 可信行情 / 幂等 / 费用 / 账本 / 运行身份闭合 | **通过** | 6 项闭合全过（唯「视图权益=引擎权益」属 A-1 缺陷，非 C 关） |

**C 关：部分通过。** C1~C3 通过，**C0 不通过**——这是本轮唯一阻塞日常部署的项，与 AUDIT-05 的结论一致（「手起之后全自动」≠「启动系统就自动」）。

## 二、C1：两组配置真进程重启全序列

**与反重力 ITEM-2 的关键差别**：他们的「重启」是 `rt1.stop(); del rt1; rt2 = UnifiedRuntime(...)`，在**同一 Python 进程**内重建对象；我的 stage1 是独立子进程，跑完用 `SIGKILL` 硬崩（不走 `finally`、不 `release_lock`、不写 `stopped` 状态），stage2 是全新进程。

### 场景补注（我改了夹具，必须说明）

反重力场景的退出 bar 是 `low=48000`，只够打穿 A 组止损 50540；B 组止损 46816 **打不到**，原样跑 B 会停在 `status=open`、`exit_price=null`（我第一次跑就是这样）。为满足「两组配置均完成退出」，我为 B 组**追加了一根 15m bar**（`open_time = t_exit_cl + 15m`、`low=44000`）。这是**补场景，不是改产品代码**，且追加后 B 组的退出路径仍由引擎自己判定触发。

## 五、我怀疑过的一条洞，实测被否定

**假设**：`live_api.paper_order_post` L913 `origin = payload.get("origin") or "signal"`，`origin` 完全来自请求体；`paper_engine.open_position` L878 `is_replay = (origin in ("replay","test") or pending_id is not None)` ⇒ 客户端只要写 `origin="replay"` 并带一个真实存在的 `signal_uid`，就能指定过去时刻开仓（= AUDIT-01 的 P0 复活）。

**实测**（`queries/12_C关回填复现.py`，回填目标 = 90 分钟前，晚于 paper epoch 9 天）：

| 变体 | 请求 | HTTP | reason | 成交 |
|---|---|---|---|---|
| V0 对照 | origin 缺省 | 200 | `pending_future_fill` | 否 |
| **V1 回填** | `origin=replay` + `now_ms=requested_at=90 分钟前` | **409** | **`bar_after_attempt_clock_no_lookahead`** | **否** |
| V2 越界 | 早于信号 `available_at` | 400 | `request_before_signal_available` | 否 |
| V3 无信号 | `origin=replay` 但不给 `signal_uid` | 200 | `pending_future_fill`（被强制 `origin="manual"`） | 否 |

**结论：假设不成立。** 原因是 `open_position` 里还有第二道结构约束：`earliest_fill_ms = attempt_ms + delay_ms`，而 `bar_open >= earliest_fill_ms` 且要求 `bar_open <= attempt_ms`。只要 `signal_execution_delay_minutes > 0`（冻结配置 15 分钟），这两个条件**不可能同时满足** ⇒ 注入的过去时钟无法成交。AUDIT-01 的 P0 在结构上被关闭，不是靠参数检查。

我把这条写出来是因为：**我原本准备把它当重大缺陷报告，实测后必须自己撤回。** 假设不成立也是结论。

## 六、C 关的两个真实限制

1. **信号引擎不是 FT-LOW4H**。`unified_runtime.RealSignalEngine` 封装的是 `策略/WyckoffMaster/event_trend_v0_1/state_machine.py::EventStateMachine`（42 根 4h 箱体 → 1h 扫低 → 缩量回踩 → 放量突破）。反重力报告 §1.1 明说是「退役 `live_worker.py` 后的替代路径」。**执行侧**用的是 FT-LOW4H 的 `s`/`d`，但**信号产生侧**是 `WX_EVENT_TREND_V0_1`——而该策略 Gate 未过 / FAIL / PIT UNPROVEN。所以 C 关证明的是「**这套执行管线能自动跑通**」，**不能**外推为「FT-LOW4H 策略在真实信号下有效」。
2. **配置不是冻结口径**。反重力全链路用 equity 5000 / 10 仓 / 单名 0.10 / 总多 0.80 / 参与率 0.01 / 组合 0.05 / 滑点 5bps；我按冻结口径（2000 / 3 / 0.30 / 0.90 / 0.001 / 0.015 / 3bps）重跑，**结论不变**（仍全部跑通），说明管线不依赖这套数值。但「冻结参数集能否被正确加载」仍受 A-1 阻挡（权益字段不生效）。
