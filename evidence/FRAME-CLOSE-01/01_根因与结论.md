## 四、这个错误值是怎么来的（可证的部分）

### 4.1 报告声称的来源根本不成立

报告第 32 行声称该行是"核验 `evidence/FRAME-PIT-02/00_自哈希.txt` 与工作区实际代码文件"得来。但那份自哈希表**根本没有 `pit_guard.py` 这一行**——它只登记 PIT-02 自己的 21 个交付物（`README.md`、`flow_oi_four_groups_v2.py`、`logs/*.log`、`runs/*` 等），策略包代码一个都没有。

所以这句话在事实层面站不住：**这个哈希不可能是从那张表里读出来的。**

### 4.2 套件从来没有算过文件哈希

VERIFY-04 的验证套件里，第 122 行定义了 `file_sha256()` 函数，但**全文再无一处调用它**（只有定义，没有使用）。套件真正落盘的只有 `test_execution_summary.json` 和 CSV，两者都不含任何文件哈希字段。

也就是说：**报告里那张"被测文件哈希比对"表，10 个值全部是人工誊写进文档的，没有任何机器校验环节。** 手工誊写正是这个错误的产生位置。

### 4.3 同一份报告还有一处类似的口径夸大（附带发现）

报告与 01 文档都写"测试前后版本核对 100% 绝对一致（Pre-check 与 Post-check SHA 完全一致）""被测源码逐文件比对无偏差"。实际情况：

- 套件只比较 **Git HEAD**，没有比较任何文件内容；
- 原始日志第 4 行明写 `dirty=True`（工作区是脏的）；
- `pit_guard.py` 本身**未被 Git 跟踪**（`??`），HEAD 相同根本覆盖不到它。

**"HEAD 相同"不等于"文件相同"**，这条推论在本工程里是失效的。这也是为什么这次差异不能靠 Git 澄清，只能靠文件哈希澄清。

> 说明：这属于表述口径问题，不影响 25 项测试结论本身（见第 05 份文档：复跑同样 25 项全通过）。

## 五、VERIFY-04 实际测的是哪个版本

**答案：`79f60d11adc1aa63…`，就是当前这一版。** 五条证据：

1. **导入路径唯一**。套件第 44–52 行把 `策略/` 目录插入 `sys.path`，然后 `from WyckoffMaster.trading_core.pit_guard import ...`，加载的是工作区真实文件，不是副本。
2. **全工程只有一个该文件**。按文件名递归查找，`pit_guard.py` 只有 1 份（无 `.bak`、无 `.orig`、无快照副本）。
3. **字节码可佐证**。`__pycache__/pit_guard.cpython-313.pyc` 的文件头记录"源文件 mtime 21:54:53 / 大小 21,253"，与当前源文件完全一致；该字节码生成于 22:40，早于测试。说明测试时 Python 加载的就是这份源码。
4. **四份早于测试的独立记录**都是 `79f60d11`（见第三节时间线）。
5. **复跑可重现**。用当前字节重跑 VERIFY-04 套件，25 项全通过，且 25 项里有 **24 项的实测值逐字符相同**；唯一不同的是那条含时间戳的运行编号（`bt_20261018T191422Z_…` → `bt_20261019T012237Z_…`），属预期差异。

## 六、行为差异：无

由于 `cfadbf3d` 没有对应文件，**不存在"两个版本"可以对比**，因此谈不上行为差异。
