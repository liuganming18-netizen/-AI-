# 06 未覆盖路径与防护边界

## 一、防护到哪

**管住了**（有测试）：

| 场景 | 拦在哪 |
|---|---|
| 用未收盘的 1h / 4h K 线做决策 | `PitBridge.assert_candles_closed` → 抛 `PitViolation` |
| 读「起点等于决策时刻」的 5m OI 桶 | `extract_real_oi_growth_ex` 的 `available_at` 判据 |
| 读「已结束但尚未发布」的桶 | 同上（`declared_lag` 规则） |
| 发布时间缺失时静默填默认值 | `unproven` 来源只能拒用或判不合格，没有第三条路 |
| 取不到 OI 时外推 / 拿旧值凑 | `max_distance_ms` + 显式 `oi_*_too_far_*` / `oi_*_missing_*` |
| 帧里混进未来行 | `assert_frame_available` |
| 无状态机时默认合格 | `_build_run_files(sm_inst=None)` 强制 `qualified=False` |
| 热重启换回更宽松口径 | `export_state` / `restore_state` 带 `pit_mode` |

---

## 二、**没**管住的（必须如实说）

### 1 同进程仍可直接读文件

```python
df = pd.read_parquet("数据/市场数据/parquet/oi/binance/um/COTIUSDT/xxx.parquet")
# 上面这行不受任何约束
```

本框架提供的是「受控入口 + 违规可检测」，**不是**进程级隔离。
要真隔离只有三条路：独立进程 + 只读接口、文件系统权限、或者把数据访问层封成服务。
三条都不在本单范围内。

### 2 `load_symbol_data` 读的是整段历史

`EventTrendRunner.load_symbol_data` 会把该标的**全部** parquet 读进内存，
再按窗口切片。守卫是在「取用」时按 `available_at <= decision` 筛，
**不是**在「读取」时裁。

实测证据：COTIUSDT 一个 6 个月窗口的 run，
`pit_audit.oi_available_at_rows = 513164` —— 这是**全历史** OI 行数，
远超该窗口需要的量。

⇒ 所以「文件被读进内存」这件事本身不受约束。
如果你担心的是「未来数据根本不该进内存」，本单没做到。

### 3 数组本身不是可信边界

`process_1h_bar` 收到的 `oi_timestamps` / `oi_values` 是普通 ndarray。
如果调用方篡改（例如把 `available_at` 全设成桶起点），守卫会照它算。

`scripts/compare_old_new.py` 复现旧规则用的就是这个手法 ——
这既是对照工具，也证明了这个边界确实存在。

### 4 K 线的「本地摄取延迟」仍然未证

candles parquet 有 `available_at` 列但 **100% 为空**，`is_closed` 全为 1。
所以只能证明「K 线在 `close_time + 1ms` 已闭合」，
**不能**证明我们那一刻就收到了它。

`rule_candles` 的 note 里如实写了「本地摄取延迟未证」。
这是本框架目前能做到的最强表述，不得升级成「已证明」。

### 5 `oi_resonance_v1` 那条链没接

`trading_core/pit.py` 只被 `oi_resonance_v1/core.py:253` 调用，
它在缺 `oi_observed_at` 列时会把 `close_ms` 当成观测时刻（最乐观假设）。
本单没改它 —— 不在范围内（本单范围是 `WX_EVENT_TREND_V0_1` 与 FLOW-OI 四组实验的数据链）。

**风险**：如果以后有人用 `oi_resonance_v1` 那条链跑正式结果，
它仍然带着这个最乐观假设。已登记，未代改。

### 6 15m 撮合层没加守卫

`engine_adapter.py` 用「`close_time` 严格早于 15m `open_time`」判可用，
这个口径本身是对的，但它不是走 `pit_guard`。本单没统一它 ——
改了会影响撮合，超出「只负责 PIT 与数据访问」的边界。

### 7 没做「反向验证」

本单只证明「守卫能拦住已知的越界方式」，
没有做「穷举所有可能的越界方式」—— 那需要形式化或差分模糊测试，不在范围内。

---

## 三、一句话边界

> 守卫让**经过它的路径**无法读到未来数据，并让**所有路径**的违规结果
> 都能在 run 产物里被查到；它不能让同进程的任意代码读不到未来数据。
>
> 因此：**不得宣称已完全隔离。**

---

## 四、如果要把边界推进一步

按成本从低到高：

1. **数据访问层收口**：把 `pd.read_parquet` 全部换成 `pit_guard` 提供的
   `read_source(name, symbol, timeframe)`，并禁止其它模块 import pandas 的 IO。
   （成本：中；需要改 20+ 处）
2. **CI 静态检查**：在门禁里加一条「除 `pit_guard` 外不允许出现 `read_parquet`」。
   （成本：低；但只能防新代码，防不住 `__import__`）
3. **独立数据服务**：回放进程通过 HTTP/socket 向数据服务请求「截至 T 的数据」，
   数据服务自己按 `available_at` 裁剪。（成本：高；这是真正的隔离）
