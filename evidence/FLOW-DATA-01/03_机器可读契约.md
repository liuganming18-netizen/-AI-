# 03 机器可读字段契约

机器可读版：`contract/flow_fields.contract.json`（v1.0.0）。
本文件是它的中文解释与判定规则，两者冲突时**以 JSON 为准**。

---

## 一、四个核心量的公式（唯一定义）

| 量 | 契约字段 | 公式 | 单位 | 说明 |
|---|---|---|---|---|
| **主动净额（币）** | `taker_net_base` | `2 × taker_buy_volume − volume` | 基础资产 | = 主动买量 − 主动卖量 |
| **主动净额（额）** | `taker_net_quote` | `2 × taker_buy_quote_volume − quote_volume` | USDT | 同上，计价口径 |
| **买入占比（币）** | `taker_buy_share_base` | `taker_buy_volume / volume` | [0,1] | 分母 ≤ 0 ⇒ null |
| **买入占比（额）** | `taker_buy_share_quote` | `taker_buy_quote_volume / quote_volume` | [0,1] | 分母 ≤ 0 ⇒ null |
| **基础资产 CVD** | `cvd_base_cum` | `cumsum(taker_net_base)` 自显式起点 | 基础资产 | 跨断档**必须断开重开** |
| **报价资产累计净额** | `cvd_quote_cum` | `cumsum(taker_net_quote)` 自显式起点 | USDT | 与上面是两个量，禁止互替 |
| **归一化 CVD** | `cvd_quote_norm` | `cvd_quote_cum / Σquote_volume(同窗口)` | [−1,1] | 唯一可跨币种比较的形式 |

**币口径与额口径不等价。** 两者的差就是买卖均价差；同一个窗口里
`taker_buy_share_quote ≠ taker_buy_share_base`（实测 BTCUSDT 1h 上差到 0.3 个百分点）。
契约要求**两个都存、名字分开**，禁止只留一个再声称"通用"。

## 二、成交主动方向 ≠ 真实资金流入（这是本契约最容易被违反的一条）

| 概念 | 回答什么问题 | 数据来源 | 能不能叫"净流入" |
|---|---|---|---|
| 主动净额 / CVD | 这一段时间里，**谁先动手**（吃单方是买还是卖） | K 线 `taker_buy_*` | **不能** |
| OI 变化（币） | 场内**净开仓/净平仓**多少 | `sum_open_interest` | **不能** |
| OI 变化（额） | 上面那个 × 价格 | `sum_open_interest_value` | **不能**，且混入价格 |
| 真实充值/提现 | 有多少**钱从场外进来/出去** | 币安不公开 | 这才是"净流入" |

三条硬规则：

1. **`taker_net_*` 不得命名为 inflow / net_flow / 资金流入。** 它只表达主动方向。
2. **`delta_oi_quote` 不得命名为资金流入。** 恒等式 `1+Δ额 = (1+Δ量)(1+Δ价)`，实测残差 ~1e-16 ⇒ 名义额变化 = 数量变化 + 价格变化，价格涨 10% 就会让"名义额涨 10%"而没有任何新钱进来。
3. **`net_external_flow` 在契约里状态是 `UNAVAILABLE`。** 不许用上面任何一个派生量顶替。若下游一定要"资金流"这个词，只能写成"主动方向净额"或"场内净开仓"。

> 佐证：BTCUSDT 2026-09 的 24h 分解里，Δ名义额 与 Δ数量 的相关系数 0.83、与**价格收益率**的相关系数 0.77；
> UNIUSDT 分别是 0.84 / 0.91；LPTUSDT 0.95 / 0.83。名义额变化主要由价格驱动，拿它当资金流会系统性误判。

## 三、零分母 / 缺失 / 断档

| 情形 | 处理 | 禁止 |
|---|---|---|
| 分母 = 0 或 < 0 | 结果 `null`，写 `reason` | 加 epsilon（`+1e-8`）把 0 分母变成有效值 |
| 上游字段为 NaN | `null`，写 `reason` | 填 0、ffill、插值 |
| 上游给出 `sum_open_interest = 0` | 视为**缺失**（OI 不可能真为 0） | 当成真实 0 参与变化率 |
| 断档（间隔 > 1.5 × 周期） | 滚动/累计类指标置 `null` 并 `gap=true` | 跨缺口继续累加 |
| 窗口内根数不足预期 90% | `null` + `partial_window=true` | 用不足的窗口算完当正常值 |
| 计算结果溢出（inf） | 置 `null` | 保留 inf 让它污染后续统计 |

**实测到的真实坑**：LPTUSDT 2026-09-12 21:05 有 `sum_open_interest = 0` 且 `value = 0` 的观测。
若按 `(x−0)/0` 算变化率会得到 inf；本轮做 OI 分解时正是因为这一行，相关系数直接算不出来（NaN）。
把它当缺失剔掉后，`corr(Δ额, Δ量) = 0.9528`。这就是"零值必须当缺失"的现场证据。

## 四、滚动窗口

1. **窗口一律用时间差定义**（`ts − 24h`），**不许**用"往前数 N 根"。原因：本机数据存在断档（metrics 2022 年整块缺失、funding 有 16 天级停更），数根数会悄悄把窗口拉长到几天。
2. 窗口必须**同时记录实际根数**（`window_bars`）与名义根数（`window_bars_expected`）。
3. 窗口右端**不得包含未收盘的 K 线**（见第五节）。
4. 累计类（CVD）的起点必须显式写进输出，不能隐含"从数据开头算"。

## 五、时间对齐（PIT）

| 数据 | 时间列 | 何时可用 | 契约规则 |
|---|---|---|---|
| K 线 | `open_time` | `close_time = open_time + 周期 − 1ms` | 只能用 `close_time < ts` 的 K 线 |
| metrics | `create_time` | 桶 `[T, T+5min)` 结束，即 `T+5min` | 只能用 `T + 5min <= ts` 的桶 |
| funding | `funding_time` | 该次结算发生时刻 | 只能用 `funding_time <= ts` 的结算 |
| 聪明钱 | 无上游时点 | 本机取回时刻 | 只能标 `local_fetched_at` |

**这条是硬约束。** 反重力当前实现取的是 `open_time <= ts` 的最后一根 —— 在 `ts` 恰好等于某根 K 线 `open_time` 时，那根 K 线**一根都没走完**。详见 `04` 的实测。

## 六、陈旧上限（超过即断档）

| 数据 | 上限 | 依据 |
|---|---|---|
| metrics 5m | 900 s | 3 个桶 |
| OI 5m | 900 s | 3 个桶 |
| funding | 该标的**自身**结算周期 × 2 | 4h/8h/1h 混合，禁止写死 8h |
| 聪明钱快照 | 600 s | 采集周期 300 s × 2 |
| K 线 | 2 × 周期 | 与反重力现用阈值一致 |

超限后：结果置 `null` + `stale=true` + `age_seconds`。
**不许**用更早的值顶替后仍标"新鲜"——实时快照层若沿用上一轮，必须带 `carried_over=true` 和该块自己的 `fetched_at`（现有 `public_extras` 已经是这个做法）。

## 七、PIT 假设（必须随结论一起披露）

历史数据只有**观测时间**，没有**发布时间**：

- K 线：档案本身就是收盘快照 ⇒ "收盘即可用"是成立的。
- metrics：`create_time` 是观测桶时间，币安**未公开**真实发布时点 ⇒ "桶结束即可用"是**乐观假设**。
- funding：结算时刻即公布时刻，基本成立。
- 聪明钱：连观测时间都没有，只有本机取回时间。

**披露要求**：任何用这些字段做的回测，报告里必须写一句
「metrics 按桶结束即可用处理，属乐观 PIT 假设，非严格 PIT」。
**不得**声称已完成严格 PIT；**不得**把该假设省略。

## 九、跨币种比较规则

只能用无量纲量：占比、`cvd_quote_norm`、各类比率、变化率。
**禁止**直接比较金额或币数（BTC 的 1000 万美元和某小币的 1000 万美元含义完全不同）。
小币的 OI 名义额受价格与合约乘数双重影响，`oi_quote / oi_base` 与收盘价最大差 10.4% ⇒ 小币上更不能用名义额做跨币种对齐。

## 十、契约自检清单（下游接入前必须逐条过）

1. 所有分母都做了 `<= 0 → null`，没有 `+1e-8`。
2. 所有缺失都是 `null`，没有 0、没有 ffill、没有跨断档累加。
3. K 线只用了 `close_time < ts` 的；metrics 只用了 `T + 5min <= ts` 的。
4. 币口径与额口径分开命名，没有互相替代。
5. 没有任何字段被命名为"净流入/资金流入/聪明钱金额"。
6. 滚动窗口用时间差定义，且记录了实际根数。
7. 报告里写了 PIT 假设那句话。
8. 聪明钱相关字段全部标为"仅实时"，没有混进历史回测。
