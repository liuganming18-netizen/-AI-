## 一、一句话结论

**重启会让状态不一样，根因不是 ATR 漂移，而是「重建窗口的起点决定了手里有没有一个更早建立的箱体」。加深窗口永远收敛不了（实测 8→2→2→1，从不归零）；换成「所有重建都从同一个绝对时刻开始」之后，全池 526 币的重启差异变成 0，而且这个 0 是构造上成立的，不靠深度凑。**

---

## 二、问题长什么样

生产重启做的事是：丢掉内存里的状态，按「截止时刻往回看 W 小时」把状态重放出来。

问题就出在这个「往回看 W 小时」：

- 箱体是**相位周期**的东西（7 天箱体 + 24h 冷却）；
- 起点往前挪一天，窗口里「第一个够格建档的 4h 收盘」就换了一根；
- 那一根被谁吃掉，会一路决定后面所有箱体、扫低、回踩的归属。

所以同一份行情、同一个截止时刻，只是起点不同，两个引擎的箱体序列就整体错位。

**关键澄清（本轮实测）**：这**不是** ATR 数值漂移。对 6 个分歧币逐根 4h 比 `last_atr`，最早数值分歧全部为 `None`（一根都不差）。分歧是「决策层」的：同一根 4h 上，一个引擎手里已经有 10 月 15 日建立的箱体，另一个还停在 IDLE。

## 三、为什么「把窗口加深」这条路走不通

全池 526 币、同一截止时刻，只改重放深度，看相邻两档之间有多少币的**有效状态**变了：

| 相邻档 | 有效状态变了的币数 | 迁移数变了的币数（不并入状态） |
|---|---|---|
| 1160h → 1800h | **8** | 518 |
| 1800h → 2400h | **2** | 518 |
| 2400h → 2880h | **2** | 508 |
| 2880h → 3360h | **1** | 505 |

- 有效状态 = 阶段 / 箱体身份 / 箱体高低 / 扫低 / 回踩 / 冷却；
- `n_transitions` 与 `candidate_ids` **单列**，因为按构造它们随深度单调增长，不是状态；
- **`stable_from_hours = None`** —— 不存在「再深一点就稳定」的那个深度。

> **更正一条旧结论**：上一轮曾得出「D\* = 1800h 之后稳定」。那个结论是错误口径的产物——它把 `n_transitions` 和候选日志一起算进了「状态差异」，所以数字看起来收敛在某个点。本轮把这两项剔出去之后，真实有效状态差异是 8→2→2→1，**从不归零**。两套结果都留在 `out/02_深度敏感性.json`（旧口径）与 `out/02_深度敏感性_effective.json`（新口径），不删。

> **关于「深度是不是单一变量」**：`02` 的读入天数是**固定 190 天**（不随深度变），所以这一组里「深度」确实是唯一被改的变量，ATR 预热长度不变。这一点与 `03` 不同（`03` 的读入天数按深度裁），已在 `03` 里单独说明。

结论：**这条路在原理上就是死的**。只要地板跟着截止时刻滑动，差异就永远存在。

## 四、真正的解法：绝对锚点

不再「往回看 W 小时」，而是：**所有重建都从同一个绝对时刻开始**。

- 锚点存在 live 库里（`live_run.state_anchor_ms`），**首次运行落一次，之后永不后移**；
- 之后无论什么时候重启，地板都是这个锚点，与「当前截止时刻」无关；
- 于是重启和持续运行走的是**完全相同的行情序列**，终态逐币恒等 —— 这是构造上成立，不依赖深度够不够。

有一个必须同时成立的条件，否则锚点会失效：**读入起点也必须绝对固定**。如果读入起点还跟着截止时刻走，两边的 ATR 预热长度会差几根 4h，末位 ATR 不同，临界币的建档/冷却就会翻转。实测这个坑真实存在（`EDUUSDT`、`TAKEUSDT`）。

### 锚点必须「明显更早」才有验证力度

第一版验证用的是 `--anchor-hours 2880`，也就是锚点 = 截止 − 2880h，而 `replay_ms` 恰好也是 2880h。这意味着**锚点地板和相对窗口地板几乎重合**，0 差异可能只是「两条路本来就走同一条线」，证明不了锚点起了作用。

所以补了一组 `--anchor-hours 4000`：

| | 地板时刻 | 与相对窗口地板的关系 |
|---|---|---|
| 相对窗口（2880h） | 2026-06-25T06:59 | 基准 |
| 锚点 2880h | 2026-06-27T06:59 | **几乎重合（验证力度弱）** |
| 锚点 4000h | 2026-05-11T14:59 | **早 44.7 天（验证力度足够）** |

只有 4000h 那一组的 0 差异，才算「锚点把两条路钉在同一序列上」的证据。

### 我在这轮里犯过的一个错（如实记录）

第一版写的是 `floor = min(upto - replay_ms, anchor)`，本意是「锚点只让地板更早」。这是错的：

- `upto - replay_ms` **本身仍随 upto 滑动**；
- 只要它比锚点更早，地板就还是跟着 upto 走。

实测后果（同一份行情、同一锚点 `2026-06-27`）：

| | 连续推进（从 10-21 起） | 现场重建（@10-25） |
|---|---|---|
| 实际地板 | 2026-06-23T03:59 | 2026-06-27T03:59 |
| 喂入 4h 根数 | 785 | 761 |
| 第一根迁移 | 07-19 建档 | 07-23 建档 |

差 24 根 4h = 4 天，正好等于两个起点的时间差。**多 24 根就多一次建档机会**，于是迁移流水整体错位，`05` 一次性报出 35,247 项「判据指标不符」。

修正后：地板恒等于锚点，两边 `atr_bars_seen` 都是 760，迁移流水 **28/28 逐条精确匹配**。

> 这条值得单独记住：**错位会伪装成大规模不一致**。看到「几万项不符」先别急着找策略问题，先确认两边是不是在同一根 K 线上比。

### 又一处测量口径缺陷：`init == end` 时没有 advance

本单在并行核查中（`SIGNAL-CLOSURE-06-R1`）指出：`prod_session` 在 `init_ms == end_ms` 时**完全跳过 `step()`**，而 `bootstrap` 只按 **4h 收盘**驱动 `process_market`。后果是最后一根 4h 之后已经闭合的那几根 1h **从来没被喂进状态机**（实测差 3 根：A=2874 / B=2871）。

这会同时污染两个地方：

- `restart_state_change_at_Tr` 里的「现场重建」那一侧（`sess(Tr, Tr)`）；
- `05` 里 R 侧（现场重建）与 L 侧（逐 1h 推进）本来就不对称。

修正：`prod_session` 增加 `force_step`，在 `init == end` 时显式补一次 `step(end_ms)` —— 生产 `run_forever` 每轮都会 `step(now)`，所以「重建」之后必然再走一步，回放要等价就必须补上。

**并且加了自证**，否则「0 差异」可能只是因为两边都没处理到那几根 1h：

- `03` 记录两边 1h 处理根数的最小值并要求 `n_1h_equal`；
- `05` 把 `n_1h_processed` 纳入比对字段，不等就会被算成状态差异。

修正后 `05` 仍是 0/288，且 `n_1h_processed` 参与比对仍为 0 差异 ⇒ 这个 0 是**构造性**的，不再靠运气。

> 候选复现这里也有一个坑值得记：候选的 `snapshot_time_ms` 是**1h 收盘**（如 07:00），而 `bootstrap` 以 4h 收盘为驱动单位。直接拿 07:00 当重建截止，它所属的那根 4h（04:00–08:00）还没闭合，扫不到这根 1h，候选当然不出现。正确做法是从「最近一个 ≤ 快照的 4h 收盘」bootstrap，再逐 1h 推进到快照时刻——既不引入前视，又覆盖 1h 判定。修正后复现率从 1/2 变成 2/2。

## 八、边界与未解决

1. **锚点会让首次启动变慢**：锚点在 2026-06-27，距现在 120 天，首次 bootstrap 要重放 120 天数据。这是「构造性恒等」的代价，不是缺陷。
2. **锚点对不同币的可达性不同**：`AIGENSYNUSDT` 只有 178.7 天历史（晚上市），锚点落在它的历史范围内但更早的部分拿不到。这会让它的重放长度短于其他币，已在逐币表里如实体现。
3. **深度不收敛这个结论本身是重要的**：它说明只要不用绝对锚点，就永远存在差异。任何「把 W 调大一点就好了」的方案都不成立。
4. **本单没有产生新的自然候选**：全池 46 个候选全部是历史回放产物，且全部早于 paper epoch。这与 SIGNAL-HISTORY-FIX-01 的结论一致（机会稀缺，≈12 天/个），不是本单引入的问题。
5. **未做**：没有验证真实挂钟下的自动成交（需要等自然候选出现，可能数周）；没有动 `max_holding_hours=240` 这个「已取消但仍在参数里」的历史包袱（改了会让已登记实验身份漂移）。
6. **并行工单交叉影响**：本轮 06:45Z 的受控重启与 `PROJECT-REVIEW-07-R1` 的并发压测在时间上重叠。那次重启是本单主动执行的，不是压测导致的（pid `79140 → 2978` 与时间点完全对应本单的 `restart` 命令）。该工单因此作废的 1,016 条请求，归因应记为「外部主动重启」。
7. **本单脚本改过一次，部分早期产物绑定的是旧版脚本**：`03` 的 `D1160` / `D2880`（相对窗口两组）跑在补 `force_step` 之前。这两组的 `n_diff_vs_continuous` 不受影响（`R{k}h` 的 `Tr != T1`，本来就 advance，两边对称），但 `restart_state_change_at_Tr` 未采。锚点两组（2880h / 4000h）已用当前版本重跑，结论绑定当前 SHA。
