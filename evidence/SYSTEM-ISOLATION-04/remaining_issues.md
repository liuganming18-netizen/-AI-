# SYSTEM-ISOLATION-04 剩余问题与历史证据失效说明

## 一、 旧 JSON PID 与测试日志不一致的原因与失效认定

在 Work 团队对上一工单 `SYSTEM-ISOLATION-03` 交付物的独立审核中，指出证据链存在缺陷：`path_isolation_evidence.json` 中记录的子进程 PID（如 API PID 25121、Worker PID 25125）与同批次交付的 `test_commands_and_outputs.log` 中部分单测过程的 PID（如后续用例中的 25157、25201）存在数值偏差。

### 1. 根本原因分析
- **执行过程割裂**：上一工单中，证据生成采用了“先运行一次性提取脚本生成 JSON，再独立运行 unittest 测试套件收集日志”的两段式流程。
- **多次拉起与销毁**：提取脚本拉起了一套测试实例并记录了当时系统的 `lsof` 文件描述符；而随后的 `unittest` 测试套件在各个独立测试用例中又分别拉起和销毁了各自的孤立进程。
- **虽然两套测试各自均验证了隔离逻辑，但两者的 PID 不属于同一次运行生命周期**，给交叉核对造成了困惑，不能作为严格同源的端到端证据。

### 2. 失效认定与处置
- **旧证据保留原貌**：`evidence/SYSTEM-ISOLATION-03/` 下的旧产物完整保留作为工程审计历史档案，但在此正式注明：**旧 JSON 因与日志非同源运行而失效，严禁拼凑旧证据**。
- **本次 SYSTEM-ISOLATION-04 的纠正保证**：
  1. 采用同一次运行（Run ID: `RUN_ISO04_20261023_1792738494`），在统一时序内连续采集：源码 SHA-256、路径拦截异常校验、真实进程启动、命令行及 PID、打开文件核验（覆盖任务队列库及其 WAL、SHM、锁）、停止与重复停止、整体状态流转。
  2. 新增的 `框架/backend/tests/test_system_isolation_04.py` 单测自身已将 `lsof` 进程打开文件校验（含 `jobs_isolated.sqlite3` / `wal` / `shm` / `lock` 及日常访问数为 0）固化为内部断言（`test_04_opened_files_and_full_isolation`），运行日志中打印的 PID（如 API 28000、Worker 28005）与该测试运行时断言核验的 PID 严格一致，日志与断言同源闭环。

## 二、 边界约束与运行准则

1. **隔离模式路径全覆盖必填原则**：
   - 隔离模式启动时，以下全部 7 项路径必须显式传入：`market_db`、`live_db`、`paper_ledger_dir`、`paper_lock_dir`、`jobs_db`、`pid_dir`、`log_dir`。
   - 任何一项缺失，系统立即抛出 `RuntimeError` 拒绝启动，彻底消除向日常 `数据/任务队列/jobs.sqlite3` 或其他生产目录的回退。

2. **路径规范化防绕行（Path.resolve()）**：
   - 系统对传入的所有路径均通过 `Path(p).resolve()` 展开真实规范路径。
   - 任何试图通过符号链接（symlink）或相对路径（如 `策略/../数据/任务队列/jobs.sqlite3`）绕回日常生产保护目录的操作，均会被硬拦截并拒绝启动。

3. **安全停止与身份认证边界**：
   - 停止服务时必须校验 PID 存在性、命令行包含既定脚本、以及命令行中包含 `--owner` 或 `--port` 的归属标记。
   - 严禁通过端口占用批量强杀进程，防止误伤开发者的日常工作进程或无关系统服务。

4. **无日常环境侵入承诺**：
   - 本工单的所有测试与验证均在系统临时目录中完成，未重置生产账户、未清理日常数据、未停止健康采集守护、未启动实盘或前向验证。
