## 三、盘上有图但时间错位（83 个拒收案例）特别核查

在默认目录 `runs/` 下原本有 `chart.json` 的 729 个运行中，进一步排查发现了一类严重的历史污染遗留：
- **错图数量**：**83 个运行**；
- **错图特征**：图表中的 `window` 被写死为固定的 `2024-01-01 ~ 2024-06-30`，而这 83 个运行的真实交易发生在 2021 ~ 2023 年（其账本中的 89 笔真实成交里有 85 笔落在图表外部）；
- **历史成因**：早期读接口在遭遇缺图时，使用了硬编码的写死窗口重建，并使用 `S.write_chart` **反向覆盖写回了磁盘**（即读接口产生了不可逆的写副作用）；
- **本工程处理契约**：
  - 后端接口激活 `_chart_window_reject_reason(run_id, chart)`：**盘上图表时间窗口与本 run 自身真实窗口偏差超 1 天的，一律拒收！**
  - 拒收后自动转入 `_fallback_chart_cached`，以本 run 自身真实时间窗口从 parquet 动态重建正版 K 线；
  - **绝不回写盘上**，run 目录保持只读；
  - 界面图表打上 `非原始 chart.json · 盘上图表窗口不符已被拒收` 警示徽章，彻底避免错图误导。

## 四、结论与处置方案

1. **源数据真实性保全**：全池 2125 个运行中，**真实缺少原始 K 线的运行为 0**；全部 464 个运行均具备完整、真实的底层 15m/1h/4h parquet 数据。
2. **拒绝伪造数据**：界面对于 464 个缺失静态 `chart.json` 的运行，按真实窗口动态读取底层行情，并在 UI 与图表元数据中显式标注 `derived_from: 读时重建 · 非原始 chart.json`。
3. **保持证据库只读**：读时动态重建的数据仅保留在内存 LRU 缓存中（TTL 300s），绝不改写 `回测日志/` 目录下的任何历史文件。
