# 04 字段语义表｜现实时间口径下的每个时刻到底指什么

- 工单：SIGNAL-NOW-01-WORK
- 生成时间：2026-10-28（北京时间）
- 数据来源：`baseline/paper_3a_snapshot.sqlite3`（WAL 一致性快照）+ `框架/backend/paper_engine.py` 源码 + `out/02_test_probe_succ_溯源.json`
- 用途：本单所有判断都建立在「哪个字段是真实世界发生过的时刻、哪个字段是事后回填的记账值」之上。这张表把每个字段钉死，避免把记账值当成现实时刻。

## 一、三个水位（epoch）——只用于「历史恢复/筛选」，**不决定当前入场时间**

| 字段 | 值（ms） | UTC | 语义 | 现实时间口径下能不能当入场时刻 |
|---|---|---|---|---|
| `paper_epoch_ms` | 1791939600000 | 2026-10-14T01:00:00Z | 纸面账本的起算纪元 | **不能**。它只回答「早于这个时刻的信号一律不接」 |
| `live_start_ms` | 1792748844240 | 2026-10-23T09:47:24.240Z | 实跑身份起点（01 单受控生效那一刻） | **不能**。同上，只是准入门槛 |
| `state_anchor_ms` | 1782542715686 | 2026-06-27T05:25:15.686Z | 结构/状态机历史重建的锚点 | **不能**。只用于把历史结构算出来 |

派生：`L.effective_floor_ms() = max(live_start_ms, paper_epoch_ms) = 1792748844240`。

**本单修正的一处口径**：`unified_runtime.py:1069` 原用 `L.get_paper_epoch_ms()` 拼「早于纪元被拒」的文案，与真实门槛 `effective_floor_ms()` 差 9 天 8 小时（10-14 vs 10-23）。**只改文案取值，不改判定逻辑**，避免拒绝原因指向错误的水位。判定本身一直用 `effective_floor_ms()`，未受影响。

## 二、`paper_pending`（挂单）——现实时间语义的核心

| 字段 | 语义 | 现实时间口径下的正确读法 |
|---|---|---|
| `event_time` | 信号**确认**的那根 bar 的时刻（该 bar 收盘、结构成立） | 这是机会在现实世界第一次「已知」的时刻。**不是**入场时刻 |
| `available_at` | 该信号所依赖行情数据的可得时刻（PIT） | 现实里「这个信息什么时候能被看到」。为 `NULL` = **无法证明当时可得**（研究行全为 NULL） |
| `requested_at` | 本次挂单被创建时写入的墙钟 | 创建时刻，会被后续重放覆盖语义（见 `first_request_ms`） |
| `first_request_ms` | **首次**请求墙钟，`paper_request_anchor` 用 `INSERT OR IGNORE` 只落第一次 | 唯一能代表「我们第一次想下单」的现实时刻。**不能用它给旧信号续期** |
| `earliest_fill_ms` | 允许成交的最早时刻 = `order_request_ms + 15 分钟` | 派生量。`order_request_ms` 的定义本单改了，见下 |
| `epoch_ms` | 建单时的准入水位快照 | 审计用，不是时间 |
| `created_at` / `resolved_at` | 行创建墙钟 / 出结果墙钟 | 真实发生过的现实时刻 |
| `status` | `pending` / `filled` / `rejected` / `expired` | — |
| `reason` | 拒绝/过期原因码 | 本单新增 `fill_point_closed_before_process_start` |
| `bar_open_time`（在结果里回带） | 实际取价的那根 bar 的开盘时刻 | **不是**成交时刻 |

### `order_request_ms` 的定义（本单 C1 修正）

```
改前：order_request_ms = max(event_time, available_at, first_request_ms)
改后：order_request_ms = max(event_time, available_at)   # 两者皆空（手工请求）才退回 first_request_ms
```

改前那个 `max(..., first_request_ms)` 的效果：**任何一个旧信号，只要今天第一次被请求，执行点就被推到今天**。它让「4 天前的确认」合法地变成「今天的入场」，正是用户口径明确禁止的「按历史时间」。

## 三、`paper_fill` / `paper_position`——哪个是现实时刻，哪个是回填

| 字段 | 语义 | 现实时间口径下的正确读法 |
|---|---|---|
| `fill_ts` | 成交记账的墙钟（真实发生过） | **唯一能代表「钱在现实里什么时候动的」** |
| `entry_ts` | 入场时刻，**恒等于 `bar_open_time`** | **回填值**。它写的是「我们假定自己在 bar 开盘时就进了」，不是现实 |
| `bar_open_time` / `bar_close_time` | 取价 bar 的开盘/收盘 | 取价依据 |
| `raw_price` | 该 bar 的 `open`（未计滑点） | 行情原值 |
| `fill_price` | `raw_price` + 5bps 滑点 + 一个价格步进 | 记账成交价 |
| `qty` / `notional` / `fee` / `slippage_cost` | 数量/名义/手续费/滑点成本 | 派生 |
| `planned_risk` | 开仓时的计划风险额 = `initial_equity × risk_budget_per_trade`（含倍数） | 不受本单影响 |
| `initial_stop_price` | 入场即定的初始止损 | 本单未改 |
| `first_request_ms` / `epoch_ms` / `config_fingerprint` | 溯源用 | — |

### 硬结论（`known_gap`，已写进 `FILL_POLICY`）

`paper_fill` 只在 bar `is_closed=1` 之后才取得到 ⇒ **执行动作从未在 bar 开盘时刻真实发生过**。账本里 `entry_ts` 一定早于 `fill_ts` 15～30 分钟。这是现行成交模型的结构性事实，不是 bug，但**不能把它讲成「当时就成交了」**。

要做到「现实执行点成交」，需要在 bar 开盘瞬间拿实时报价——本单**不自选**新成交模型（工单禁止新增策略/改成交模型），只如实标注为已知缺口，交主代理裁决。

- A 闭 bar 规则本身成立 —— 成交价确实取自已闭合 bar 的 `open`；
- B **属收盘后回填开盘价** —— `entry_ts` 比真实处理时刻早 15.245 分钟；
- C **信号已失效** —— 按现实口径应在 4 天前就过期，现被续期成今天入场。

**附加 PIT 疑点（未裁决）**：行情库该 bar 的 `available_at = 1793118616461`（16:30:16.461Z），**晚于 `fill_ts` 1.733 秒**。即「记账时刻早于该 bar 数据自报可得时刻」。本单只记录，不据此改判，也不回写任何行。

**禁语**：不得称其为「自然策略成交」「自然候选闭环」「成交闭环已打通」。它是外部测试探针所建，本单只接管、不追溯、不删除、不强平。
