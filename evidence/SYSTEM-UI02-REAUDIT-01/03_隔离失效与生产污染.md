## 一、结论先行

**UI-02 宣称的「完全独立的测试沙盒」只隔离了一半。**

| 链路 | 是否隔离 | 原因 |
|---|---|---|
| 信号（`live_signal`） | **是** | `live_store.LIVE_DB = os.environ.get("LIVE_DB", …)` 走环境变量，脚本设了 `LIVE_DB` |
| **账本（持仓 / 已实现 / 止损 / 权益）** | **否** | `live_store.LEDGER_DIR = get_ledger_dir()` 是**模块级常量**，只认 `PAPER_LEDGER_DIR`；脚本**没设** |

⇒ 报告 §7 关于「持仓」与「止损轨迹」的全部证据，**读的都是生产账本 `数据/paper/paper_3a.sqlite3`**，不是隔离库。

## 五、这解释了截图为什么会长这样

回到 `01_截图与操作覆盖复算.md` 里那几个「差异 ≈ 0」的现象，现在原因清楚了：

## 六、生产 locks 被写入假守护状态，且未还原

`test_system_ui_02.py` 第 305 行：

```python
lock_dir = BACKEND / "locks"          # ← 框架/backend/locks，生产状态目录
```

第 250–303 行的守护进程是一个 `python -c` 的 `while True` 桩，每秒往这个目录写两份 JSON，内容固定为：

```json
{"status": "running", "health": "ok", "blocked_reason": null, "pid": <自己>}
```

**它不调用 `unified_runtime`，不调用 `paper_loop`，不读行情，不撮合任何订单。** 交付自己的 `07_*.json` 也照实写了 `process_cmd: "python -c [daemon_worker_loop]"`。

### 6.1 当前残留状态（只读核验）

| 文件 | mtime | pid | status | PID 是否存活 |
|---|---|---|---|---|
| `框架/backend/locks/paper_daemon_3a_status.json` | 2026-10-23 12:12:41 | 13419 | **running** | **否（已退出）** |
| `框架/backend/locks/paper_runtime_3a_status.json` | 2026-10-23 12:12:41 | 13419 | **running** | **否（已退出）** |

**测试结束后这两份文件没有被还原或删除。** 现在生产环境里躺着两份「守护正在运行、PID 13419、无阻断」的状态文件，而 13419 这个进程早已不存在。

**后果**：任何人此刻启动生产前端，守护卡片会显示 `running / PID 13419 / 无阻断 · 正常流转` —— 一个死进程被渲染成健康状态。这正是上一轮 D-7 那类缺陷，但这次是**测试自己造成的**。

`07_守护进程真实运行与心跳证据.json` 还把这个路径写进了证据：

```json
"runtime_status_file": "/Users/boos/Desktop/威科夫因子共振趋势/框架/backend/locks/paper_daemon_3a_status.json"
```

⇒ **不是误写，是把「读生产状态目录」当成证据来源记录在案。**

## 七、关于「真实 PID 13419」这个卖点

报告 §1.1 说：

> 「守护 PID 与心跳**完全来自 OS 真实进程**（本轮验证真实 PID：`13419`，每秒真实推进 cycle 并写入心跳），经后端严格系统级存活探测（`os.kill(pid, 0)`）核验」

**这句话字面为真，但会误导：**

| 它证明了 | 它没有证明 |
|---|---|
| 存在一个真实的 OS 进程，PID 是 13419 | 这个进程是**执行守护** |
| 这个进程真的每秒写一次状态文件 | 这个进程做任何撮合、读任何行情、推进任何策略 |
| 页面能显示一个真实存在的 PID | 页面显示的状态**准确反映**系统真实运行状态 |

按工单第 5 条纪律：**桩进程写状态文件只证明「页面能渲染一个 PID」，不构成「执行守护在工作」的证据。**

## 八、违反的边界

工单明确要求「**不再用测试实例访问日常库**」。本轮核实的实际情况：

| 边界 | 是否被触碰 | 证据 |
|---|---|---|
| 读生产账本 | **是** | 持仓 / 已实现 / 止损 / 权益四项全部来自 `数据/paper/paper_3a.sqlite3` |
| 写生产账本 | **未发现** | 4 库 `paper_realized` / `paper_position` / `paper_stop_history` 行数与内容均为测试前状态（3 行 closed / 3 行 voided / 0 行止损） |
| 写生产 locks | **是** | 2 份状态文件被覆盖为假 `running`，PID 已死 |
| 写生产行情库 | **未发现** | 本轮未启动服务，未做核验；交付未声明是否触碰 |
| 读生产行情库 | **是**（推断） | 页面 9 列行情来自 `market_v2.sqlite3`，属只读，可接受 |

**「读」和「写」要分开说**：读生产账本不损坏数据，但**会让所有基于这些截图的结论失去隔离意义**——因为你无法区分「页面显示的是预置数据」还是「页面显示的是生产历史」。事实上，页面显示的全是生产历史。

## 九、为什么这一条必须在第二阶段之前解决

工单把「先独立确认路径隔离成立，再启动测试实例」放在第二阶段前置，是对的。原因在本轮已被证实：

1. 隔离不成立时，**测试数据根本没进页面**，截图看起来正常但证明不了任何事；
2. 隔离不成立时，**测试会顺手写脏生产状态**（locks 已被写），且没人会发现；
3. 隔离不成立时，**「三态覆盖」会退化成「同一张空图编三种说法」**，因为真实数据源里本来就没有那三种状态。

### 9.1 第二阶段启动前必须满足的最小条件（建议）

| # | 条件 | 验收方式 |
|---|---|---|
| 1 | `PAPER_LEDGER_DIR` 指向隔离目录，且**隔离目录内确有** `paper_3a..3d.sqlite3` | 进程内打印 `L.LEDGER_DIR` 实际值 + 目录列表 |
| 2 | `PAPER_LOCK_DIR` 指向隔离目录 | 同上 |
| 3 | 页面 DOM 里的持仓/已实现/止损**等于隔离库**，不等于生产库 | 双侧比对，任一侧不中即判隔离失败 |
| 4 | 生产 `数据/paper/*` 与 `框架/backend/locks/*` 的 mtime 与 SHA-256 在测试前后**完全不变** | 测试前快照 + 测试后复算 |
| 5 | 守护状态若要用桩，必须在报告里显式标为「桩」，且**不得写生产 locks** | 证据文件里写明 `is_stub: true` |

**在第 1–4 条通过之前，任何「重拍截图」都会重复同一次污染。** 所以本轮不重拍。

## 十、本项结论

| 子项 | 判定 | 依据 |
|---|---|---|
| 信号链路隔离 | **通过** | `LIVE_DB` 环境变量生效，清理操作打到隔离库（3→0） |
| 账本链路隔离 | **不通过** | `PAPER_LEDGER_DIR` 未设置，`LEDGER_DIR` 为模块级常量 ⇒ 读生产 |
| 页面持仓数据来自隔离库 | **不通过** | DOM「0 仓在持 / 3 笔已平」= 生产，隔离库 1 条 open 从未渲染 |
| 页面权益数据来自隔离库 | **不通过** | `$5,000.00` = `INIT_EQUITY` 常量（生产 `paper_account` 空表回落） |
| 页面止损轨迹来自隔离库 | **不通过** | 生产 `paper_stop_history` 0 行，隔离库 2 行未出现 |
| 未写生产账本 | **通过（未发现）** | 4 库行数与内容未变 |
| 未写生产 locks | **不通过** | 2 份状态文件被覆盖为假 `running`，PID 已死，未还原 |
| 守护进程是真实执行守护 | **不通过** | 桩进程，不调用 `unified_runtime`/`paper_loop` |
| 「真实 PID」证明力 | **不足以支撑结论** | 只证明页面能渲染一个真实 PID |
