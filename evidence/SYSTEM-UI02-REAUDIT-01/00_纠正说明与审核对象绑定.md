## 二、上一轮总览必须修正的判断（逐条）

上一轮 `evidence/SYSTEM-PARALLEL-AUDIT-01/00_总览与边界.md` 有 4 条判断需要修正。**旧报告原样保留，本节是增量纠正，不覆盖历史。**

### 2.1 D-2：从「页面白屏」降级为「后端接口 500」——我上一轮越界推断

| | 内容 |
|---|---|
| **上一轮原话** | 「D-2 高 `live_api.py:637` 只 catch `LedgerUnavailable`/`LedgerIdentityMismatch`，缺 live 库抛 `OperationalError` ⇒ 500」；并在 C 任务判定里把「缺库接口 500」当作「UI 硬崩」的证据 |
| **本轮核实** | 后端缺陷**成立**：缺 live 库时 `/api/v1/paper/accounts` 确实 500，异常未被捕获。**但「页面白屏」是推断，不是观察。** |
| **实际前端证据** | UI-02 在代理层对 `/api/v1/paper/accounts` 注入 HTTP 500 后，`state_position_failed.png` 与正常态**像素差异 23.52%**，且构建产物 `dist/assets/index-BCc0oEMd.js` 中存在文案「**持仓接口读取异常**」⇒ 页面渲染的是**红色告警框**，不是白屏 |
| **纠正结论** | **D-2 仍是一个有效的后端缺陷（缺库不降级、返回 500）**；但**不得**由「接口 500」推断「新版页面白屏」。要判定页面表现，必须有前端实际证据。 |
| **对旧结论的影响** | `SYSTEM-PARALLEL-AUDIT-01` 里 C2「UI 硬崩」的措辞**作废**；C2 不通过的实质理由应改为「缺 live 库时接口不降级」+「service_manager 无法隔离数据路径」两条，**不含白屏** |

**这条纠正的方法论意义**：后端返回码 ≠ 前端表现。中间隔着 fetch 封装、错误边界、组件降级三跳。跳过这三跳就是拿 A 的证据判 B 的结论。

## 三、本轮采用的判定纪律

1. **三态判定**：`通过` / `不通过` / `未验证`。**「未验证」不计入通过。**
2. **测试注入记录只证明页面功能。** 预置信号、预置持仓、`500` 注入、桩进程写状态文件——这些最多证明「页面在某种输入下渲染成什么样」，**不构成**「真实信号 → 成交 → 持仓 → 退出闭环」证据，也**不构成**策略有效性证据。
3. **空转成功不算闭环通过。** 本轮没有任何一次真实信号触发成交，所有持仓都是预置数据。
4. **数字必须能被脚本机械复算。** 本文件每个数字都对应 `queries/` 下脚本与 `out/` 下 JSON 的字段。
5. **不把局部通过升级为系统通过。**
