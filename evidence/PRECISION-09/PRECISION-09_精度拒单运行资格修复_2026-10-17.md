## 1. 根因

### 1.1 资格判定链：谁决定「这次运行算不算跑成功」


### 1.3 为什么会漏

出场三处是「失败即意味着仓位状态说不清」，所以当初一并写了无效标记；入场三处是「不成交就等于没发生」，看起来无害，于是只留了明细。但**「没发生」和「执行链路坏了」是两件事**：

- 精度拒绝入场 ⇒ 这条信号**本来该成交却没成交**，后续统计（胜率、盈亏、成交数）分母已经错了；
- 更糟的是它**看起来完全正常**：`trades_count=0`、`open_positions=[]`、现金原封不动、账本恒等成立，`run_valid` 还是 `true`。一批回测里混进这种 run，人工复核几乎看不出来。

## 2. 两类拒单的分界

### 2.1 判据

| | 执行有效性错误 | 策略/风控取消 |
|---|---|---|
| 含义 | 撮合层或合约规格层面这笔单**根本不成立** | 策略/风控**主动决定不做** |
| 典型 | 原价非正、步长非法、取整后 ≤0、数量 < minQty、名义额 < minNotional | 开盘跌回箱体、跳空过高、身份链不可解析、风控仓位为 0 |
| 是否判无效 | **是** | **否** |
| 为什么 | 这次运行的执行链路不可信，成交统计已经失真 | 这是规则要求的正常结果，判无效等于「只要有一次取消就宣布整次回测作废」 |

### 2.2 映射表（机器反查，不手抄）

`工具_20_映射表.py` 从代码里正则抓出 `fill.py` 的每个 `FillRejected("...")` 字面量和 `engine.py` 两处闸门的 reason，再逐条与人工判断表对账 —— 任何一条不一致直接报错退出。结果：

- **执行有效性错误 8 条**：`non_finite_or_invalid_price`、`nonpositive_raw_price`、`non_finite_or_invalid_price_step`、`invalid_price_step_nonpositive`、`nonpositive_or_nonfinite_entry_fill`、`nonpositive_or_nonfinite_exit_fill`、`qty_below_min_step`、`notional_below_min`
- **策略/风控取消 15 条**：`canceled_fell_back_into_box`、`canceled_gap_above_0.5a`、`candidate_identity_unresolved`、`candidate_symbol_mismatch`、`candidate_signal_bar_mismatch`、`invalid_signal_stop`、`nonpositive_qty`、`notional_cap_exceeded_zero_qty`、`duplicate_symbol_active`、`max_concurrent_trades_reached`、`open_gapped_beyond_stop`、`nonpositive_equity`、`zero_unit_risk`、`portfolio_risk_cap_exceeded`、`portfolio_margin_cap_exceeded`
- **本轮未归类 2 条**：`participation_volume_unavailable`、`participation_cap_zero_qty`

完整表（含产生位置、依据）见 `映射表_拒单分类.md` / `.csv`。

### 2.3 为什么不能「所有拒单一律判无效」

因为拒单表里 15 条是正常业务结果。最直接的反例就是工单点名的 `canceled_fell_back_into_box`：它是**规则本身要求的取消**（下一根开盘跌回箱体上沿以下就不做）。若一律判无效，任何一段回测只要出现过一次「开盘跌回箱体」，整次运行就会被宣布作废 —— 这会让 `run_valid` 变成「几乎永远为 false」的字段，等于自废这个判据。

### 2.4 未纳入的 2 条：为什么留白

`participation_volume_unavailable` / `participation_cap_zero_qty` 来自可选的参与率约束（`participation_rate`，**默认 None**）。它们既不是「价格/规格不成立」，也不是「策略主动不做」，而是**数据缺失时的 fail-closed**。本轮不擅自归类，分类器把它们标成 `unregistered`（不判无效），并在报告里点名留待单独工单 —— 因为一旦把它们判无效，所有没接成交量数据的回测都会批量转红，那不是本次修复该承担的改动。

## 3. 修改

### 3.1 新增 `策略/WyckoffMaster/trading_core/rejects.py`（142 行）

只做一件事：把「哪条原因该判无效」集中登记一次。

```python
EXECUTION_VALIDITY_REASONS = frozenset({...8 条...})
STRATEGY_CANCEL_PREFIXES  = (...15 条前缀...)   # 前缀匹配，兼容带括号实参的写法

def classify_reject(reason) -> str:             # execution_validity / strategy_cancel / unregistered
def is_execution_validity(reason) -> bool:
def mark_if_execution_invalid(invalid_reasons, stage, reason) -> bool:
    """执行有效性错误 ⇒ 追加 `<stage>:<reason>`；其余一律不写。幂等。"""
```

两个设计取舍：

- **用前缀匹配而不是精确集合**：`decide_entry` 的若干原因带实参（`canceled_fell_back_into_box (open=100.0 < H=101.0)`），精确集合必然漏。
- **未登记默认 fail-open（不判无效）**：新加的策略取消原因不会因为忘记登记而误杀整次运行。代价是「新加的执行错误可能漏判」，由两条测试兜底 —— 见 §5.3。

### 3.2 `engine.py`（净 +37 行，6 处）

| 处 | 改动 |
|---|---|
| 入场价格（原 452-462） | **新增** `mark_if_execution_invalid(..., STAGE_ENTRY_FILL, rej.reason)` |
| 入场数量（原 537-550） | **新增** `mark_if_execution_invalid(..., STAGE_ENTRY_QTY, "qty_below_min_step")` |
| 入场名义额（原 551-567） | **新增** `mark_if_execution_invalid(..., STAGE_ENTRY_NOTIONAL, "notional_below_min")` |
| 出场三处 | 把硬编码前缀 `f"exit_gap_fill_rejected:{...}"` 换成常量 `STAGE_EXIT_GAP`，**字符串逐字相同**（有测试钉死） |
| 全部六处 | `precision.rejects[]` 增加一个加性字段 `"class"`，便于逐条对账 |

`mark_if_execution_invalid` 同时做了**幂等去重**：坏数据可能在多根 bar 上重复触发同一原因，不让 `invalid_reasons` 无限增长。

### 3.3 `__init__.py`（+10 行）

按既有分层写法把 `rejects.py` 登记进包导出与分层注释，不改变任何既有导出。

### 3.4 为什么不是「在三处各写一行 append」

三行 append 也能让探针转绿，但那样「什么算执行错误」就散落在 6 个分支里 —— 这次的缺陷本身就是这么来的。集中一张表之后：新增原因必须显式登记，登记漏了有测试先红（§5.3），而不是等某天又出现「0 成交但 run_valid=True」。

### 3.5 明确**没有**动的东西

- ❌ 没接 R6（`price_step > raw_price`）、没接 R7（`fill ∈ [low, high]`）—— 那是 PRECISION-08 的 M1–M6，另行实施；
- ❌ 没改滑点（3bps）、没改取整方向（买 ceil / 卖 floor）、没改参考价来源、没改止损与跟踪止损；
- ❌ 没改风控（`risk.py` 未变，哈希一致）、没改策略参数（`config.py` 未变，哈希一致）；
- ❌ 没改 `fill.py`（未变，哈希一致）—— 分类表只读它的 reason 字符串，不侵入撮合逻辑。

**`oi_resonance_v1` 回测口径零变化**：`build_fill_adapter`（`execution.py:105-108`）构造 `SimulatedBarFillAdapter` 时不传 `strict`（默认 `False`），`_guard` 直接返回、不会抛 `FillRejected`；`build_core` 也不传 `instrument_specs`，两处数量闸门被 `if spec is not None` 跳过。所以本次修复对旧回测路径**不可能产生任何数值差异**。
