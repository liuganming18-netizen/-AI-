# SIGNAL-LINK-01 · 把信号接通（诊断 + 修复 + 可复算证据）

**结论先说（三句话）**

1. **链路是通的**——不是「以为通」，是用生产同一份代码在隔离环境里把
   `候选 → 落库 → 可执行扫描 → 挂单 → 成交 → 持仓` 五段全部跑通，**5/5 通过**，
   且生产库与账本逐字节未被写。
2. **「0 条信号」的真相是供给稀缺，不是故障**——全部可用历史（**47.12 天 / 526 标的**）
   只走出 **4 个候选**，平均约 **12 天/个**；这 4 个**全部早于**本轮 paper 启用时刻
   （`2026-10-14T01:00:00Z`），按纪律**不补开**。所以启动后几小时内必然是 0。
   这个节奏不是感觉，是可算的四层结果（见 §3.5）：

   - **条件相乘**：箱体→扫低 20.4% → 回踩 59.7% → 候选 1.00%，箱体→候选仅 **0.122%**；
   - **时间被箱体占满 93%**：平均 6.2 个箱体/标的 × 7 天 = 43.6 天，其中 79.6% 连扫低都没等到；
   - **回踩后 90% 死于跌破 `Lr−0.1A`**：`P0 = Lr − 0.1A` 离回踩低点只有 0.1 ATR，
     是规则的直接后果，不是缺陷；
   - **统计上还不确定**：只有 4 个事件 ⇒ 泊松 95% 区间 **4.6 ~ 43.2 天/个**。

   ⇒「约 12 天」只能当量级看，**不得当精确值**。

   **顺带回答「500 多个币为什么还喂不饱」（§3.6）**：覆盖广度**不是浪费**——只盯成交额
   前 50 名（占全市场 86.8% 成交额），47 天**一个信号都没有**，4 个候选全在中长尾；
   但覆盖**改不了速率**（526 已是全部合规合约，机会频率被「7 天箱体 + 24 小时冷却」锁死），
   全市场每天 69.57 次机会 × 0.122% 中奖率 = 0.085 个/天。**要样本只能按年等**（30 个 ≈ 1 年）。
3. **修掉 2 个真缺陷**：① 池口径模块 `_pool_scope` 文件在工程内**已丢失**，
   导致 `live_pool` 静默退化到「冻结 375 名单」；② 全局水位取「库最大值」，
   一旦库里出现未来时间戳坏 bar 或预热到过去某刻，引擎会**永久空转且无报错**。
   两处修完标的集合与生产语义**均无变化**（526 = 526；库最大值 ≤ 现在时两者相等）。

**本轮不通过的部分（必须照写）**：日常部署仍**不可交付**。
「链路通」不等于「策略有效」，也不等于「有信号」。当前仍**没有**任何一笔
来自自然行情的实盘/模拟成交。

## 1. 为什么必须先分开两种「0」

生产状态里这三个数字都是 0：

```
signal_engine.signals_generated_total = 0
order_processing.orders_routed_total  = 0
live_signal 表行数                     = 0
```

这有两种**完全不同**的解释，只看数字永远分不出来：

| | 含义 | 该做什么 |
|---|---|---|
| 甲 | **链路断了**：信号生成了，但落库/扫描/路由/挂单某一段接不上 | 修代码 |
| 乙 | **链路通、只是没信号**：策略在这段时间没产出候选 | 不能靠改代码「变出」信号 |

所以本工单做了两件互相独立、都必须能机械复算的事：

- **探针②（`20_e2e_link.py`）** 判「甲」成不成立；
- **探针①（`10_funnel.py`）** 量化「乙」的供给速率。

## 2. 探针②：端到端链路验证（隔离，5/5 通过）

`open_position`——契约校验、epoch 门禁、选 bar、滞后检查、仓位取整、止损计算、
持仓落库**全部是生产代码**。

### 3.5 为什么是这个节奏（`probes/30_rhythm.py` → `out/rhythm.json`）

只念「12 天/个」等于没解释。它其实是三层叠加的结果。

**第一层：五道独立条件相乘**

| 关卡 | 通过率 | 要满足什么 |
|---|---|---|
| 4h 箱体成立 | —（47 天里 3,278 次） | 42 根 4h 宽度在 2A~8A，且效率比 ≤ 0.30（≈7 天横盘） |
| 箱体 → 扫低 | **20.4%** | 最低价落在 `[L−0.5A, L)`（跌破但不超过半个 ATR），**同一根**收盘回到 `L+0.1A` 以上且不高于 `H` |
| 扫低 → 回踩 | **59.7%** | 低点在 `[L, L+0.5A]` 且高于扫低低点、收阳、量 ≤ 0.8×扫低那根 |
| 回踩 → 候选 | **1.00%** | 先不能跌破 `Lr−0.1A`，再首次上穿 `H+0.1A`，且当根量 ≥ 1.5×过去 20 根中位量 |
| 箱体 → 候选 | **0.122%** | 以上全部同时成立 |

**第二层：时间被箱体占满，但转化极低**

平均每标的 **6.2 个箱体** × 每个 7 天窗口 = **43.6 天**，占 47.12 天窗口的 **93%**。
也就是说：一个标的几乎一直待在「某个箱体」里，但其中 **79.6% 连扫低都没等到**，
就过期或失效，然后吃 24 小时冷却再重来。时间不是没花，是花在低转化率的箱体上。

**第三层：回踩之后是真正的断崖**

400 个回踩里，**360 个（90%）**死于「跌破 `Lr−0.1A` 或连续 2 根收盘破 `L`」，
6 个死于「回踩后 7 天内没突破」，剩下才轮到候选。
`P0 = Lr − 0.1A` 这条冻结止损线离回踩低点只有 0.1 个 ATR —— 价格稍一抖就出局。
**这是规则的直接后果，不是实现缺陷。**

**标的层面更直观**：526 个标的里，100% 出过箱体、77.0% 出过扫低、54.9% 出过回踩，
**只有 4 个（0.8%）出过候选**，且每个只出 1 次。

**第四层：统计上还不确定**

只有 4 个事件，点估计本身很粗。精确泊松 95% 区间：

```
lambda = 1.090 ~ 10.242 个 / 47.12 天
⇒ 真实节奏 4.6 ~ 43.2 天/个（点估计 11.8）
```

所以「约 12 天一个」只能当量级看，**不能当精确值**，也不能据此评判策略优劣 ——
要收紧这个区间，唯一办法是攒更多时间的数据。

### 3.6 「全市场 500 多个币」为什么还是喂不饱（`probes/40_coverage.py` → `out/coverage.json`）

这一节回答一个很容易想歪的问题：**都已经盯 526 个标的了，怎么还缺样本？**

**先把数量级纠正过来。** 直觉会算成 `526 标的 × 47 天 = 24,722 次机会`，
但实际只有 **3,278 次**（13.3%）。原因在规则里：箱体成立要 **42 根 4h（7 天）**横盘，
箱体结束后还有 **24 小时冷却**，同一时刻每个标的最多只有一个箱体在观察
⇒ 每标的 47 天平均只有 **6.23 次**机会（中位数 6，最少 2，最多 12）。
**机会不是「每个币每天一次」，是「每个币每 7 天左右一次」。**

**速率恒等式（可复算）**：

```
全市场每天机会 3,278 / 47.12 = 69.57 次
× 单次中奖率 4 / 3,278        = 0.122%
= 每天 0.0849 个 ⇒ 11.78 天/个
校验：69.57 × 0.001220 = 0.08489
```

三项里，**标的数**和**机会频率**都被锁死了，能动的只有中奖率。

**覆盖反事实：只盯大币会怎样**（按窗口内 4h 成交额排序，用各标的**实际**箱体数与实际候选数算）

| 只覆盖 | 成交额占比 | 箱体（机会） | 候选 | 节奏 |
|---|---|---|---|---|
| 前 20 名 | 78.0% | 120 | **0** | 47 天 0 个 |
| 前 50 名 | 86.8% | 292 | **0** | 47 天 0 个 |
| 前 100 名 | 92.7% | 589 | 2 | 23.6 天/个 |
| 前 200 名 | 96.9% | 1,195 | 3 | 15.7 天/个 |
| 前 300 名 | 98.6% | 1,811 | 4 | 11.8 天/个 |
| 全部 526 | 100% | 3,278 | 4 | 11.8 天/个 |

**结论一：覆盖广度不是浪费，是唯一来源。** 只盯成交额前 50 名（占全市场 86.8% 成交额），
47 天**一个信号都没有**。4 个候选全部来自中长尾（成交额百分位 45.6 / 64.3 / 81.4 / 83.5）。
所以「盯 500 多个币」这件事本身是对的，而且是必须的。

**结论二：但覆盖广度改不了速率。** 526 已经是全部合规合约（排除 `ALLUSDT`/`BTCDOMUSDT`
这类指数合约），**没有第 527 个可加**；新上币历史太短，还要吃 48.3 天预热，短期进不来。
每标的机会频率被 7 天箱体 + 24 小时冷却锁死。**唯一还能线性增长的是时间。**

**结论三：低频的成因是「筛得太狠」，不是「市场没机会」。** 按成交额五等分看得很清楚：

| 档位 | 标的数 | 成交额占比 | 箱体 | 候选 | 单次中奖率 |
|---|---|---|---|---|---|
| Q1（最高） | 105 | 93.1% | 615 | 2 | **0.325%** |
| Q2 | 105 | 4.1% | 641 | 1 | 0.156% |
| Q3 | 105 | 1.6% | 651 | 1 | 0.154% |
| Q4 | 105 | 0.9% | 668 | **0** | — |
| Q5（最低） | 106 | 0.4% | 703 | **0** | — |

大币的中奖率是小币的 2 倍（0.325% vs 0.154%），但箱体数并不更多 ——
**长尾是「抽奖次数多、中奖率低」，大币是「抽奖次数少、中奖率高」**，两头都喂不饱。
另外 526 个标的**全部**有效参与（0 个标的箱体数为 0、0 个 4h K 线少于 120 根），
不存在「死币占位」把覆盖稀释掉的情况。

> **不能过度解读的地方（照写）**：上面两张表都是**这 47.12 天的一次实现**，
> 不是「大币永远没信号」的定律，也不是「长尾更好」的证据。全部候选只有 4 个，
> 分到五档后每档 0～2 个，**档间差异远在统计噪声内**。它们只能支撑一个结论：
> 覆盖广度在这段窗口里是必需的；不能支撑任何关于「哪类币更适合这个策略」的判断。

**结论四：攒够样本的时间账（不改任何规则）**

| 目标样本 | 期望耗时 |
|---|---|
| 10 个 | ≈ 118 天 ≈ 0.32 年 |
| 30 个 | ≈ 353 天 ≈ 0.97 年 |
| 50 个 | ≈ 589 天 ≈ 1.61 年 |
| 100 个 | ≈ 1,178 天 ≈ 3.23 年 |
| 200 个 | ≈ 2,356 天 ≈ 6.45 年 |

**这一节不推荐任何做法**。要提速只有三条路，且各有代价：
① 加标的 —— 已无可加；② 加时间 —— 不改规则，但按上表要按年算；
③ 放宽某道关卡（例如回踩阶段不要求不破 `Lr−0.1A`）—— **等于改冻结规则，须走裁决流程**，
且放宽后还是不是同一个策略、样本外表现如何，当前**未验证**，不能假设会更好。

## 4. 修了什么（代码改动）

### 4.1 缺陷：池口径模块丢失，被静默降级

**现象**：`live_pool.scope_symbols()` 返回 **375**、`pool_source=fallback_frozen_375`、
并带 warning「范围文件不可读 ⇒ 已回退冻结 375 名单」。

**根因**：`live_pool.py` 顶部 `import _pool_scope as PS`，期望
`框架/backend/logs/_pool_scope.py`；**该文件在工程内已不存在**（全盘 `find` 无副本，
旧工作区 `取消成交额硬门槛与375新准入37/` 也已不在），于是 `except` 分支启用
`_FallbackPoolScope`。而 `_FallbackPoolScope.binance_scope_symbols()` 读的是
`scope_crypto.json` 的 `symbols`/`binance` 键 —— 该文件用的是 `binance_items`，
所以返回空 ⇒ 再退到冻结 375。

**影响面**：`unified_runtime._default_universe()` 因此不走 `scope_crypto_v1`，
改走行情库兜底（本次恰好也是 526）；但 `live_signal_engine`（旧链路）、
`live_pool.diagnostics`、准入/排名会按 **375** 算，报告里 `pool_source` 写成兜底值。

**修法**：
- 新增 `框架/backend/pool_scope.py`（正规位置，完整实现）；
- 新增 `框架/backend/logs/_pool_scope.py`（三行转发垫片，兼容历史 `sys.path` 布局，
  即使 `logs/` 被日志清理误删，真正的解析逻辑也不会被带走）。

**核对**：范围文件 `binance_items` 526 条 vs 行情库（排除 `ALLUSDT`/`BTCDOMUSDT`）
526 个 ⇒ **逐币完全相同，双向差集为空**。故本修复**零交易行为变化**，只修身份。

### 4.2 缺陷：全局水位取「库最大值」⇒ 预热到过去 / 库里出现未来坏 bar 时**永久空转且无报错**

`MultiSymbolSignalEngine.bootstrap()` 原实现：

```python
self._global_1h = self.watcher.global_last_open("1h")   # ← 全库最大值，与 upto_ms 无关
self._global_4h = self.watcher.global_last_open("4h")
```

而 `step()` 的第一句是：

```python
g1 = self.watcher.global_last_open("1h")
if g1 == self._global_1h and g4 == self._global_4h:
    return []          # 水位没动 ⇒ 整轮空转
```

**两种会变成真故障的场景**：

1. 库里混入**未来时间戳**的坏 bar（本项目历史上多次出现数据质量问题）⇒
   水位被顶到未来 ⇒ `g1 == self._global_1h` 恒成立 ⇒ **引擎永久空转**，
   直到真实挂钟追到那个未来时刻，**且没有任何报错、没有任何红灯**；
2. `run_replay(start_ms)` 或任何「预热到过去某刻」的调用 ⇒ 同样恒空转。

**为什么一直没被发现**：生产上 `upto_ms ≈ now`、库最大值 ≈ now，两者相等 ⇒ 看不出差别。
本轮做漏斗验证时才暴露：预热到「10 天前」再推进 10 天，`step()` 直接返回 0。

**修法（最小）**：水位取「本次真正预热到的那批 bar 里最大的 `open_time`」（必然 `<= upto_ms`）；
只有当库最大值本身就 `<= upto_ms` 时两者相等 ⇒ **生产语义完全不变**。
同时在 `bootstrap_stats` 里如实暴露 `watermark_clamped` 与 `watermark_note`，
避免「引擎空转」再次毫无痕迹。

**验证**：预热到 10 天前再推进 ⇒ `watermark_clamped=true`、`since_start` 正确累计
（箱体 886 / 扫低 341 / 回踩 192 / 候选 0 / 失效 749 / 超时 177 / 错过 3），
修正前同一操作返回 **0**。

### 4.3 让「0 条」不再含糊：漏斗进状态接口

`框架/backend/unified_runtime.py` 新增（**纯只读统计，不改任何成交/止损/仓位/路由判定与时钟口径**）：

- `MultiSymbolSignalEngine.transition_counts` / `history_transition_counts` /
  `candidates_since_start` / `last_candidate_ms`；
- `_absorb_transitions()`：按「已计数条数」幂等推进，**只计 `step()` 期间新产生的迁移**；
- `bootstrap()` 里把预热期迁移记为「历史」，并**不计入** `since_start`
  （否则会把 48 天的历史说成「刚刚发生」）；
- `bootstrap_stats` 新增 `_window_hours`（=1,160h）——「历史 4 个候选」必须带分母才成立；
- 状态接口 `signal_engine.funnel`：
  `{since_start, history, candidates_since_start, last_candidate_ms,
    last_candidate_utc, history_candidates_discarded, bootstrap_window_hours, note}`。

**纪律**：三个数互不替代 ——
`since_start` = 本进程启动后；`history` = 预热回放期（≈48 天）；
`history_candidates_discarded` = 其中产生但按纪律丢弃的候选。
