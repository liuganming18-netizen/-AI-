# 热转冷导出任务

## 它解决什么问题

采集器把实时行情写进**热库**（`数据/市场数据/db/market_v2.sqlite3`），
回测和前端读的是**冷层**（`数据/市场数据/parquet`）。
这两层以前靠一个外部工具手动搬，工具一停，冷层就停在原地——
9 月 14 日之后整整一个月没数据，回测也就跑不到最新。

这个任务把这一步接回项目内部：**热库有新的已闭合 K 线，就自动搬到冷层。**

## 怎么用

```sh
# 启动（已在跑就复用，不会起第二个）
./框架/backend/exporter.sh start

# 看状态和最近日志
./框架/backend/exporter.sh status

# 停
./框架/backend/exporter.sh stop

# 只跑一轮
./框架/backend/exporter.sh once
```

默认每 600 秒一轮，改间隔：`INTERVAL=300 ./框架/backend/exporter.sh start`

## 数据落在哪

```
parquet/candles/{交易所}/{市场}/{标的}/{周期}/live.parquet
parquet/candle_heads/{交易所}/{市场}/{标的}/{周期}/live.parquet   与上一行成对
parquet/oi/{交易所}/{市场}/{标的}/live.parquet
```

`live.parquet` 是**新增文件**，不覆盖任何 `{年份}.parquet` 历史分片。
回测读的是目录下所有 `*.parquet`，所以历史分片和 `live` 会被一起读到，按 `open_time` 去重。

## 为什么只加不改

- 回滚 = 删掉所有 `live.parquet` 和 `_export_state.json`，历史数据一个字节都没动过。
- 每轮写完都是「临时文件 + 原子替换」，中途断电不会留下半个文件。
- 每根 K 线在写入前会和 `_export_state.json` 里的水位比对，保证 `live` 与历史分片不重叠。

## 频率与保护

| 数据 | 频率 | 原因 |
|---|---|---|
| 15m / 1h / 4h | 每轮（10 分钟） | 回测执行和信号确认要用 |
| 5m / 30m / 8h / 12h / 1d | 至少间隔 6 小时 | 回测用不上，没必要反复重写 |
| 持仓量 | 至少间隔 1 小时 | 同上 |

磁盘剩余低于 5 GiB 时自动停手，不会把盘写满。
两轮重叠时后一轮直接跳过（文件锁），不会并发写同一个文件。

## 日志

- 运行日志：`回测日志/热转冷导出.log`
- 水位状态：`数据/市场数据/parquet/_export_state.json`

## 已知限制

1. **热库只保留最近 5 周左右**。9 月 12 日之前的历史行情，热库里没有，只能靠原来的历史下载补，本任务补不了。
2. 冷层中间如果有洞（历史分片本身缺），本任务只追加「比该组合最后一根更新」的数据，填不了洞。要填洞得用 `evidence/Work_补缺落库_2026-10-16/工具_冷层追加补缺.py`。
3. 需要 `pyarrow` + `duckdb`。项目本身没声明依赖，默认用
   `/Users/boos/.workbuddy-ai/binaries/python/envs/default/bin/python`；换解释器设 `PY` 环境变量。
4. 系统级定时（launchd）在本机装不上（`launchctl bootstrap` 报 Input/output error），
   所以现在是**常驻进程**模式。机器重启后需要手动跑一次 `exporter.sh start`。

## 和采集器的关系

采集器（`collector.sh`）负责「从交易所拿数据写进热库」，
本任务负责「从热库搬到冷层」。两者互不依赖，采集停了本任务照样跑（只是没新数据）。
