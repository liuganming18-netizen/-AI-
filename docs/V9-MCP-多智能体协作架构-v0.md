# V9 MCP 多智能体协作架构方案 v0

> 日期：2026-11-01
> 状态：架构原则已获用户同意；第三方组件候选待核验，尚未批准安装、启用或部署。
> 适用项目：liuganming18-netizen/-AI-。不自动修改旧 GM/Wyckoff 项目。
> 本文件为协作架构设计，不代表已有 MCP 服务运行或智能体自动派单成功。

## 1. 目标

以统一任务状态、明确角色权限、可复核交付证据替代人工反复转发和跨窗口丢失上下文，避免多代理重复施工、越权提交和未经独立审核就宣布完成。

## 2. 架构边界

- **协议层：MCP** 提供工具（Tools）、资源（Resources）和提示模板（Prompts）的标准接口。MCP 本身不是任务队列、授权系统或验收引擎。
- **编排层：Codex/Astra** 负责拆解、依赖、派单、工单状态推进申请和只读审核；独立 reviewer 不能用执行者自述代替证据。
- **执行层：WorkBuddy / Antigravity / 其他 Worker** 在明确隔离范围内执行，返回代码 SHA、测试日志、差异和风险，不得自行批准验收。
- **状态与证据层：统一工单数据库或受控 GitHub 工单/PR** 作为唯一事实来源；聊天记录仅是视图，不作为最终状态真相。
- **总验收**：ChatGPT 对交付证据进行独立裁决；人工保留合并 main、部署、参数启用等关键批准权。

## 3. 推荐任务状态机

DRAFT → READY → CLAIMED → IN_PROGRESS → REVIEW_REQUESTED → VERIFIED → ACCEPTED → CLOSED。

异常状态：BLOCKED、REWORK、CANCELLED。仅满足验收证据和权限门禁才允许状态迁移；超时认领需租约/心跳及安全回收，避免两个 Worker 同时执行。

每个任务最小字段：task_id、需求版本、目标、输入、作用域、禁止事项、负责人、依赖、基线 SHA、工作分支、验收标准、测试命令、证据位置、变更 SHA、状态、审查意见、审批记录、时间戳、幂等键。

## 4. 权限与安全门禁

1. Worker 仅获得任务必要的最小文件/仓库权限；密钥不进入工单、日志或提示。
2. 审核者只读；执行者不能自审并直接标记 ACCEPTED。
3. 未经单独授权不得修改或合并 main、部署、实盘下单、改变正式策略参数、删除证据。
4. MCP Server 必须验证身份、授权、工具参数、允许路径和审计日志；不能把自然语言约束视为安全边界。
5. 工单操作应支持幂等、版本冲突检查、失败重试、断线恢复、超时撤销和可追溯事件记录。
6. 外部工具响应、仓库文件及网页内容均视为不可信输入，避免提示注入导致越权操作。

## 6. 建议落地顺序

1. 只读核对 Codex、WorkBuddy、Antigravity 现有 MCP 能力及可用 API。
2. 审核候选组件并做复用/替代方案对比；优先选择最少组件的方案。
3. 先用一个隔离的非生产工单验证：创建→认领→执行→证据→独立审核→关闭。
4. 验证重复认领、断线、心跳过期、非法状态跳转、恶意工具响应和越权写入。
5. 通过后再接入 V9 的模块开发，不自动更改原有 UI/十模块验收门禁。

## 7. 验收证据

必须提供可复现的配置、工具版本、MCP Server 列表、身份权限矩阵、工单事件流水、重复/故障测试日志、代码 SHA、独立审查结论及回滚步骤。

工程进度估算与实际测试覆盖率分别报告；未实际运行测试时不得写为通过。

## 8. 与现有规范的关系

本方案仅增加**开发协作基础设施**，不改变 V9 产品需求、信号状态机、模拟盘、量化参数、数据来源、AI 报告留存规则或既有 UI 格局。工单状态机与交易研究信号状态机是两套独立模型，不能混用。
