## 1. 本次冻结的产品方向
AI根据全量历史背景与实时证据，研究震荡阶段的潜在承接、吸筹、派发等行为假设；不是先建立
一整套传统指标买卖策略再让AI写解释。程序负责数值计算、数据与几何校验，AI负责提出结构、
假设、反证及画线提案，模拟风险规则独立执行。

界面保持深蓝紫玻璃三栏：左侧四个主导航“加密货币、数据监控、策略分析、历史回测”，中部榜单
与K线、图表下可折叠AI对话面板，右侧模拟盘。不能改格局。面向用户的文字全部中文，币种代码、
代码关键字、标准接口字段按技术需要保留英文。

日线为背景，1h/4h/8h为核心结构分析；5m只辅助入场定位。支持5m/15m/30m/1h/4h/8h/12h/1d，
拒绝1m。8h沿用已确认的币安原生约束。币安主源，只有币安没有对应合约才核验并使用OKX独立系列；
不跨交易所偷偷拼接。仅模拟，没有真实交易通道。

### 建议落地形态：本地模块化系统，不先拆成微服务
浏览器终端 → 统一API → 只读行情/证据/图形/信号查询。
统一数据入口 → 质量与时间门禁 → 扫描与证据计算 → AI主模型/复核 → 图形与判断版本
→ 唯一信号中心 → 页面/通知/模拟账户。
同一数据快照与事件契约供历史回放读取；运行状态持续进入“数据监控”的动态画布。

建议进程职责：一个前端/API服务、一个受控数据写者（已有共享服务能提供则不新建）、一个
受预算约束的分析工作进程，以及仅模拟的执行/核算进程。可部署为同一代码仓库里的模块，
不要求一模块一服务。后台长任务不塞进HTTP请求线程。数据库是唯一事实来源，页面不是数据库。

原始数据：已有热数据/冷Parquet不复制。状态元数据：本地SQLite优先候选。分析查询：
DuckDB按分区读取，避免整库载入16GB内存。需要多机多写且有实测证据时再考虑PostgreSQL。
任务先采用事务发件箱与幂等消费；首版不默认部署Redis、Kafka或Kubernetes。[S11—S13、S21]

现有Node候选服务可以先保留；是否引入React/TypeScript/Vite与Python/FastAPI通过各模块概念验证决定，
不是为了套技术栈先推翻现有可用功能。[S02、S09、S20]

AI输出的是中立绘图对象，不是屏幕像素，也不是生成图片。前端通过图表适配器调用覆盖物接口；
KLineChart提供时间/价格锚点、锁定及交互回调，Lightweight Charts可通过插件/图元实现同类能力。

七类验收对象：支撑线、阻力线、趋势线、震荡箱体、承接/派发区域、关键事件标记、判断失效线。

线条可以从已知锚点向未来空白区域延伸，但不能拿未来K线的实际价格作锚点。
10000根K线/100个图形、两种价格轴、像素比1与2、75%/100%缩放下，数据锚点不变；
重投影误差≤2 CSS像素为本方案提出的工程目标。

例如：10:00发布版本1，10:15更新版本2，10:30撤销。回放到09:59不能见线，
10:10只能见版本1，10:20只能见版本2，10:40不能再显示为有效，但撤销历史可查。
历史重评的系统生成时间与历史决策时钟必须分开，不伪称模型过去真的给过该判断。

## 5. 执行顺序与通用验收门禁
G00准备 → M01界面与基础行情 → M02图表绘图 → M03统一数据 → M04扫描调度
→ M05行为证据 → M06AI与自动画线 → M07信号观察与通知 → M08画像
→ M09模拟核算 → M10回放、监控、部署与最终交付。

严格按模块串行。可预先研究备选，但不得跨模块并行施工。每张工单是一项独立候选变更；
执行代理按专长领取，但同时只允许当前获准模块的工单施工。总验收人只对可读证据及实际复现
作出裁决，不能因施工代理自报完成而写PASS。

M10内部的研究样本不足不阻止已通过的工程功能继续做前瞻模拟采样；
但不得解锁“已证明有效”的宣传或新增真实交易。将工程通过、研究待积累分开登记，避免循环依赖。


每张工单的通过条件：边界无越权；全部P0用例实际运行并通过；P1全部关闭或有明确批准的延期记录；
输入、输出、错误路径、重启/恢复路径均可复现；提交SHA、环境锁文件、数据/夹具版本与报告一致；
由非施工者独立复核。用户明确确认本模块后，才能解锁下一模块。“条件通过”不自动解锁。

报告必须区分：通过、失败、错误、跳过、未运行、阻塞。没有日志不是通过；有测试文件不等于执行过；
通过率不是代码覆盖率；界面截图不是完整交互验收；工程运行通过不是AI预测能力或盈利能力证明。
本轮仅制定方案与检查交付文件，未执行这115项业务验收用例。

建议工程测试门槛（执行前在G00-02冻结）：新建核心领域模块行覆盖率≥90%、分支覆盖率≥85%；
