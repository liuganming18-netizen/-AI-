# 后端架构重构方案（2026-10-19）

> **定位**：本文只解决**运行架构**问题——进程怎么分、请求怎么走、任务怎么排队、数据谁来写、出错怎么查。
> 不涉及策略语义、撮合规则、账本口径。那部分以 `docs/系统架构收敛与施工蓝图_2026-10-16.md` 为准，两者是上下层关系，不冲突。
>
> **硬边界**：冻结核心（规则文件 SHA256 `1f1167de…9a8ab`）、撮合取整、PIT 守卫、账本目录规则，本轮**一行不改**。任何重构若需要动它们，方案作废。

---

## 〇、给不看代码的人：三句话

1. **现在的问题不是"代码写得差"，是"所有事挤在一个进程里"**。网页请求、行情入库、回测计算、缓存全在同一个进程。回测一跑满，网页就卡；进程一崩，全挂。
2. **改法不是推倒重来，是"分房间"**。把网页服务、后台计算、行情采集拆成独立进程，中间用一张任务表传话。一个房间着火，其他房间照常营业。
3. **风险可控**。分五期做，每期都能单独上线、单独回滚。每期上线前用"改造前后接口返回逐字节比对"证明行为没变。

## 一、现状实测（先看数字，不看感觉）

| 项目 | 实测值 | 说明 |
|---|---|---|
| 后端代码总量 | 26,510 行 / 30 个文件 | `框架/backend/` |
| 主文件 `adapter.py` | 3,826 行 / 126 个函数 / 34 个路由分支 | 传输、业务、SQL、缓存混在一起 |
| 自动化测试 | 346 项可收集（65 项按环境跳过）；第 2 期新增 17 项 | 已有较好护栏，重构必须全绿 |
| 回测产物目录 | 1,198 个 run 目录 | 每个目录若干 JSON 文件 |
| 行情库 | 7.6 GB + WAL 782 MB | `market_v2.sqlite3` |
| 冷层归档 | 19 GB Parquet | 已按 30 天热/冷分层 |
| 进程内并发上限 | 64（轻接口 12 / 重接口 52） | 代码里手工划分的信号量 |
| 大响应字节缓存 | 3 秒 | 只对 4 个最大只读端点生效 |
| 鉴权 | **无** | 仅靠"只监听本机回环" |

这些数字说明一件事：**过去半年系统是在"打补丁式救火"**。代码注释里留下了完整的救火记录——线程从 24 提到 64、加轻/重两套信号量、加 3 秒字节缓存、加单飞（同一 key 只允许一个线程重算）、加连接池避免单请求新建 557 个连接。这些补丁每一个都对，但它们治的都是症状。症状的根在架构。

## 二、六个真正的病根（按影响排序）

### 病根 1：一个进程干所有事，故障连坐

现在 `adapter.py` 一个进程里同时装着：HTTP 服务、响应缓存、SQLite 连接池、回测执行线程（`threading.Thread`，daemon）、行情尾段入库。

后果有三层：

- **崩溃连坐**：回测线程里一个未捕获异常，或者一次内存暴涨，整个进程死，网页跟着 502。
- **算力连坐**：回测是纯 CPU 计算，Python 有全局解释器锁（GIL），回测跑满时网页请求拿不到 CPU。代码注释里记录的"轻接口 p50 从 7 毫秒恶化到 3 秒以上"就是这个原因。
- **状态连坐**：缓存、连接池、任务表全在进程内存里，重启即清零。

### 病根 2：读接口会写库，而且是三个写者抢一个库

这是最隐蔽、也最该先修的一条。

`adapter.py:1952` 在 K 线读取路径里调用 `_tail_store()`，把 REST 补来的尾段**写进行情库**（`adapter.py:1884–1935` 有 INSERT / UPDATE / DELETE）。也就是说：**用户打开一张 K 线图，可能触发一次数据库写入**。

同时还有另外两个写者：实时采集器（`realtime_collector.py`）、历史下载器。三个进程/线程写同一个 7.6 GB 的 SQLite 文件。

SQLite 同一时刻只允许一个写者。写者一多，就出现：写锁等待 → WAL 无法检查点 → WAL 膨胀到 782 MB → 每个新连接都要读 WAL 索引 → 单请求从毫秒级掉到秒级 → 前端 5 秒轮询追不上 → 线程堆积。代码注释里记录的"1,971 个 socket、1,742 个数据库文件句柄"就是这么来的。

**所以：不是库太小，是写者太多，而且读路径不该写。**

### 病根 3：后台任务只活在内存里

`backtest_api.py:1020` 创建回测的方式是：起一个 daemon 线程，把线程对象塞进一个字典 `_THREADS`。

这意味着：

- 进程重启 → 正在跑的回测**直接消失**，启动钩子只能把它标成 `interrupted`（`backtest_api.py:1127`）。
- 没有排队 → 同时点 10 次回测就是 10 个线程一起抢 GIL。
- 没有重试 → 一次网络抖动就整单失败。
- 没有取消 → 用户点"停止"没有实现路径。
- 没有进度 → 前端只能轮询状态字段。

### 病根 4：列表接口靠扫目录

`backtest_store.py:432` 的 `list_runs()` 会遍历 `runs/` 下所有子目录，逐个 `json.load`。现在有 **1,198 个目录**，每次列表请求的成本随 run 数量线性增长，而且是无上限的。

同理，`/api/v1/markets` 一次请求要为 549 个标的各查一次摘要。现在的解法是 2 秒 TTL 缓存——这是对的应急手段，但本质是"用缓存掩盖没有索引"。

### 病根 5：路由是 3,826 行文件里的 if/elif 长链

`adapter.py:3234` 的 `route_v1()` 是一串 `if seg == [...]`，34 个分支。新增一个接口必须改这个文件，而且必然和别人的改动撞车。

更麻烦的是：路由、参数解析、业务逻辑、SQL、降级文案全写在同一个函数里。想单独测试一个接口的业务逻辑，只能起整个服务。

### 病根 6：出问题只能靠翻日志和猜

- 没有请求标识，一条错误日志无法串起"哪个请求、走了哪条路、卡在哪一步"。
- 没有慢查询记录。
- 没有任务看板（现在有多少在跑、多少在排队、多少失败）。
- 健康检查只有"能返回 200"，不区分"进程活着"和"依赖可用"。

## 三、目标架构

### 3.1 进程拓扑（仍然只有一个对外端口 8787）

```
启动系统.command
      │
      ▼
 守护进程 supervisor.py          ← 拉起、监控、崩溃自动重启、单实例锁
      │
      ├── web 进程        :8787   ← 只做 HTTP：路由、鉴权、参数校验、读模型
      │                              【严格只读，绝不写行情库】
      │
      ├── worker 进程     无端口   ← 只做后台计算：回测、导出、重算
      │                              【唯一写任务库；按租约领任务】
      │
      ├── collector 进程  无端口   ← 行情采集（已有，保持独立）
      │                              【行情库的唯一写者】
      │
      └── maintenance 进程 无端口  ← 定时：WAL 检查点、索引重建、过期清理
```

**关键点：进程之间不共享内存，只通过一张任务表（SQLite）传话。不新增任何对外端口。**

为什么不新增端口：用户的既有约定是"统一走 3000 一个口"，后端只在 8787 被前端代理。多开端口会让部署、防火墙、调试全部复杂化，收益为零。

### 3.2 分层（模块化单体，不是微服务）

```
┌─────────────────────────────────────────────────┐
│ 接入层  api/                                     │
│   路由注册表 · 中间件（请求标识/鉴权/限流/计时）    │
│   按资源分文件：markets / signals / paper / ...   │
├─────────────────────────────────────────────────┤
│ 应用层  application/                             │
│   用例编排：创建回测、查信号、下单、导出           │
│   只依赖领域接口，不写 SQL、不碰 HTTP             │
├─────────────────────────────────────────────────┤
│ 领域层  domain/  【冻结，只读引用，零改动】        │
│   策略核心 · 撮合取整 · PIT 守卫 · 账本口径        │
├─────────────────────────────────────────────────┤
│ 基础设施  infrastructure/                        │
│   仓储（行情/回测/账本）· 任务队列 · 缓存          │
│   交易所网关（含熔断）· 数据库连接角色             │
└─────────────────────────────────────────────────┘
```

依赖方向**只能从上往下**。领域层不知道 HTTP 存在，也不知道 SQLite 存在。这条规则用一条静态检查脚本守住：`domain/` 目录里出现 `import sqlite3`、`import http`、`import requests` 即构建失败。

### 3.3 三个扩展点（"扩展性"落到具体动作）

| 要加什么 | 现在要改哪 | 改造后要改哪 |
|---|---|---|
| 一个新接口 | 改 `adapter.py`（3,826 行）+ 改路由长链 | 新建 `api/resources/xxx.py`，在路由表注册一行 |
| 一个新策略 | 改注册表 + 可能改执行桥 | 实现策略协议 + 注册，不碰执行与账本 |
| 一个新数据源 | 改采集器主循环 | 实现数据源协议 + 注册，采集器按注册表轮询 |

判断标准很简单：**加功能时需不需要打开一个超过 500 行的文件。** 需要，就是扩展性没做好。

## 四、关键设计决策（连同被否方案）

### 决策 1：模块化单体，不做微服务

**采纳**：单进程部署单元，内部按层分包。

**否决微服务**，理由不是"保守"，是三条硬事实：

1. 单机部署。微服务的收益（独立扩缩容、故障隔离）在单机上大部分拿不到，但网络调用、序列化、分布式追踪的成本全额支付。
2. Python + GIL。拆成多个 HTTP 服务不会增加 CPU 并行度，只会增加 HTTP 开销。真正要的是**多进程**，不是**多服务**。
3. 346 项测试是围绕进程内调用写的。拆服务等于重写测试，且会引入"分布式事务"这个新问题——而交易系统的账本恰恰最怕这个。

**保留微服务的一个好处**：故障隔离。这一条用"多进程 + 任务表"拿到了，成本低一个数量级。

### 决策 2：任务队列用 SQLite 表，不引入 Redis / RabbitMQ

**采纳**：同一台机器上建一个 `jobs.sqlite3`，WAL 模式，web 写任务，worker 领任务。

**否决消息队列**，理由：

- 引入一个常驻中间件，就多一个会挂的组件、多一套要备份的数据、多一份要监控的东西。当前系统连"任务表"都还没有，先补最基础的一层。
- 任务量级是每天几十到几百个（回测、导出），SQLite 每秒能处理数千次事务，量级差三个数量级。
- SQLite 任务表天然可查、可审计、可用任意工具打开看，符合这个项目"一切可对账"的风格。

**代价**：跨机器扩展不了。但当前是单机，且短期没有多机需求。任务表结构设计成与具体数据库无关（纯 SQL 标准子集），将来要换 PostgreSQL 只改连接层。

### 决策 3：行情库继续用 SQLite，暂不迁 PostgreSQL

**采纳**：保留 SQLite，但做三件事——**单写者、读写连接分离、定期检查点**。

**否决迁移**，理由：

- 7.6 GB 数据、单机、读多写少，SQLite 完全够用。现在的慢不是数据库选型问题，是写者太多 + 没有索引。
- 迁移要停机、要重写所有 SQL、要重跑 346 项测试、要重新验证账本恒等式。风险极高，收益不明。
- 真正需要分析型查询（全池历史扫描）的部分，已经走 Parquet + DuckDB 冷层了，那才是正确的工具。

**留后路**：所有 SQL 收进 `infrastructure/repo/`，上层只调仓储方法。将来真要换，改一个目录，不改业务。

### 决策 4：web 进程必须严格只读

**采纳**：web 进程对行情库只开 `mode=ro` 连接。所有写入（尾段补写、导入、归档）移交给 collector 或 worker。

这是本轮**最重要的一条**。它同时解决三个问题：写锁竞争、WAL 膨胀、读请求延迟不可预测。

**代价**：K 线读取时若发现尾部缺失，不能当场补了。改为投递一个"补尾"任务，前端这次先返回已有数据并带 `missing_reason`。这符合项目既有纪律——**缺数据就说缺，不偷偷补**。

### 决策 5：任务必须持久化，且副作用必须幂等

**采纳**：任务落表，至少一次投递（at-least-once），配合业务幂等键。

**关键区分**：

- **可重算的任务**（回测、导出、索引重建）：重跑无害，租约到期自动重投。
- **有外部副作用的动作**（下单、平仓、写账本）：**绝不允许盲目重跑**。做法是"意图先落库，再执行"——先把 `client_oid` 和意图写进库，再调交易所；重试时先按 `client_oid` 查是否已成交。这是唯一能保证"不重复下单"的结构。

这条不是新发明，是交易系统的标准做法。当前代码里 `trd_…` 这类账本 ID 已经具备幂等基础，把它提升为强制约束即可。

## 五、分模块设计

### 5.1 接入层（`api/`）

**路由注册表**替换 if/elif 长链：

```python
ROUTES = [
    Route("GET",  "/api/v1/health",            health.get,      group="light"),
    Route("GET",  "/api/v1/markets",           markets.list,    group="heavy", cache=3),
    Route("POST", "/api/v1/backtests",         backtests.create, group="write", idempotent=True),
    # 新增接口只在这里加一行
]
```

匹配用"静态段优先、参数段兜底"的两级匹配，避免现在的长链顺序依赖。

**中间件链**（顺序固定）：

1. 请求标识：生成 `request_id`，写入日志与响应头。
2. 来源校验：写接口校验 `Origin`，防浏览器跨站写（当前完全没有，属于真实缺口）。
3. 鉴权：写接口要求本机令牌（从环境变量读，不落盘）。读接口保持无感。
4. 限流：沿用现有轻/重分组，补每客户端令牌桶。
5. 计时：记录总耗时、数据库耗时、缓存命中。
6. 异常兜底：统一转成错误信封，**不泄漏堆栈到响应**（现在会把异常类型名返回给前端）。

**统一错误信封**（在现有 `envelope` / `missing` 基础上补齐）：

```json
{
  "error": {"code": "RUN_NOT_FOUND", "message": "回测不存在", "retryable": false},
  "request_id": "req_01J...",
  "as_of": "2026-10-19T00:00:00Z"
}
```

错误码用枚举，不用中文句子当机器标识——现在前端只能靠字符串匹配判断错误类型，很脆。

### 5.2 应用层（`application/`）

每个用例一个函数，输入是普通数据结构，输出是普通数据结构。不碰 HTTP，不碰 SQL。

```
backtest_service.create(spec, idempotency_key) -> job_id
backtest_service.status(job_id)                -> 状态 + 进度
signal_service.query(filters)                  -> 分页结果
paper_service.place_order(intent)              -> 订单结果（幂等）
```

好处是可测：这些函数可以脱离 HTTP 直接单测，不需要起服务。现在 346 项测试里有相当一部分必须起服务才能测，这是可以砍掉的成本。

### 5.3 任务与工作进程（`infrastructure/jobs/` + `workers/`）

任务表结构见附录 A。核心语义：

- **领取**：`BEGIN IMMEDIATE` 事务内选出优先级最高、创建最早、租约已过期的任务，条件更新为 `running` 并写 `lease_owner` / `lease_until`。
- **心跳**：worker 每 10 秒续租。续租失败（说明被判定死亡）立即停止当前任务，不再产生副作用。
- **回收**：`lease_until` 过期 → 回到 `queued`，`attempts + 1`。超过 `max_attempts` → `failed`，保留 `error_json`。
- **取消**：置 `canceled`，worker 在检查点（每个批次之间）读取状态并主动退出。
- **幂等**：`idempotency_key` 唯一索引。重复提交返回已有 `job_id`，HTTP 200 而不是 202。

**并发控制**：worker 进程内固定 N 个执行槽（默认 2），N 由环境变量控制。回测是 CPU 密集，超过核数没有意义，只会互相拖慢。

### 5.4 数据访问层（`infrastructure/repo/`）

**连接角色**（这是修病根 2 的核心）：

| 角色 | 谁用 | 打开方式 | 数量 |
|---|---|---|---|
| 只读 | web | `mode=ro` | 池，上限 24 |
| 写 | collector / worker | 普通连接 + `busy_timeout` | **全局 1 个** |
| 任务 | web（写）/ worker（读写） | 独立 `jobs.sqlite3` | 各自 1 个 |

**单写者原则**：每个数据库文件同一时刻只有一个写进程。这条写进启动脚本的注释和检查脚本，违反即告警。

**WAL 检查点**：maintenance 进程每 5 分钟检查 WAL 大小，超过 256 MB 执行 `PRAGMA wal_checkpoint(TRUNCATE)`。只在无长事务时执行，失败不重试（下次再来）。

**读模型物化**（修病根 4）：

- 新建 `run_index` 表：`run_id, strategy_id, status, created_at, symbol_count, net_pnl, ...`。
- 写入 run 时同步更新索引（同一事务）。
- 列表查询走索引表，`LIMIT/OFFSET` 或游标分页，**不再遍历目录**。
- 首次上线时跑一次全量重建（1,198 个目录扫一遍，一次性成本），之后增量维护。
- 索引表与目录不一致时，maintenance 进程做抽样校验并告警，不自动删数据。

### 5.5 缓存（`infrastructure/cache/`）

保留现有三套机制，但收进一个模块并明确语义：

| 机制 | 现在 | 改造后 |
|---|---|---|
| TTL + 单飞 | `_ttl()`，散在 adapter | 统一 `cache.get_or_compute(key, ttl, producer)` |
| 字节缓存 | `Handler._RESP_CACHE`，类属性 | 独立模块，按路由声明 `cache=3` 启用 |
| 连接池 | `_DB_POOL` 全局列表 | 按角色分池，带健康检查（坏连接丢弃） |

**新增一条**：写操作必须显式失效相关缓存键。现在没有失效机制，全靠 TTL 自然过期，导致"刚下的单查不到"这类问题。改为写后主动 `invalidate(prefix)`。

### 5.6 可观测（`infrastructure/observability/`）

**结构化日志**：JSON Lines，每条必带：

```json
{"ts":"...","level":"info","request_id":"req_...","route":"GET /api/v1/markets",
 "status":200,"duration_ms":42,"db_ms":31,"cache":"hit","job_id":null}
```

**指标**（`GET /api/v1/metrics`，纯文本，便于接入任意监控）：

- 请求：按路由的计数、p50/p95/p99 延迟、状态码分布。
- 数据库：连接池借出/归还/等待、写锁等待时长、WAL 大小。
- 任务：各状态计数、排队时长、执行时长、失败率。
- 缓存：命中率、陈旧命中、后台重算次数。

**分级健康**：

- `liveness`：进程活着（不做任何 IO）。
- `readiness`：数据库可读、任务表可写、冷层可访问。
- 现有 `health_items` 保留，作为 readiness 的明细。

**慢查询**：超过 200 毫秒的 SQL 记录指纹 + 参数摘要（脱敏），供后续加索引。

### 5.7 安全（`api/middleware.py`）

现状是**完全没有鉴权**，只靠"绑定 127.0.0.1"。这个假设在单机场景下基本成立，但有两个真实缺口：

1. **浏览器跨站写入**：任何网页都能向 `http://127.0.0.1:8787/api/v1/paper/orders` 发 POST。本机服务对浏览器是同源的"内网"，CSRF 防护不能省。
2. **误绑定**：一旦有人把监听地址改成 `0.0.0.0`（调试时常有），整套系统直接暴露，无任何保护。

措施（都很轻，不影响使用）：

- 写接口校验 `Origin` 必须是 `http://127.0.0.1:3000` 或 `http://localhost:3000`。
- 写接口要求本机令牌，令牌由启动脚本生成写入 `.system/token`（权限 600），前端由同源代理注入。
- 启动时检查监听地址，非回环则**拒绝启动**，除非显式设置 `ALLOW_NON_LOOPBACK=1`。
- 启动时校验冻结核心 SHA256，不匹配拒绝启动。这条能防"核心被改了却没人知道"。

### 5.8 配置与启动

- 所有配置走环境变量，集中在一个 `config.py` 里声明、校验、给出默认值。现在是 17 处散落的 `os.environ`。
- 启动时打印生效配置（脱敏），并写入日志首行。现在出问题要先猜"到底用的哪个库、哪个解释器"。
- 启动顺序：supervisor → 检查单实例锁 → 起 collector → 起 worker → 起 web → 起 maintenance。任一关键进程起不来，整体退出并报错（fail-loud），不静默降级。

## 七、五期迁移路线（每期可独立上线、独立回滚）

原则：**绞杀者模式**。新结构从外面包住旧结构，旧代码一段段搬走，任何时刻系统都是可运行的。

### 第 0 期：立基线（半天）

不改任何业务代码，只建立"改坏了能立刻发现"的能力。

- 跑通全部 346 项测试，记录结果。
- 对所有 GET 接口抓一份响应快照存 `evidence/架构重构基线_2026-10-19/golden/`，比对时忽略 `as_of`、时间戳、耗时字段。
- 压测基线：50 并发重请求 + 8 个轻探针，记录 p50/p95、5xx 数、文件句柄数。
- 记录冻结核心文件的 SHA256。

**回滚**：无（只读操作）。

### 第 1 期：抽路由表（2–3 天）

- 把 `route_v1()` 的 34 个分支搬进 `api/resources/`，函数体**原样搬**，只改签名。
- 路由表注册，匹配逻辑用新实现，但保留旧长链作为兜底开关 `LEGACY_ROUTER=1`。
- 验收：全部 GET 响应与第 0 期快照**逐字节一致**（忽略声明字段）。

**回滚**：置 `LEGACY_ROUTER=1`，一个环境变量回到旧路径。

### 第 2 期：拆进程 + 任务表（3–5 天）

- 新建 `jobs.sqlite3` 与任务表。
- 回测创建改为投递任务，`POST /api/v1/backtests` 返回 `job_id`（字段兼容现有 `run_id`）。
- 新增 `workers/backtest_worker.py`，领任务、执行、写回状态。
- web 进程不再起任何回测线程。
- 启动脚本加 supervisor。

**验收**：

- 提交 20 个回测，全部完成，结果与改造前逐笔一致。
- `kill -9` worker，任务在租约过期后自动重跑，最终结果不重复、不丢失。
- `kill -9` web，5 秒内自动拉起，正在跑的回测不受影响。
- 50 并发重请求下，轻接口 p95 相比第 0 期**不劣化**。

**回滚**：`INPROCESS_JOBS=1` 回到线程模式；任务表保留不删。

### 第 3 期：web 只读 + 读模型（3–4 天）

- web 的数据库连接全部改 `mode=ro`；`_tail_store()` 调用改为投递"补尾"任务。
- 建 `run_index` 表，全量重建一次，列表接口切过去。
- `/api/v1/markets` 的摘要改为读物化表，保留 TTL 缓存作为第二层。

**验收**：

- 全库扫描确认 web 进程打开的行情库连接均为只读（`PRAGMA query_only`）。
- 列表接口在 1,198 → 2,000 个 run 时耗时**不随数量线性增长**。
- WAL 峰值 < 256 MB，写锁等待 p95 < 50 ms。
- 缓存失效生效：写后立即读能拿到新值。

**回滚**：路由切回旧实现，索引表保留（不影响旧路径）。

### 第 4 期：可观测 + 鉴权 + 优雅退出（2–3 天）

- 结构化日志、指标端点、慢查询记录、任务看板。
- 写接口加来源校验与令牌；启动加监听地址与核心哈希校验。
- 优雅退出：收到信号停止接新请求，等在飞请求最多 10 秒，worker 交还租约。

**验收**：

- 任一错误日志能用 `request_id` 串起完整调用链。
- 伪造 `Origin` 的写请求被拒（403）。
- `SIGTERM` 后无请求被截断、无任务被误判失败。

**回滚**：鉴权开关 `AUTH_MODE=off`；日志与指标只增不减，无回滚需求。

### 第 5 期（持续）：按需演进

不在本轮做，但接口留好：数据层换 PostgreSQL、冷层换 DuckDB 直查、任务表换外部队列。都是替换 `infrastructure/` 下的一个实现，不动上层。

## 八、验收门禁（硬指标，不达标不算完成）

| 编号 | 门禁 | 判定方式 |
|---|---|---|
| G1 | 行为零变化 | 全部 GET 响应与基线快照逐字节一致（忽略声明字段） |
| G2 | 测试全绿 | 原有 346 项 + 新增项全部通过，`--basetemp` 指定可写目录 |
| G3 | 冻结核心零改动 | 核心文件 SHA256 与第 0 期一致 |
| G4 | 进程隔离有效 | `kill -9` 任一非 web 进程，读接口 5 秒内仍可用 |
| G5 | 任务不丢不重 | 崩溃注入 20 次，任务完成率 100%，副作用重复次数 0 |
| G6 | 背压有效 | 50 并发重请求下，轻接口 p95 < 200 ms，5xx = 0，句柄数不增长 |
| G7 | 写者唯一 | 运行 10 分钟采样，行情库写连接持有者恒为 1 个进程 |
| G8 | 扩展成本 | 新增一个只读接口，改动文件数 ≤ 2，无需打开 500 行以上文件 |

G5 的"副作用重复次数 0"是最高优先级。回测重跑无所谓，下单重复是事故。

## 九、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 拆进程后调试变难 | 定位问题变慢 | `request_id` 贯穿所有进程日志，日志统一写一处 |
| SQLite 多进程写冲突 | 写入失败 | 单写者原则 + `busy_timeout=10s` + 写失败进重试队列 |
| 迁移期新旧路径并存 | 行为分叉 | 每期只切一条路径，开关控制，快照比对 |
| 任务重复执行 | 账本错乱 | 业务幂等键 + 意图先落库，G5 门禁卡死 |
| 基线快照本身有错 | 误判"零变化" | 快照由两个独立进程各抓一次，不一致则人工复核 |
| 改造引入性能回退 | 页面变慢 | 每期都跑同一套压测，与第 0 期对比 |

**总回滚方案**：保留第 0 期的完整代码快照与数据库备份。任何一期出问题，`git` 回退 + 环境变量切旧路径，不需要恢复数据（因为每期都不改数据结构，只加表）。

## 十、明确不做的事

1. **不拆微服务**。单机、GIL、346 项进程内测试，收益为负。
2. **不引入 Redis / Kafka / 消息队列**。多一个常驻组件就多一个故障点。
3. **不迁 PostgreSQL**。当前瓶颈不是数据库选型。
4. **不改冻结核心**。策略、撮合取整、PIT、账本口径一行不动。
5. **不改前端契约**。所有接口字段只增不改，前端零改动。
6. **不新增对外端口**。仍然只有 8787。
7. **不做大爆炸式重写**。每期都可独立上线、独立回滚。

## 附录 A：任务表结构

```sql
CREATE TABLE jobs (
  job_id           TEXT PRIMARY KEY,
  kind             TEXT NOT NULL,              -- backtest / export / backfill / reindex
  idempotency_key  TEXT UNIQUE,                -- 业务幂等键，重复提交返回同一任务
  payload_json     TEXT NOT NULL,
  state            TEXT NOT NULL,              -- queued / running / succeeded / failed / canceled
  priority         INTEGER NOT NULL DEFAULT 0,
  attempts         INTEGER NOT NULL DEFAULT 0,
  max_attempts     INTEGER NOT NULL DEFAULT 3,
  lease_owner      TEXT,
  lease_until      INTEGER,                    -- 毫秒时间戳
  heartbeat_at     INTEGER,
  progress_json    TEXT,                       -- 供前端轮询进度
  result_ref       TEXT,                       -- 结果存放位置（run_id 或文件路径）
  error_json       TEXT,
  created_at       INTEGER NOT NULL,
  started_at       INTEGER,
  finished_at      INTEGER
);

CREATE INDEX idx_jobs_claim ON jobs(state, priority DESC, created_at);
CREATE INDEX idx_jobs_kind  ON jobs(kind, state);
```

领取语句（单条原子操作，避免惊群）：

```sql
UPDATE jobs
   SET state='running', lease_owner=?, lease_until=?, heartbeat_at=?,
       attempts=attempts+1, started_at=COALESCE(started_at, ?)
 WHERE job_id = (
   SELECT job_id FROM jobs
    WHERE state='queued'
       OR (state='running' AND lease_until < ?)
    ORDER BY priority DESC, created_at
    LIMIT 1
 )
 RETURNING *;
```

**结论**：这次重构的核心不是"写更好的代码"，是把**故障域**切开。现在一个进程里任何一处出问题都能拖垮全部；改造后，网页、计算、采集各自独立，一个倒下不影响其他。同时把"读请求写库"这个隐藏多年的根因拔掉，把后台任务从内存搬进数据库。
